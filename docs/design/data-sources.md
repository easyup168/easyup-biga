## 0. 这份文档要回答的问题

不是「我们用了哪些源」——那个 `bin/biga-data providers` 就能列。
是下面这三个**换源时才会问、而那时已经来不及查**的问题：

| 问题 | 为什么重要 |
|---|---|
| 这个 dataset 挂了，有没有第二条路？ | 没有备胎 ⇒ 源一挂，当天整条链停 |
| 备胎和主源**口径一样吗**？ | 不一样却当等价用 ⇒ 降级那天的数悄悄变了含义 |
| 换到备胎之后，**还剩几道校验**？ | 有些校验依赖主源特有的字段，换源后会**静默退化成恒等式** |

🔴 第三条最容易漏。举一个本仓库真实的例子：
`cn.security_master` 的质量策略里有一条「provider 自报总数 vs 实际归一化条数」。
备用源**不自报总数**，于是那道校验在降级时两边恒等 —— **它还在跑，但什么都没查**。

> **一道在降级时退化成恒等式的校验，比没有这道校验更危险：
> 它让人以为那天也被查过。**

### 2.1 对照组读出来的结论：东财是**按 host 组**挂的，不是整体限流

`push2` / `push2his` 全挂，而**同一时刻、同一 IP、同样的请求头**下
`push2ex` / `datacenter` 正常。所以：

> 这不是「我被限流了」（那该等），是「那一组挂了」（那该走降级链）。
> 两件事下一步完全相反，而屏幕上长得一样。

⚠️ 同一天内还观察到**故障在扩散**：`push2his` 上午还是 200，下午变成连接被关闭。
⇒ 「现在它还好」不等于「一小时后它还好」，这正是备胎要**提前**探活的理由。

### 2.2 两个探针本身踩的坑（写下来，别重踩）

| 坑 | 后果 |
|---|---|
| 盘后包探针用「今天」的日期 | 它在**非交易日返回 404** —— 周末跑一次就读成「源挂了」。实测第一版写了中秋当天，404 被当成故障查了半天 ⇒ 改用**固定的已知交易日** |
| 只判 HTTP 200 | 限流页、空壳 JSON、登录跳转**都是 200**。财联社就是 200 + `{errno,msg}` ⇒ 判据必须打在**形状**上 |

### 3.2 日线的三级链，以及通达信盘后包的特殊价值

```
sina_eod (PRIMARY) → tdx_daily_package (FALLBACK) → eastmoney_eod (FALLBACK)
```

顺序有讲究，**且这个顺序现在真的生效**（见 §3.5）：

| 位次 | 源 | 理由 |
|---|---|---|
| 1 | 新浪 | 收盘即可取，最快（12 页 / 28 秒） |
| 2 | 通达信盘后包 | **第三个风控面**，且唯一能补历史。代价是「收盘后数小时」才发布，17:30 的定时器可能赶不上 ⇒ 排在新浪之后 |
| 3 | 东财 | 与 `push2` 同组，2026-09-26 起整组故障 |

🔴 **盘后包的独有能力：按指定交易日取。**

| | 新浪 / 东财 | 通达信盘后包 |
|---|---|---|
| 取数方式 | **快照**，只能拿「此刻」 | 按**指定交易日**下载 |
| 补历史 | ❌ | ✅ 实测取到 2023-01-03 |
| 含北交所 | ✅ | ✅（2022-05-06 起包里才有 bj 文件）|
| 代价 | JSON | 二进制（`.cod` + `.md1`）|

**验证**：用 2026-09-24 的真包与新浪同日快照**逐只对拍 5556 只**，
收盘价与开盘价**零处不一致**。

⚠️ 它在**非交易日返回 404**，那是正确行为，不是故障。

#### 🔴 快照型 provider 不许服务历史日

新浪与东财**根本无法**回答「2023-01-03 收盘是多少」。
让它们参与补历史，结果要么被日期校验拦下（好），要么在某个没想到的路径上
把今天的价当成那天的（灾难）。

⇒ 它们在补历史时抛 `SourceError` 而**不是从链里删掉** ——
这样会落进 `provider_attempts`，库里能查到「那天为什么没走主源」。

### 3.5 备用源的顺序：声明即优先级（2026-09-26 改）

`fallback_providers` 原来会被**按 id 排序**，理由是「确定性」。
但元组本身已经确定，排序买不到额外确定性，却**吃掉了声明里的信息** ——
写的人自然按优先级排，而它被静默重排了。

> 那是「看起来能控制某件事、实际不能」的配置。

逼出这次改动的正是日线：盘后包快且能补历史，东财当时正在故障，
而按 id 排会让故障那个排在前面、每次白等三次重试。

⚠️ **VALIDATOR 仍按 id 排** —— 那里顺序**没有含义**（校验源是全部都要问的）。
在没有含义的地方排序让输出稳定；在有含义的地方排序是把含义丢掉。

### 3.6 补历史的 point-in-time 边界

盘后包能取到 2023-01-03 的日线，而那次取回发生在今天。
原来 universe 按 `retrieved_at` 解析 ⇒ 会把 2023 年的行情配上**今天的**在册名单。

> 那是 point-in-time 的静默违反：不会报错，只会让回测里出现一批当时还没上市
> 的票。而幸存者偏差只会让回测**好看**。

⇒ universe 改按**交易日当日 23:59:59** 解析。
于是补历史会 fail-closed（我们没有那天的名单快照）—— **那是诚实的红**，
与 `cn.security_master` 「只宣称从第一次成功同步那天起」是同一条原则。

### 3.3 口径差异（`cn.equity.daily_bars` 主备之间）

| | 东财 `clist` | 新浪 `hs_a` |
|---|---|---|
| 成员 | 板块过滤串 | 行情节点，**当前在交易的** |
| 自报总数 | 有 | **没有** |
| 停牌股 | 返回，OHLC 为 `"-"` | **不返回** |
| 成交量单位 | 股 | 股（**实测**，见下）|

🔴 **停牌股不返回，不是缺陷，但它改变了下游的理由。**
`cn.security.tradability` 用「在 universe 里、当日没有价」区分停牌与数据缺失。
两个源在那里都归到同一种状态，**结论不变、理由不同** ——
别把「没返回」读成「源坏了」。

## 3. 一道用真实事故换来的守卫：成交量单位

同机那套实例的代码里留着一句注释：

> 成交股数用 `amount/close` 推，不用 `volume` —— **volume 单位跨某日变过**。

也就是说这个字段的单位**在历史上真的漂移过一次**。

⇒ 本仓库不写死倍数，改成**每次取数都自检**：
`(amount / close) / volume` 的中位数应当接近 1。
上游哪天改回「手」，这个比值跳到 ~100，当场 fail closed。

```python
# src/easyup_biga/providers/sina_eod.py
_VOLUME_UNIT_WINDOW = (0.5, 2.0)
```

窗口取得宽是故意的：分子用收盘价、分母是全天成交量，本来就有
VWAP 与收盘价的偏离（实测当日 p5/p95 = 0.99 / 1.02）。
**这道守卫抓的是数量级跳变，不是精度。**

样本不足 20 只时**宁可失败**，不假装查过。

## 3.4 同机那套实例**每天真的在调**哪些端点

普查是「能不能取到」，这一节是「哪条路扛得住天天跑」—— 两件事不能互相替代。
按它源码里的出现次数归并（只列 A 股相关）：

| 端点 | 用途 | 我们的对应关系 |
|---|---|---|
| `hq.sinajs.cn/list` | 实时报价（出现最多）| 我们走腾讯；这是**已验证的备胎候选** |
| `vip.stock.finance.sina.com.cn/.../Market_Center.getHQNodeDataSimple` | **全市场日线落库** | ✅ 我们 2026-09-26 起的日线主源就是它 |
| `money.finance.sina.com.cn/.../CN_MarketData.getKLineData` | 个股历史 K 线（回测）| 我们的指数日线走同一族端点 |
| `datacenter-web.eastmoney.com/api/data` | 龙虎榜等 | 我们没用（口径不合，见 §2）|
| `push2.eastmoney.com/api/qt` | 板块资金流、流通市值 | 我们的 `board_snapshot` 主源同域 ⇒ **同一组故障面** |
| `push2ex.eastmoney.com` | 涨停池 | ✅ 与我们 `limit_pool` 主源一致 |
| `qt.gtimg.cn/q` | 腾讯实时 | ✅ 与我们 `index.realtime_quote` 主源一致 |
| `www.cls.cn/v1/roll` | 财联社电报 | 候选备胎（本次探活需签名，未通）|

**三条可直接抄的结论：**

1. **全市场日线用新浪 Simple 端点、`num=500`、串行 + 间隔** —— 它每天在跑
2. 🔴 **不要相信 `volume` 字段的单位** —— 它的代码里留着
   「成交股数用 `amount/close` 推，不用 `volume` —— volume 单位跨某日变过」
3. **交易日判断必须查真日历，不能只判 weekday** —— 它为此记过一次事故：
   节假日被当成交易日，catch-up 把上一交易日的数写进节假日标签下，污染了十几张表

第 3 条我们已经满足（`fact_trading_calendar` + `holiday_fallback`），
且定时器**故意不判交易日**（判断塞进 `OnCalendar` 会产生第二份日历口径）。

⚠️ 它还有一条我们**不需要**抄的：它用 `verify_data_is_fresh()` 靠 `ticktime`
猜「新浪是不是返回了周末缓存」。我们的 `_verify_eod_date` 比它强 ——
要求日历确认是交易日**且**同日收盘后取，那个坑结构上进不来。

## 3.7 主源「报数」、备用源「数数」—— 一种要写出来的性质差别

`cn.market.breadth` 的两个源不只是端点不同：

| | 东财（主源） | 新浪（备用） |
|---|---|---|
| 家数从哪来 | **源报的**（`f104/f105/f106`）| **我们数的** |
| 口径 | 沪 + 深 | 沪 + 深 + **京** |
| 「平盘」的定义 | 源的口径，我们不知道 | `changepercent == 0`，**我们定的** |
| 成本 | 一次请求 | 拉整个市场（~1.7 MB / 3 页 / 8 秒）|

🔴 **不去掉北交所来「对齐」主源** —— 那是硬凑：为了让两个数看起来可比，
而丢掉真实观测到的一部分市场。差异应当**被声明**，不应当被抹平。

⚠️ 实测过没有更便宜的替代：东财的 `ulist.np` 只存在于挂掉的那组 host，
同花顺 `realhead` 502、涨跌幅排行返回 HTML，百度返回空。

### 3.8 🔴 加备胎那一刻差点让系统更脆

`ProviderChainExhausted` 的基类原来是 `RuntimeError`，而
`decision_client.freeze_required` 只接 `(SourceError, ValueError)` 当可降级失败。

于是给 breadth 配上备胎的那一刻，「两个源都挂」从
**「这条数据缺失」变成了「整张卡出不来」**。

> **降级链的终点必须仍然是一次可降级的失败。**

测试当场抓到了它（stub 掉整条链之后炸在 `ProviderChainExhausted` 上）。
下一个给别的 dataset 配备胎的人会走到同一个路口。

### 3.9 「0」的两种相反含义

| 字段 | `0.000` 的含义 |
|---|---|
| 开 / 高 / 低 / 收 | 没有成交 ⇒ **缺失** |
| 涨跌幅 | **平盘** ⇒ 一个真实的值 |

第一版把 `"0.000"` 写进了统一的空值表 ⇒ **平盘家数恒为 0**。
实测：全市场首页 2000 只里 58 只的 `changepercent` 就是 `"0.000"`，
它们有成交量、有真实价格。

> 一个恒为 0 的计数不会报错，只会让人以为那天市场没有平盘。

同理，停牌的判据是**有没有价**，不是「涨跌幅是不是空」——
停牌票的涨跌幅可能是 `0.000`，按涨跌幅判会把它算成平盘，
于是停牌多的日子看起来像市场很平静。

## 3.10 板块备用源：口径少两个字段，但**降级会被看见**

同机另一套长期运行的实例的代码里写着（原样转述其判断）：

> 主数据源：新浪 `newFLJK.php`（175 个概念板块，免费无限制）
> 备用数据源：东财 push2（500 个概念板块，**部分环境被拒**）

也就是说在一个每天跑的生产系统里，这两者的主备关系与本仓库当前的**正好相反**。
2026-09-26 我们撞上的正是「被拒」。

| | 东财（主源） | 新浪（备用） |
|---|---|---|
| 概念板块数 | ~500 | **175** |
| 行业板块数 | ~86 | 84 |
| 涨跌幅排行 / 领涨股 | ✅ | ✅ |
| **主力净流入** | ✅ | ❌ |
| **板块内涨跌家数** | ✅ | ❌ |

🔴 缺主力净流入**不是静默降级** —— 消费方早就为此写过一条专门的 missing：

> 主力净流入 —— N/N 个板块接口未给该字段，**排名不成立**

那条是外部评审 F6 逼出来的（「资金字段可以独立于 pct 失效，而『第一名』
读起来毫无破绽，带着 0.0 亿直接上卡」）。备用源正好落进它已经准备好的那条路。

⚠️ 这三个字段写 `None` 而不是 `0`：
0 会让「没有资金进出」和「没给这个字段」长得一模一样。

### 3.11 🔴 Evidence 的 `source` 必须写实际供数方

`sector-calc` 里曾经写死 `f"em:clist/{kind}"`。板块有了备用源之后，
降级过的那天 Evidence 会指着一个**没供过数的源**。

> 那比缺字段更糟：**缺字段会进 `missing[]`，说谎不会。**

⇒ `FrozenDataset` 带上 `provider_id`，`read_boards` 返回它，
skill 用 `source_prefix_of()` 从注册表拼前缀。

⚠️ 前缀不能自己拼：`sina` / `sina_boards` / `sina_eod` 的前缀都是 `sina`。

### 3.12 字段位序是**对拍**出来的，不是猜的

新浪的响应是 GBK 的 `var … = {…}`，每个值是逗号分隔的字符串。
第 9~11 位**不是**「价、涨跌额、涨幅」那种直觉顺序：

```
… ,sz000829, 2.870 , 9.320 , 0.260 ,天音控股
     龙头代码  涨幅%   现价   涨跌额   龙头名
```

拿两只龙头股与新浪实时行情逐位对拍确认（`sz000829` 昨收 9.06 / 现价 9.32
⇒ 涨幅 2.870%、涨跌额 0.260）。**猜错这个顺序不会报错，只会让领涨股的
涨幅变成价格。**

## 5. 不做的事

### 5.1 不导入另一套系统的历史库

裁定 1 写着「完全独立，自己重新采数据，**不挂载对方的库**」。
除此之外还有两条技术理由，即使裁定改了也仍然成立：

1. **它解不开任何一个当前的阻塞。** 上线验收要的是「连续 5 个交易日
   EOD **跑通**」——判据是这条 pipeline 真跑过，不是库里有那几天的数。
2. 🔴 **导入的行没有 raw。** 本仓库的日线分区必须指回一份 RawArtifact
   （原始响应字节 + `content_sha256` + `retrieved_at`）。导入只有两个选择：
   不给 raw（发布服务 fail-closed，发不出去），或者拿导入的行**自己序列化
   一份当 raw** —— 那正是「自己证明自己」，本仓库刚花一整轮修掉它。

   而且 `knowledge_cutoff` 不可知：证明不了某年某月那天的那份数据在**那一刻**
   长什么样。point-in-time 查询会因此给出一个看起来合理、却无法追溯的答案。

⚠️ **如果将来 Phase 4 的回测确实需要历史日线**，正确的做法是单独建一个
dataset（而不是往决策链的那个里灌）：它自己的 provider id、显式声明
`effective_trade_date`、raw 是**那次导入的原始导出文件本身**（那是诚实的：
它确实是我们收到的字节），并在注册表里写明「非 point-in-time，
不能用于回答『当时看到的是什么』」。
