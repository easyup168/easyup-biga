## 1. 范围

Phase 2 补齐到 **7 个 Agent**（`main` + 6 个 Specialist）：

```
main ──┬── market      ✅ 2.1
       ├── emotion     ✅ Phase 1
       ├── sector      ✅ 2.3
       ├── technical   ✅ 2.3
       ├── news        ⬜ 2.4
       └── risk        ✅ 2.2（Stage 2 制衡层）
```

`discipline` **不在 Phase 2**（裁定 13）。它的输入是人的交易行为史，
而 BigA 不下单、不接账户、不挂邻居的库 —— **现在没有输入源**。
此时建它等于同时踩中 L-1（零消费方）与 L-2（无输入却给得出 PASS）。

开发在独立分支 `phase2` 上（裁定 14）。

### 🔴 Phase 2 真正要证明的不是「有 7 个 Agent」

> **新增一个 Specialist，不需要改动核心架构。**

这条有一个可核对的判据。2.1 加 `market` 时的实际结果：

| 组件 | 改动 |
|---|---|
| `_contract` | **0 行**（后来的改动来自可追溯性，不是 market） |
| Supervisor 的 market 特判 | **无**（roster 表加一行） |
| `DecisionCard` | **0 行** |
| `_store` | 加了一张表 —— **但不是因为 market**，是因为「LLM 搬运 JSON 会丢字段」 |

⇒ 抽象是站得住的。2.3 会再验一次：`sector` / `technical` 应当只需要
「新增 skill + 新增 agent + 新增测试」。

## 3. 各步的关键决策

### 3.1（2.1）事实的归属：同一个事实只能有一个生产方

上游文档把「市场宽度」同时派给了 market 与 emotion。本项目**只让 market 算**（裁定 15）。

它的端点是**不带日期的实时快照**：两个 Agent 并行各调一次，
同一张 Card 上就会出现同一个字段两个值，而两个都带着推断出来的 `as_of`。
不会报错，只会某天悄悄给出两个数。

**例外是溯源字段**（`trade_date`）：它不是「同一个事实的两份实现」，
而是各自的元数据 —— 两者不一致本身就是信息。规则反过来：**要求每个 skill 都有**。

由 `tests/test_field_single_producer.py` 全仓扫描钉死。

### 3.2（2.1）数据源按「谁能自证时间」分工

| 源 | 提供 | 它自己声明的时间 |
|---|---|---|
| 新浪日线 | 交易日 / 点位 / 涨跌幅 / 量能基线 | 每行自带 `day` ← **权威** |
| 腾讯行情 | 成交额 | 14 位时间戳 |
| 东财 ulist | 涨跌家数 | **没有**（只能推断，必须发 warning） |

最省事的方案（给宽度那次请求多加几个字段）被实测推翻：
唯一稳定可达的主机返回 `最新=0.0`、`涨跌幅=-29971017728.0`，
而 `rc=0`、字段齐全、类型正确 —— **量级校验是唯一能拦住它的东西**。

⚠️ 跨源做比值前先确认单位：新浪按**股**、腾讯按**手**，差 100 倍。
反过来这个恒等式成了一条免费的双源校验。

### 3.3（2.1）结构化数据不经过 LLM

契约原本要求 Specialist「把 skill 的 JSON 原样带上」、Supervisor 再抄一遍。
实测两层复述之后 15 条证据的 `retrieved_at` **一条不剩**，
落库的值变成了「Supervisor 敲命令的时刻」，与真实采集差 106 秒。

⇒ schema v3 `agent_verdicts`：skill 直接落原件并返回 id，Agent 只传 id。
修订（追加缺失项、提交 stance）走 `amend_verdict.py`，**写新行、指回原件**。

这条是 `architecture.md` §9 **L-10** 的由来，也是 2.2 能成立的前提 ——
risk 读冻结证据的入口，就是这张表。

### 3.4（2.2）否决权放在 `stance`，不放 `verdict`

一个字段装不下两件事：risk 数据完整且要否决时，`verdict` 填 `BLOCK`
就再也说不出「它的数据是全的」，而「否决」与「凭什么否决」都需要知道。

- `VerdictLevel` = `PASS / WARNING / UNKNOWN`，只描述数据完整度
- `VETO_STANCE = "否决"`，**只许一处定义** —— 改了词表忘了改判据，
  否决权会静默失效
- 有人否决 ⇒ Card 状态必须是 `AVOID` 或 `BLOCK`。
  只拦 `BUY` 不够：否决被显示成 `WAIT` 同样是软化制衡层

### 3.5（2.2）risk 在结构上不许采数据

制衡的意义在于审**别人据以下结论的那份证据**。自己重采一遍，
看到的可能是另一个市场，那时它审的是自己的幻觉；而且回放时两边对不上。

⇒ `risk_check.py` 不 import `_sources`、无网络依赖，由 AST 测试钉死。
输入只有 Stage 1 的 `verdict_id`。

**覆盖不足是「无法判定」的理由，不是「放行」的理由。**
否决的意思是「我看到了风险」，不是「我没看清」。

### 3.7（2.3）`technical` 做**指数**技术面，不做个股

architecture §3.1 给 technical 的职责是「个股技术结构」。但 Phase 2 **不选股**，
没有个股输入 —— 硬做就会变成第二个 `discipline`（没有输入源却硬建，只能编）。

⇒ Phase 2 的 technical 分析**指数**（上证 / 深证综指）的技术面。
它有真实输入（日线序列），产出可核对。个股技术面等有了选股输入再说（Phase 3+）。

### 3.8（2.3）「范围外」与「数据缺失」不是一回事

sector 的「板块持续性」（连续几天领涨）需要历史序列，而 Phase 2 不做历史回补。

两种处理方式，差别很大：

| 做法 | 后果 |
|---|---|
| 塞一条 `missing`「持续性算不出来」 | 它**每次都在**，很快变成没人看的常驻噪音 |
| ✅ 写进契约：**agent 不许谈持续性**，并说明理由 | 缺失项只留给真正的数据缺失 |

> **`missing[]` 是给「本该有却这次没有」的，不是给「我们还没做」的。**
> 前者每次不同，后者每次相同 —— 混在一起，前者就被后者淹没了。

范围外的事写在契约里（agent 不许说），数据缺失才进 `missing`。

### 3.9（2.3）同一端点被两个 skill 各采一次 —— 正视它

`technical` 要 120 根日线算 MA60/MACD，`market` 要 25 根算量能基线。
两者都打 `sina:kline/sh000001` —— Stage 1 并行时就是**两次独立请求**，
盘中可能拿到两个不同的快照。

三个选项：

| 选项 | 评价 |
|---|---|
| 让 technical 读 market 的冻结证据 | ❌ market 的证据里只有聚合值，没有 120 根原始日线 |
| 加「每次决策的采集缓存」 | 是对的，但属于 Phase 3「数据层加厚」，现在做是提前优化 |
| ✅ 接受重复采集，但**让它可检测** | 见下 |

#### 🔴 原设计的 `raw_hash` 方案造不出来 —— 记下它错在哪

本节最初写的是：*「同一次决策内，同一个 `source` 的 `raw_hash` 应当一致，
不一致就报出来」*。2.3 真要落地时才发现**这个检查一写出来就永远是红的**：

| agent | 打的端点 | 要几根 |
|---|---|---|
| `market` | `sina:kline/sh000001` | 25 |
| `technical` | `sina:kline/sh000001` | 120 |
| `sector` | `sina:kline/…` | 2 |

同一个 `source` 标识，**参数不同 ⇒ 报文必然不同 ⇒ 哈希必然不同**。
分歧不是异常，是设计本身。按原方案实现，得到的是一个天天报红的检查 ——
正是本项目反复清理的那种失效守卫（L-7）。

错在哪：`source` 是**端点的名字**，不是**那次请求的身份**。
把「同名」当成「同一份数据」，这一步在写设计时看着显然，在有数据时才站不住。

> 通用原则：设计阶段能想出的检查，和有真实数据后能成立的检查，是两回事。
> 发现造不出来时，**要留下它错在哪** —— 否则下一个人会照着同一段推理再设计一遍。

#### 能造出来的版本：比**导出值**，不比报文

报文可以合法地不同，但两者算出的**上证收盘价必须是同一个数**。
于是把检查下移一层：

```python
CROSS_CHECK_PAIRS = (
    ("market", "sh_close", "technical", "close", "上证收盘价"),
)
```

由 `risk` 逐对比较，不等就进 `missing`（`risk.upstream.cross_check_conflict`）。

⚠️ 这同时补上了裁定 15 的一个**漏网缺口**。守卫
`tests/test_field_single_producer.py` 比的是**字段名**，而这两个字段叫
`sh_close` 和 `close` —— 同一个事实，不同的名字，守卫一眼看不见。
2.3 合入时它就在那儿，没人发现。

所以规则要精确成：**重复是允许的，前提是有人核对。**
`CROSS_CHECK_PAIRS` 里声明过的字段豁免单一生产方检查，但守卫反过来要求
它必须出现在 `risk` 的核对清单里 —— 声明了却没人查，就退回裁定 15 要防的
那种情况：两个数悄悄不一样，没人知道。

`Evidence.raw_hash` 因此**暂时没有消费方**。不删（它在回放比对里另有用途），
但本节不再声称它是这个问题的答案。

### 3.6 Stage 拓扑写在契约层

`STAGE1_AGENTS` / `STAGE2_AGENTS` 定义在 `_contract`，
`risk-check`（算覆盖率）与 `latency_report`（判并行）共用。

各写一份名单必然漂，而漂开的表现是**并行判据在正确行为上报红**
（risk 本该在 Stage 1 之后）—— 那种检查很快会被训练成噪音。

由此得到一条正确性检查：**Stage 2 若与 Stage 1 重叠，说明它读的是没冻结的证据。**

## 4. 出口条件

全部满足才能合回 `main`。

| # | 条件 | 状态 |
|---|---|---|
| 1 | Stage 1 **实测并行**（判据是区间相交，不是总耗时变短） | ✅ 4 个已证；5 个时需复测 |
| 2 | Stage 2 拿到的是**冻结证据**，不是自己重采 | ✅ 结构保证 + AST 测试 |
| 3 | 至少 1 次真实 `否决` 端到端落库，且 `replay --check` 复现 | ⬜ 本地三条路径已验，缺真 agent 的一次 |
| 4 | `missing[]` 在**真实**缺数据时非空 ≥5 次 | ⬜ 需按日历累积，见下 |
| 5 | 延迟预算按实测重推并写回 §10.1，**不照抄 105s** | 🔶 盘中已测（214.9s，超 2.4×），但根因未清完 |
| 6 | 成本分解：逐个 agent 的 token / $ | ⬜ |
| 7 | 每一步都有教程章节 | ✅ 11 / 12 / 13 / 14 |
| 8 | 隔离自检重跑（agent 变多 ⇒ 并发变高） | ⬜ |

### 当前实测（6 个 Agent，`BIGA-20260921-005`，周日休市）

```
Stage 0  main       9.8s
Stage 1  market    28.3s ┐
         sector    21.6s │ 四者区间相交 ⇒ 真并行
         technical 24.1s │ （Stage 1 墙钟 31.2s，串行需 98.5s）
         emotion   24.5s ┘
Stage 2  risk      16.4s   （在 Stage 1 之后）
Stage 3  main      13.6s
         端到端     71.0s   预算 90s ✅
```

🔴 **加 3 个 agent，端到端反而从 87.9s 降到 71.0s。** 不是因为变快了 ——
是 004 那次的 87.9s 里混了别的东西。并行的边际成本是
`max(新 agent)` 而不是 `sum`，所以 Stage 1 从 2 个到 4 个只多了 ~6s。

⚠️ 这个数字**是休市日测的**，`technical` 是唯一 PASS（它用的是已收盘日线）。
盘中四个 agent 都要打实时接口，延迟分布会不同 —— 出口条件 5 要的是盘中实测。

### 3.10（2.4 前）盘中实测推翻了休市日的所有结论

`BIGA-20260921-009`（周一 09:52，交易时段内）：

```
Stage 0  main       34.7s
Stage 1  sector    113.6s ┐
         market     38.9s │ 四者区间相交，最小重叠 36.3s ⇒ 真并行
         emotion    37.9s │ 墙钟 113.6s，个体之和 226.7s
         technical  36.3s ┘
Stage 2  risk       23.7s
Stage 3  main       29.0s
         端到端     214.9s   预算 90s  ❌ 超 2.4×    成本 $1.04
```

三条结论：

**1. 休市日那个 71.0s 不代表任何东西** —— 盘中差了 3 倍。
   差距几乎全在 `sector`：休市日 21.6s，盘中 113.6s。
   Stage 1 是 `max()`，一个慢 agent 决定整个阶段。

**2. 慢的是 skill，不是 agent。** 展开调用序列看到 sector 在 `process poll`
   上等了两次 30 秒 —— 因为 skill 跑了 68 秒，被运行时自动转了后台。
   量下去：`fetch_boards` 串行翻页，industry+concept 一共 11 次请求、
   **58.8 秒纯网络等待**。

   > 又一次印证：Agent 的「慢」多数时候是它在**等**或在**找**，不是在想。

**3. 🔴 并发解决不了全部问题，过头了反而是成本。**

   | 并发 | 连跑三次 | 判断 |
   |---|---|---|
   | 1（原实现） | 67.9s | 串行等待占 58.8s |
   | 4 | 7.2s → 25.2s → **60.1s** | 🔴 单调上升 ⇒ 渐进限流 |
   | **2** | 23.3s → 9.1s → 23.5s | ✅ 不再爬升，均值 ~19s |

   单调上升不是网络抖动 —— 抖动会双向。打得越猛越慢，说明对方在限速。
   这是别人的公开接口：目标是折叠掉串行等待，不是把它打满。

   > 通用原则：**调并发度必须连跑几次看趋势**，单次计时分不出
   > 「这次快」和「还没被限到」。

   ⚠️ 顺便测准了一个旧坑的边界：`pz` 被硬顶在 **100**
   （`pz=200/300/500` 都只返回 100 行，`total` 照报 504）。页数减不了。

### 3.11（2.4 前）盘中出不了有把握的卡 —— 时间基准是分裂的

同一次盘中运行（09:52，交易时段内）里，四个 Specialist 报出了**两个交易日**：

| agent | `trade_date` | 为什么 |
|---|---|---|
| `emotion` | `20260921` | 用实时涨跌停池 ⇒ 说的是**此刻** |
| `market` / `technical` / `sector` | `20260918` | 用日线 ⇒ **今天的日线还没收**，只能报上一个已完成交易日 |

`risk` 正确地拒绝把它们当成同一天的事实一起审
（`risk.upstream.trade_date_inconsistent`），Card 落在 `WAIT`。

**这是对的行为，但它意味着一件事要写明白：**

> 按目前的构造，BigA **盘中出不了有把握的卡** —— 不是因为哪里坏了，
> 而是因为数值基准本身是分裂的：一半 Agent 说「此刻」，一半说「昨天收盘」。

两种解法，都不在 2.4 的范围内：

| 解法 | 代价 |
|---|---|
| 日线类 Agent 盘中改用**当日分时**合成一根未完成的 K | 指标语义变了（MA/MACD 基于未完成 K 会跳动），要重新定义 |
| 明确 Card 只在**盘后**出 | 放弃盘中决策辅助 —— 但短线系统的价值恰恰在盘中 |

⇒ 记入 Phase 3 的待决项。**现在不选，因为两条都要改指标口径，
而口径一改，此前所有实测数字都不可比。**

### 🔴 「≥5 次真实 missing」攒不快

它要的是**真实**缺数据，不是注入故障。而 Phase 2 不建 cron
（第一条在 Phase 3）⇒ 需要手工日跑 + 一份台账：
日期 / 哪个源缺 / 缺失代码 / Card 状态。

缺失项现在带机器可读代码（`MissingItem.code`），这条才统计得出来。

## 5. 明确不做

`discipline`（裁定 13）/ 任何 cron / 飞书 / 任何下单路径 /
PostgreSQL / Redis / 回测 / 历史数据回补 / Web UI。

以及两条来自外部评审、**经实测否决**的建议：

- **「Offline First, Live Last」** —— 对本项目恰好是反的。
  market 的数据源选型完全来自先探测真接口。先写 fixture 等于
  把一个坏掉的 API 形状固化进测试。正确表述是「**测试离线，设计先探活**」
- **`volume_state = EXPANDING/NORMAL/SHRINKING` 由 skill 产出** ——
  违反铁律 4。skill 给 `volume_ratio` 这个数，归类由 Agent 做
