## 1. 范围

Phase 2 补齐到 **7 个 Agent**（`main` + 6 个 Specialist）：

```
main ──┬── market      ✅ 2.1
       ├── emotion     ✅ Phase 1
       ├── sector      ✅ 2.3
       ├── technical   ✅ 2.3
       ├── news        ✅ 2.4
       └── risk        ✅ 2.2（Stage 2 制衡层）
```

`discipline` **不在 Phase 2**（裁定 13）。它的输入是人的交易行为史，
而 BigA 不下单、不接账户、不挂邻居的库 —— **现在没有输入源**。
此时建它等于同时踩中 L-1（零消费方）与 L-2（无输入却给得出 PASS）。

开发在独立分支 `phase2` 上（裁定 14）。

## 3. 各步的关键决策

### 3.1（2.1）事实的归属：同一个事实只能有一个生产方

上游文档把「市场宽度」同时派给了 market 与 emotion。本项目**只让 market 算**（裁定 15）。

它的端点是**不带日期的实时快照**：两个 Agent 并行各调一次，
同一张 Card 上就会出现同一个字段两个值，而两个都带着推断出来的 `as_of`。
不会报错，只会某天悄悄给出两个数。

**例外是溯源字段**（`trade_date`）：它不是「同一个事实的两份实现」，
而是各自的元数据 —— 两者不一致本身就是信息。规则反过来：**要求每个 skill 都有**。

由 `tests/test_field_single_producer.py` 全仓扫描钉死。

### 3.2（2.1）数据源按「谁能自证时间」分工

| 源 | 提供 | 它自己声明的时间 |
|---|---|---|
| 新浪日线 | 交易日 / 点位 / 涨跌幅 / 量能基线 | 每行自带 `day` ← **权威** |
| 腾讯行情 | 成交额 | 14 位时间戳 |
| 东财 ulist | 涨跌家数 | **没有**（只能推断，必须发 warning） |

最省事的方案（给宽度那次请求多加几个字段）被实测推翻：
唯一稳定可达的主机返回 `最新=0.0`、`涨跌幅=-29971017728.0`，
而 `rc=0`、字段齐全、类型正确 —— **量级校验是唯一能拦住它的东西**。

⚠️ 跨源做比值前先确认单位：新浪按**股**、腾讯按**手**，差 100 倍。
反过来这个恒等式成了一条免费的双源校验。

### 3.3（2.1）结构化数据不经过 LLM

契约原本要求 Specialist「把 skill 的 JSON 原样带上」、Supervisor 再抄一遍。
实测两层复述之后 15 条证据的 `retrieved_at` **一条不剩**，
落库的值变成了「Supervisor 敲命令的时刻」，与真实采集差 106 秒。

⇒ schema v3 `agent_verdicts`：skill 直接落原件并返回 id，Agent 只传 id。
修订（追加缺失项、提交 stance）走 `amend_verdict.py`，**写新行、指回原件**。

这条是 `architecture.md` §9 **L-10** 的由来，也是 2.2 能成立的前提 ——
risk 读冻结证据的入口，就是这张表。

### 3.4（2.2）否决权放在 `stance`，不放 `verdict`

一个字段装不下两件事：risk 数据完整且要否决时，`verdict` 填 `BLOCK`
就再也说不出「它的数据是全的」，而「否决」与「凭什么否决」都需要知道。

- `VerdictLevel` = `PASS / WARNING / UNKNOWN`，只描述数据完整度
- `VETO_STANCE = "否决"`，**只许一处定义** —— 改了词表忘了改判据，
  否决权会静默失效
- 有人否决 ⇒ Card 状态必须是 `AVOID` 或 `BLOCK`。
  只拦 `BUY` 不够：否决被显示成 `WAIT` 同样是软化制衡层

### 3.5（2.2）risk 在结构上不许采数据

制衡的意义在于审**别人据以下结论的那份证据**。自己重采一遍，
看到的可能是另一个市场，那时它审的是自己的幻觉；而且回放时两边对不上。

⇒ `risk_check.py` 不 import `_sources`、无网络依赖，由 AST 测试钉死。
输入只有 Stage 1 的 `verdict_id`。

**覆盖不足是「无法判定」的理由，不是「放行」的理由。**
否决的意思是「我看到了风险」，不是「我没看清」。

### 3.7（2.3）`technical` 做**指数**技术面，不做个股

architecture §3.1 给 technical 的职责是「个股技术结构」。但 Phase 2 **不选股**，
没有个股输入 —— 硬做就会变成第二个 `discipline`（没有输入源却硬建，只能编）。

⇒ Phase 2 的 technical 分析**指数**（上证 / 深证综指）的技术面。
它有真实输入（日线序列），产出可核对。个股技术面等有了选股输入再说（Phase 3+）。

### 3.8（2.3）「范围外」与「数据缺失」不是一回事

sector 的「板块持续性」（连续几天领涨）需要历史序列，而 Phase 2 不做历史回补。

两种处理方式，差别很大：

| 做法 | 后果 |
|---|---|
| 塞一条 `missing`「持续性算不出来」 | 它**每次都在**，很快变成没人看的常驻噪音 |
| ✅ 写进契约：**agent 不许谈持续性**，并说明理由 | 缺失项只留给真正的数据缺失 |

> **`missing[]` 是给「本该有却这次没有」的，不是给「我们还没做」的。**
> 前者每次不同，后者每次相同 —— 混在一起，前者就被后者淹没了。

范围外的事写在契约里（agent 不许说），数据缺失才进 `missing`。

### 3.9（2.3）同一端点被两个 skill 各采一次 —— 正视它

`technical` 要 120 根日线算 MA60/MACD，`market` 要 25 根算量能基线。
两者都打 `sina:kline/sh000001` —— Stage 1 并行时就是**两次独立请求**，
盘中可能拿到两个不同的快照。

三个选项：

| 选项 | 评价 |
|---|---|
| 让 technical 读 market 的冻结证据 | ❌ market 的证据里只有聚合值，没有 120 根原始日线 |
| 加「每次决策的采集缓存」 | 是对的，但属于 Phase 3「数据层加厚」，现在做是提前优化 |
| ✅ 接受重复采集，但**让它可检测** | 见下 |

#### 🔴 原设计的 `raw_hash` 方案造不出来 —— 记下它错在哪

本节最初写的是：*「同一次决策内，同一个 `source` 的 `raw_hash` 应当一致，
不一致就报出来」*。2.3 真要落地时才发现**这个检查一写出来就永远是红的**：

| agent | 打的端点 | 要几根 |
|---|---|---|
| `market` | `sina:kline/sh000001` | 25 |
| `technical` | `sina:kline/sh000001` | 120 |
| `sector` | `sina:kline/…` | 2 |

同一个 `source` 标识，**参数不同 ⇒ 报文必然不同 ⇒ 哈希必然不同**。
分歧不是异常，是设计本身。按原方案实现，得到的是一个天天报红的检查 ——
正是本项目反复清理的那种失效守卫（L-7）。

错在哪：`source` 是**端点的名字**，不是**那次请求的身份**。
把「同名」当成「同一份数据」，这一步在写设计时看着显然，在有数据时才站不住。

> 通用原则：设计阶段能想出的检查，和有真实数据后能成立的检查，是两回事。
> 发现造不出来时，**要留下它错在哪** —— 否则下一个人会照着同一段推理再设计一遍。

#### 能造出来的版本：比**导出值**，不比报文

报文可以合法地不同，但两者算出的**上证收盘价必须是同一个数**。
于是把检查下移一层：

```python
CROSS_CHECK_PAIRS = (
    ("market", "sh_close", "technical", "close", "上证收盘价"),
)
```

由 `risk` 逐对比较，不等就进 `missing`（`risk.upstream.cross_check_conflict`）。

⚠️ 这同时补上了裁定 15 的一个**漏网缺口**。守卫
`tests/test_field_single_producer.py` 比的是**字段名**，而这两个字段叫
`sh_close` 和 `close` —— 同一个事实，不同的名字，守卫一眼看不见。
2.3 合入时它就在那儿，没人发现。

所以规则要精确成：**重复是允许的，前提是有人核对。**
`CROSS_CHECK_PAIRS` 里声明过的字段豁免单一生产方检查，但守卫反过来要求
它必须出现在 `risk` 的核对清单里 —— 声明了却没人查，就退回裁定 15 要防的
那种情况：两个数悄悄不一样，没人知道。

`Evidence.raw_hash` 因此**暂时没有消费方**。不删（它在回放比对里另有用途），
但本节不再声称它是这个问题的答案。

### 3.6 Stage 拓扑写在契约层

`STAGE1_AGENTS` / `STAGE2_AGENTS` 定义在 `_contract`，
`risk-check`（算覆盖率）与 `latency_report`（判并行）共用。

各写一份名单必然漂，而漂开的表现是**并行判据在正确行为上报红**
（risk 本该在 Stage 1 之后）—— 那种检查很快会被训练成噪音。

由此得到一条正确性检查：**Stage 2 若与 Stage 1 重叠，说明它读的是没冻结的证据。**

### 休市日实测（5 个 Agent，`BIGA-20260921-005`，周日）

> ⚠️ 已被 §3.10（盘中）与 §3.13（六 Agent）取代。留着是因为它是
> 「休市日数字不代表盘中」这个结论的原始依据。

```
Stage 0  main       9.8s
Stage 1  market    28.3s ┐
         sector    21.6s │ 四者区间相交 ⇒ 真并行
         technical 24.1s │ （Stage 1 墙钟 31.2s，串行需 98.5s）
         emotion   24.5s ┘
Stage 2  risk      16.4s   （在 Stage 1 之后）
Stage 3  main      13.6s
         端到端     71.0s   预算 90s ✅
```

🔴 **加 3 个 agent，端到端反而从 87.9s 降到 71.0s。** 不是因为变快了 ——
是 004 那次的 87.9s 里混了别的东西。并行的边际成本是
`max(新 agent)` 而不是 `sum`，所以 Stage 1 从 2 个到 4 个只多了 ~6s。

⚠️ 这个数字**是休市日测的**，`technical` 是唯一 PASS（它用的是已收盘日线）。
盘中四个 agent 都要打实时接口，延迟分布会不同 —— 出口条件 5 要的是盘中实测。

```
Stage 2  risk       23.7s
Stage 3  main       29.0s
         端到端     214.9s   预算 90s  ❌ 超 2.4×    成本 $1.04
```

三条结论：

**1. 休市日那个 71.0s 不代表任何东西** —— 盘中差了 3 倍。
   差距几乎全在 `sector`：休市日 21.6s，盘中 113.6s。
   Stage 1 是 `max()`，一个慢 agent 决定整个阶段。

**2. 慢的是 skill，不是 agent。** 展开调用序列看到 sector 在 `process poll`
   上等了两次 30 秒 —— 因为 skill 跑了 68 秒，被运行时自动转了后台。
   量下去：`fetch_boards` 串行翻页，industry+concept 一共 11 次请求、
   **58.8 秒纯网络等待**。

   > 又一次印证：Agent 的「慢」多数时候是它在**等**或在**找**，不是在想。

**3. 🔴 并发解决不了全部问题，过头了反而是成本。**

   | 并发 | 连跑三次 | 判断 |
   |---|---|---|
   | 1（原实现） | 67.9s | 串行等待占 58.8s |
   | 4 | 7.2s → 25.2s → **60.1s** | 🔴 单调上升 ⇒ 渐进限流 |
   | **2** | 23.3s → 9.1s → 23.5s | ✅ 不再爬升，均值 ~19s |

   单调上升不是网络抖动 —— 抖动会双向。打得越猛越慢，说明对方在限速。
   这是别人的公开接口：目标是折叠掉串行等待，不是把它打满。

   > 通用原则：**调并发度必须连跑几次看趋势**，单次计时分不出
   > 「这次快」和「还没被限到」。

   ⚠️ 顺便测准了一个旧坑的边界：`pz` 被硬顶在 **100**
   （`pz=200/300/500` 都只返回 100 行，`total` 照报 504）。页数减不了。

### 3.11（2.4 前）盘中出不了有把握的卡 —— 时间基准是分裂的

同一次盘中运行（09:52，交易时段内）里，四个 Specialist 报出了**两个交易日**：

| agent | `trade_date` | 为什么 |
|---|---|---|
| `emotion` | `20260921` | 用实时涨跌停池 ⇒ 说的是**此刻** |
| `market` / `technical` / `sector` | `20260918` | 用日线 ⇒ **今天的日线还没收**，只能报上一个已完成交易日 |

`risk` 正确地拒绝把它们当成同一天的事实一起审
（`risk.upstream.trade_date_inconsistent`），Card 落在 `WAIT`。

**这是对的行为，但它意味着一件事要写明白：**

> 按目前的构造，BigA **盘中出不了有把握的卡** —— 不是因为哪里坏了，
> 而是因为数值基准本身是分裂的：一半 Agent 说「此刻」，一半说「昨天收盘」。

两种解法，都不在 2.4 的范围内：

| 解法 | 代价 |
|---|---|
| 日线类 Agent 盘中改用**当日分时**合成一根未完成的 K | 指标语义变了（MA/MACD 基于未完成 K 会跳动），要重新定义 |
| 明确 Card 只在**盘后**出 | 放弃盘中决策辅助 —— 但短线系统的价值恰恰在盘中 |

⇒ 记入 Phase 3 的待决项。**现在不选，因为两条都要改指标口径，
而口径一改，此前所有实测数字都不可比。**

#### ⏩ 2026-09-21 15:21 补：「收盘后就对齐」是错的

原本以为这个分裂只在盘中出现 —— 收盘后日线一收就自动对齐。
**实测证伪**：15:21 跑的 `BIGA-20260921-019` 交易日仍然分裂，
15:22 直接查源，新浪日线最后一根还是上一交易日。

**当天日线不在 15:00 发布，有一段未知长度的延迟。**

⇒ 这个架构问题的**暴露窗口比原先认为的大得多** ——
不是「盘中 4 小时」，而是「从开盘到当天日线发布为止」。

实测（2026-09-21，5 分钟一探）：日线发布在 **15:32:47–15:37:50** 之间，
即收盘后约 33~38 分钟 ⇒ 暴露窗口约 **6 小时**（09:30 起算）。
⚠️ n=1，一个源，**不构成规律**。

> 通用原则：**「应该会……」和「实测是……」之间隔着一次运行。**
> 这条推断特别危险，因为它听起来太合理 —— 谁会怀疑「收盘后日线就有了」。

### 3.12（2.4）news —— 第一个「skill 算不出结论」的 Specialist

前五个 Agent 的形状一样：skill 把数字算完，agent 复述并从词表挑一个 stance。
news 不一样 —— **「这条消息是利好还是利空」没有算式**。

于是两条铁律在这里第一次指向同一个方向：

* 铁律 3「Agent 不做算术」 ⇒ 条数、时间、覆盖度由 skill 算
* 铁律 4「skill 不做判断性归类」 ⇒ 消息的**含义**留给 agent

⇒ 本 skill 的产出是 **事实 + 原文**。

#### 回放的定义要改一次

前五个的回放是确定的：同样的输入，Python 必然给出同样的数。
news 的判断由模型做 ⇒ 同样的输入可能给出不同的 stance。

这不是缺陷，但必须让它**可测量**：原文（含 id）随证据冻结进
`agent_verdicts`，回放时喂同一批 id 与同一段文本。

> 于是「输入相同而结论不同」从一个无法排查的现象，
> 变成一个**能被统计的量**。没有这一步，结论不同时分不清
> 「模型飘了」和「新闻变了」。

#### 数据源：四选一，两个当场出局

| 源 | 结果 |
|---|---|
| **新浪 7x24 直播** | ✅ `create_time` 已是北京时间、id 单调、9 页 ~900 条覆盖 29 小时 |
| 东财个股新闻搜索 | ✅ 可用，但形状是关键词检索 |
| 财联社电报 | ❌ 404，接口已变 |
| 东财 7x24 快讯 | ❌ 每补一个参数就再要一个，形状不稳 |

🔴 **`is_focus` / `top_value` / `tab` 全是常量 0。** 名字都像「重要性标记」，
实测 100 条里没有一条非零。照它设计过滤器会得到一个永远选出空集的过滤器 ——
而空集在下游表现为「今天没有重要新闻」，**不报错**。

🔴 **这个源的「0 条」只可能是取数失败**（凌晨 1 点仍有 21 条/小时）。
与行情源恰好相反 —— 那边的 0 常常是「这一天还没开始」。
⇒ news 不需要盘前守卫，需要的是「静默即故障」。

#### 两个额度都是按实测分布定的

**静默阈值**（取 500 条算相邻间隔）：

| 时段 | 中位 | p95 | 最大 |
|---|---|---|---|
| 盘中 | 30s | 116s | **235s** |
| 夜间 | 81s | 542s | **1830s** |

⇒ `STALE_SEC = 600`，**且只在连续竞价时段启用**。
盘中留 2.5 倍余量；非盘中不设线（夜间就能到 30 分钟，周末只会更长，
在那里设线得到的是又一个「周末必红」的灯）。

**窗口与条数上限** —— 🔴 这里犯了一次错，值得记下来：

第一版写 180 分钟 / 40 条。实跑：窗口内 250 条，只展示 40 条，
`items_truncated=210`，**而 verdict 是 PASS**。
agent 只看到 16% 却说「数据完整」——正是 R-3 要防的静默 fail-open。

按实测重定：

| 窗口 | 条数 | ≈token |
|---|---|---|
| 30 分钟 | 43 | 3.4k |
| **60 分钟** | **93** | **5.9k** |
| 180 分钟 | 245 | 22k |

⇒ 窗口 60 分钟 / 上限 120 条：盘中典型 93 条 < 120，**正常不截断**。
于是截断真发生时是一个有信息量的信号，而不是常驻噪音。
并且截断从 warning 升级为 **missing**。

> 代价是只能就最近一小时发言。这是**诚实的小范围**，
> 好过「三小时」这个读了 16% 就敢下的大结论。

#### 机器行情播报：打标，不过滤

盘中 100 条里 21 条是「上证指数涨0.44%，现报3929.027点」这类。
那是 market / sector 的事实（裁定 15）。

**不过滤** —— 过滤是判断性归类（铁律 4），且误伤一条真消息下游看不出来。
⇒ 打 `is_quote` 标记，由 agent 契约明令「不许从快讯提取任何行情数字」。

⚠️ 这个标记有已知局限：带【标题】的豁免会漏标一部分真播报
（`【国债期货开盘】30年期主力合约涨0.16%…`）。
**不调正则去追** —— 那是拿一天样本过拟合。
关键在定位：**标记是提示，契约才是防线。** `quote_count` 是下界不是精确计数。

#### 单一生产方守卫抓到了一条「同名不同事实」

`news.session_live` 与 `risk.session_live` 撞名。但这次不是
「同一事实两个名字」（`sh_close` / `close`），而是**镜像问题**：

```
周六 10:00
  session_in_progress(当天数据) = True    ← 这批数据所属交易日还没过完
  market_is_open()             = False   ← 此刻市场在不在交易
```

同名、不同事实、值还相反。⇒ news 的改名为 `market_open`。

> 两种都要防：同一事实两个名字**让守卫看不见**，
> 同名两个事实**让人以为是一个数**。

### 3.13（2.4 后）五个并行已证，瓶颈回到 Stage 3

`BIGA-20260921-013`（周一 10:40 盘中，六 Agent）：

```
Stage 1  news      63.4s ┐
         sector    51.6s │ 区间两两相交，最小重叠 27.9s ⇒ 真并行
         market    51.4s │ 墙钟 64.2s，个体之和 227.3s，**省 72%**
         emotion   32.2s │
         technical 28.7s ┘
Stage 2  risk      21.0s
main     3 轮     120.7s   占 64%   $0.36
```

两条结论：

**1. sector 的翻页优化生效了** —— 113.6s → 51.6s。

**2. 🔴 瓶颈回到了 Supervisor。** main 三轮共 120.7s，占总时长 64%，
最慢单轮 69.4s / 输出 4627 tok。Stage 1 加了一个 agent 只多 12.8s
（`max()` 的性质），而 main 反而涨了 —— 要合成的东西变多了。

这正是 11 章那句话的第三次兑现：**并行解决扇出，解决不了汇聚。**
⇒ 下一步的优化对象是 Stage 3，不是再去压某个 specialist。

⚠️ `maxConcurrent: 6` 现在正好被 Stage 1 的 5 个 + 余量占满。
Phase 3 若要加 agent，这个值必须先调 —— 否则表现是**静默排队**，
而 `--parallel-check` 会以「某两个区间不相交」的形式报出来。

### 3.14（Stage 3 优化）契约推荐的快路一直是坏的

按流程展开 main 的调用序列（不是先改提示词），三轮的构成：

| 轮 | 耗时 | 花在哪 |
|---|---|---|
| 1 | 41.0s | 写 5 条 spawn 14.5s + **`agents_wait`→`subagents`→`sessions_yield` 21.8s** |
| 2 | 16.3s | 写 risk 的 spawn 10.6s + yield 5.7s |
| 3 | 36.8s | **零工具调用 21.9s**（组合 synthesize 命令）+ 收尾写回答 14.9s |

#### 🔴 `agents_wait` 一直返回 `not_found`，瞬时

```
10:45:37  agents_wait   → 五个 id 全部 not_found，8.2s
10:45:43  subagents     → agent 自己去查状态，6.2s
10:45:50  sessions_yield→ 退回异步路径，7.4s
```

**22 秒全是协议开销，而且没有任何东西报错。**

根因在运行时源码里：`agents_wait` 的判据是 `if (!entry?.collect)` ——
它只认 **swarm collector** 子会话。而契约教 main 用 `agents_wait`，
**却没教它 spawn 时带 `collect: true`**。

⇒ 推荐的快路从来没生效过，每次都白花 22 秒走回慢路。

#### 更深一层：契约给了两条路，于是 agent 两条都走

原文是「优先用同步等待 `agents_wait`」+「spawn 之后用 `sessions_yield`
**是对的**」。给「优先 A，B 也行」，得到的是 **A 然后 B**，
而且 agent 还自己加了一次 `subagents` 去弄清 A 为什么没用。

> 通用原则：**写契约时，一个动作只给一条路。**
> 备选要明确标成「兜底」，并写清什么条件下才走它。

⚠️ `collect: true` 与 `agents_wait` 是**一对**：collect 模式没有完成通知，
只用 collect 而后 yield，这次对话会**静默地永远停住** —— 既不出卡也不报错。

#### 实测收益比预期小，如实记

| | yield 路径（10:45） | collect+wait（11:01） |
|---|---|---|
| main 轮次 | 3 轮 | **1 轮** |
| main 自身模型时间 | 94.1s | **~73.6s**（扣掉阻塞 99s） |
| Stage1→Stage2 空档 | 11–14s | **6s** |
| 端到端 | ~157s | **172.6s** ← 更慢 |

🔴 **端到端反而更慢** —— 因为这次 Stage 1 本身慢了
（news 63.4→78.3s、sector 51.6→61.9s）。**n=1 时 Stage 1 的波动盖过了这个改动。**

所以能确定的只有两条：

1. **结构变对了** —— 一条坏的代码路径被删掉，对冲行为消失了
2. **main 的模型工作量降了约 22%**

⚠️ 不能声称端到端变快。要证明它，需要在 Stage 1 稳定的条件下多测几次 ——
而 Stage 1 的波动源（第三方接口限流）**不在我们控制内**。

> 这正是开发流程第 4 条「重构要两个独立信号」的场景：
> 结构性证据（调用序列变短）已有，**数值证据还没有**。

#### `agents_wait` 是「谁先回来就先返回」

实测它被调了 5 次 —— 每次返回一批完成的，main 拿剩下的再等。
这不是 bug，重入代价只有 ~4s（立刻又阻塞住了）。但要知道它不是一次到位。

### 🔴 「≥5 次真实 missing」攒不快

它要的是**真实**缺数据，不是注入故障。而 Phase 2 不建 cron
（第一条在 Phase 3）⇒ 需要手工日跑。

#### 台账从库里生成，不手工记

原本打算手工记「日期 / 哪个源缺 / 缺失代码 / Card 状态」。
但这四项**全都已经在 `decision_records` 里了** —— 手工再记一遍就是
第二套口径（L-3），而且它会先漂。⇒ `tools/verify/missing_ledger.py`。

#### 🔴 两次「数着数着就达标了」

**一、注入的不能算。** 演练用 `--break-source` 制造的缺失如果混进来，
等于用自己制造的故障证明自己能发现故障 —— 那不是证据，是同义反复。

判据一开始写的是中文文案「演练：人为中断」。测试立刻抓到
`market_calc` / `emotion_calc` 用的是另一句。两套文案 ⇒
那两个 skill 的注入故障会被算成真实缺失。

⇒ 改用 **CLI 开关的字面量** `--break-source` 做判据。
散文会被顺手改写，开关名不会。
（顺带发现最不一致的是 `news_scan` —— 我今天刚写的那个。）

**二、不是所有真实缺失都是同等强度的证据。**

| 类别 | 例子 | 证明了什么 |
|---|---|---|
| **源级**（强） | `emotion.pool.unavailable` | 系统能发现**数据**缺了 |
| 编排级（弱） | `supervisor.agent_offline` | 只证明「我们知道自己少了个 Agent」 |
| `legacy`（弱） | 裸字符串，无代码 | 统计不出来 |

混在一起数，达标会来得太容易（29 张卡里 27 张「有真实缺失」，
而只看源级就只剩 11 张）。

#### 当前状态：数上够了，实质不够

```
有源级真实缺失的决策：11 / 29 张卡    要求 ≥5    ✅
不同的源级缺失代码：18 种            覆盖天数：1 天  ⬜
```

🔴 **全部来自同一天。** 同一天的多次运行缺的往往是**同一个东西** ——
它证明的是「这个源今天不好使」，而不是「系统能发现各种缺失」。

⇒ 这条出口条件还不能勾。需要跨天累积，工具已经会在只有一天时自己报警。

## 5. 明确不做

`discipline`（裁定 13）/ 任何 cron / 飞书 / 任何下单路径 /
PostgreSQL / Redis / 回测 / 历史数据回补 / Web UI。

以及两条来自外部评审、**经实测否决**的建议：

- **「Offline First, Live Last」** —— 对本项目恰好是反的。
  market 的数据源选型完全来自先探测真接口。先写 fixture 等于
  把一个坏掉的 API 形状固化进测试。正确表述是「**测试离线，设计先探活**」
- **`volume_state = EXPANDING/NORMAL/SHRINKING` 由 skill 产出** ——
  违反铁律 4。skill 给 `volume_ratio` 这个数，归类由 Agent 做
