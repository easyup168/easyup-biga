# 第 11 章 · 第二个 Specialist：边界划在哪，以及怎么证明它们真的并行

> 对应 Phase 2 的 2.1。设计文档见 [`docs/design/phase2-market.md`](../design/phase2-market.md)。

---

## 目标 / 产出

做完这一章你会有：

- 第二个 Specialist（`market`）与它的 skill（`market-calc`，15 个字段）
- 一个共享采集层 `skills/_sources/`
- 一条**机器可核**的判据：Stage 1 的两个 Specialist **真的并行**
- 三条在这段工作里被抓出来的 bug（其中一条是 Phase 1 埋的）

---

## 为什么这么做

### 1. 第二个 Specialist 的价值不在数据，在「并行被证明过」

market 的代码结构几乎是 emotion 的复制。真正新的东西只有一个：

> `agents.defaults.subagents.maxConcurrent: 6` 从 Phase 1 就配好了，
> 但仓库里只有一个 specialist —— **并行至今零次实测**。

一个配了却从未被验证的参数，和一个不存在的参数没有区别。
所以这一章的验收不是「market 能出数」，是「两个 Specialist 的时间区间相交」。

### 2. 先解决边界，再写代码

上游需求文档把**同一批事实同时派给了两个 agent**：

| | 上游给 market | 上游给 emotion |
|---|---|---|
| 重叠 | 涨停/跌停、炸板、连板高度、**市场宽度** | 涨停、跌停、炸板率、最高板、连板、**上涨/下跌家数** |

而 `emotion-calc` 在 Phase 1 就已经在算宽度了。一个 agent 时无所谓，
第二个 agent 上线的当天就是冲突。

**为什么不能「两个都算」**：宽度端点是**不带日期字段的实时快照**。
两个 agent 并行各调一次，落到同一张 Card 上就是**同一个字段两个不同的值**，
而且两个都带着推断出来的 `as_of`。不会报错，只会某天悄悄给出两个数。

实测坐实了它 —— 周日请求，返回的数与上一交易日**逐位相同**：

```
周日 2026-09-20 请求 → 4277 / 1173 / 180
上一交易日 09-18 记录 → 4277 / 1173 / 180
```

它把最后一个交易日的快照冻在那里反复发。

> **通用原则：同一个事实只能有一个生产方。**
> 两个消费方各算一遍不会报错，只会在某天悄悄给出两个数。

于是有了裁定 15，宽度归 market，emotion 删掉那三条。
情绪分公式只用 涨停家数 / 最高板 / 炸板率 —— **删掉零成本**，派生值一个没变。

### 3. 数据源：最省事的方案被实测推翻

原计划是「给宽度那次请求多加几个字段，一次拿到宽度 + 点位 + 成交额」。
一条 `curl` 就够，省事得很。实测结果：

```
上证指数(000001)  最新=0.0  涨跌%=-29971017728.0  额=0.0  涨/跌/平=1756/519/77
```

宽度是对的，**行情字段全是垃圾**。而且：

- `rc = 0`（接口说自己成功了）
- 字段齐全，一个不少
- 类型正确，都是数字

**任何「是不是数字」「有没有这个字段」的检查都会放过它。**
`-29,971,017,728%` 会被原样记成「今日涨跌幅」。

再试其他端点，又撞上两件事：

| 尝试 | 结果 |
|---|---|
| `push2` / `push2his` 行情 | 直接断连 / 返回 0 字节 |
| `push2his` 的 kline，`lmt=25` | **`lmt` 被忽略**，返回全历史（483KB 后被截断） |

最后的选型是三个源，**按「谁能自证时间」分工**，不按「谁方便」：

| 源 | 提供 | 它自己声明的时间 |
|---|---|---|
| 新浪日线 | 交易日 / 点位 / 涨跌幅 / 量能基线 | 每行自带 `day` ← **权威** |
| 腾讯行情 | 成交额 | 14 位时间戳 |
| 东财 ulist | 涨跌家数 | **没有**（只能推断） |

> **通用原则：数据源的分工，按「谁能自证它描述的是哪一刻」来划。**
> 一个不能自证时间的源，你永远不知道它给的是今天还是上周五。

### 4. 单位陷阱，以及它顺手变成的一条校验

```
新浪日线 sh000001  volume = 48,571,250,700   （股）
腾讯行情 sh000001  成交量 =    485,712,507   （手）
485,712,507 × 100 = 48,571,250,700           ✅ 完全相等
```

跨源做比值 = **静默错 100 倍**，而 100 倍的量能比看起来只是「今天爆量」。

所以量能基线与今日量必须同源。而反过来，这个恒等式成了一条**免费的双源校验**：
偏离超过 1% 就说明某一边的口径变了。

⚠️ 容差是 1% 而不是「完全相等」。盘中两个源的刷新时刻不同，必然有微小差异
（实测收盘后深证两源差 45 股）。**要求逐位相等会造出一个盘中永远报红的检查，
而永远报警的检查最终会被所有人忽略。**

### 5. 第二个消费方出现的那一刻，就是抽取共享层的时刻

market 需要 emotion 那套重试 / 退避 / 请求头 / 备选主机链。抄一份会怎样？

两套重试策略慢慢漂开，**而漂开时不报错** —— 表现只是某个源偶尔多一条 missing。

所以第 1 步先把 `emotion-calc/scripts/sources.py` 抽成 `skills/_sources/`。
这动的是 Phase 1 **已验收**的代码，所以要用两个独立信号证明它是空操作：

1. **124 条测试一条不变** —— 不是「仍然全绿」，是数量与内容都没动
2. **真采一次，数字与 Phase 1 记录逐位相同**

第 1 条有个细节：测试里只加了一行 `import _sources as sources`，
**局部名保持不变**，其余 200 余处引用零改动。
如果顺手把 `sources.` 全改成 `_sources.`，这个信号就脏了 ——
你将无法区分「重构没问题」和「测试被改得刚好还能过」。

### 第 4 步 · 建 agent 与配线

```bash
BIGA=~/.openclaw-biga/bin/biga
$BIGA agents add market --workspace ~/.openclaw-biga/workspace/agents/market --non-interactive
```

脚手架又生成了那五件套（嵌套 `.git` / `BOOTSTRAP.md` / `SOUL.md` /
`IDENTITY.md` / `USER.md`），照第 06 章清掉。

配置三处，**两端都要列**：

```json5
{
  agents: {
    defaults: { subagents: { announceTimeoutMs: 120000 } },
    entries: {
      main:   { subagents: { allowAgents: ["emotion", "market"] } },
      market: { subagents: { allowAgents: [] } },
    },
  },
  tools: { agentToAgent: { allow: ["main", "emotion", "market"] } },
}
```

只改一边**不会报错**，只会让工具「不可见」—— 而 Phase 1 已经为
「工具不可见」付出过一整个下午（第 07 章）。

### 第 5 步 · 并行判据

`tools/verify/latency_report.py --parallel-check`。

🔴 **判据是两个 Specialist 的时间区间是否相交，不是「这次跑得快不快」。**

串行的表现是：每步成功、Card 照常产出、日志全绿，**只是慢了一倍**。
而「慢了一倍」会被网络波动掩盖。区间相交是**结构性证据**，快慢不是。

只有一个 Specialist 时，脚本报「**判不了**」而不是「通过」：

```
Stage 1 并行检查
  窗口内只有 1 个 specialist：emotion
  ⇒ **判不了**（不是「通过」）。并行需要至少两个 specialist 才谈得上。
```

> **通用原则：R-3 对验证工具本身同样适用。**
> 一个把「没测到」报成「通过」的检查，比没有检查更危险。

## 坑

### 坑 1 · 一个 `rc=0` 的垃圾值

已在上文详述。要点是：**结构校验拦不住语义垃圾，量级校验才行。**

### 坑 2 · `lmt=25` 被忽略，返回全历史

请求「最近 25 根」，拿回 483KB 然后连接被掐断。
表现是 `json.JSONDecodeError: Unterminated string` —— 看起来像 JSON 坏了，
实际是**分页参数没生效**。

### 坑 3 · 股与手差 100 倍

见上文。这条的特殊之处在于它**既是坑也是校验**。

### 坑 4 · 🔴 Phase 1 埋的崩溃：盘中 `as_of > retrieved_at`

写 market-calc 的 as_of 时顺手验了一下 emotion-calc 的同一段逻辑：

```python
Evidence(as_of=2026-09-21T15:00+08:00, retrieved_at=2026-09-21T10:00+08:00)
→ ValueError: as_of 晚于 retrieved_at —— 数据不可能早于自身被取回
```

交易日盘中 10:00 采数据，`as_of` 被算成「今天 15:00 收盘」，
而契约层校验「数据不可能早于自身被取回」⇒ **整个 skill 抛异常退出，
连一条 missing 都留不下**。

**Phase 1 九项验收全过，却没发现它。** 为什么？

> 那几天的实测**全部发生在收盘后或非交易日**（09-18 晚、09-19、09-20 周日）。
> 验收覆盖了 R-3 的三条路径，却没覆盖**「什么时候跑」**这一维。

而 BigA 是短线决策系统，**盘中才是主场景**。

> **通用原则：验收矩阵要包含「在什么条件下跑」，不只是「输入是什么」。**
> 时间相关的代码，至少要在「窗口内 / 窗口外」两种条件下各跑一次。

修法是把换算抽成共享实现，四个分支都给出合法的 `as_of`：

| 交易日 | 相对现在 | `as_of` | warning |
|---|---|---|---|
| 过去 | — | 当日 15:00 | 无 |
| 今天 | 已收盘 | 当日 15:00 | 无 |
| 今天 | **盘中** | **取回时刻** | 「这是盘中快照而不是全天结果」 |
| 未来 | 异常 | 取回时刻 | 「声称的交易日晚于当前日期」 |

### 坑 5 · 一个字段凭空消失

`--break-source sina_sh` 演练时发现：新浪日线一挂，
来自**腾讯**的 `turnover_sh` 既不产出、也不进 `missing[]` ——
Card 上什么都不留下。

原因是把整个 per-market 循环体挡在了 `if d is None: continue` 后面，
让成交额被一个**不相干的源**的故障连坐了。

> **通用原则：一个字段要么有值，要么在 `missing[]` 里。**
> 第三种状态（悄悄消失）比错值更难发现 —— 错值至少还在卡上。

### 坑 6 · `confidence` 永远到不了 1.0

market-calc 第一次跑就崩了：`confidence 必须在 0..1，收到 1.07`（分母写成 14，
实际 15 个字段）。顺手一查，**emotion-calc 的分母是 15 而它只产 13 个字段** ——
数据完整时也只读到 0.87，**「完整」这件事永远表达不出来**。

两边都改成钉死真实字段数，并各加一条测试。
**故意不做 `min(…, 1.0)` 截断**：截断会把「加了字段忘改常数」变成一个
悄悄偏小的置信度；不截断则当场炸。宁可当场炸。

### 坑 7 · 守卫抓到一个它不该抓的东西

单一生产方守卫刚写完就报红：`trade_date` 也是两个 skill 都在产。

想清楚之后，**它不该按裁定 15 禁掉**。它不是「同一个事实的两份实现」，
而是各自的**溯源元数据**：emotion 的来自股池 `qdate`，market 的来自日线 `day`。

**两者不一致本身就是一条重要信息**（某个源陈旧了）。
强行只留一份，等于把这个信号抹掉，换来的只是形式上的整洁。

⇒ 规则改成：溯源字段**反过来要求每个 skill 都有**，
一致性核对交给 Supervisor 在 Stage 3 做。

> **通用原则：守卫报红时，先问「规则对不对」，再问「代码对不对」。**
> 一条被无脑执行的规则，会把有用的信号也一起删掉。

### 🔴 但这一章的结论是「一半绿」，得说清楚

| 项 | 结果 |
|---|---|
| Stage 1 真并行 | ✅ 区间相交 28.9s，省 41% |
| 端到端 < 90s | ❌ **159.1s，超 1.8×** |

**并行机制是对的，预算是崩的。** 而且崩的位置**恰好是设计文档预判的那个**：

> 真实的延迟风险在 Stage 3，不在 Stage 1。

对照 Phase 1（1 个 specialist）：

| | Phase 1 · 1 个 | 2.1 · 2 个 | 变化 |
|---|---|---|---|
| Stage 1（并行段） | 36.0s | 41.5s | +15% |
| Supervisor 合成 | 30.0s | **≈111s** | **×3.7** |
| 端到端 | 74.8s | 159.1s | ×2.1 |
| Supervisor 输出 tok | 1668 | **9486** | ×5.7 |

Stage 1 只涨了 15%（并行生效了，加的是「最慢那个」而不是「又一个」）。
**翻倍的是 Supervisor。** 证据从 13 条变 25 条，它的输出 token 涨了 5.7 倍。

> **通用原则：并行解决的是扇出，解决不了汇聚。**
> 扇出段加一个 agent 只付「最慢那个」的差价；
> 汇聚段加一个 agent，是实打实多一份要读、要比对、要写进结论的材料。

⚠️ 这是 **n=1 且冷缓存**的一次测量，还不足以推 8 agent 的预算 ——
但它已经足够推翻「加 agent 的主要成本在 Stage 1」这个假设。
Phase 2 的延迟预算要按这条斜率重推，见 `architecture.md` §10.1。

## 后记 · 瓶颈查下去，发现的是完整性问题

第 5 步测出「Supervisor 合成轮 ≈111s」之后，把那一轮的轨迹逐条拆开：

```
12:43:22–12:44:09   47s   零工具调用 —— 纯粹在生成 6460 字符的 JSON
12:44:09–12:44:58   49s   synthesize.py 调 3 次，前 2 次失败，中间读文档诊断
```

失败原因是 `KeyError: 'retrieved_at'`。顺着查下去：

| | `as_of` | `retrieved_at` |
|---|---|---|
| skill 实际输出 | 15 条 | **15 条** |
| Specialist 转述后 | 34 条 | **0 条** |

再对落库的卡：skill 真实采集时刻 **20:42:48**（raw 层记录），
而 Card 上 25 条 evidence 的 `retrieved_at` 全是 **20:44:34** ——
那是 Supervisor 敲命令的时刻，差 106 秒。

> **查一个延迟问题，挖出来的是一个完整性问题。**
> 「事实可追溯」这条地基，在最后一公里被 LLM 的复述打穿了。

而且 Supervisor 还给自己写了一份恢复文档，把补救写成了标准操作：
「transcribing 时给每条加一个 `retrieved_at`（用当前合成时间）」。

> **通用原则：当 agent 开始给自己写「怎么绕过这个错误」的文档时，
> 那是架构在求救。** 它已经把缺陷内化成了流程。

修法不是让它抄得更仔细，是**让它不用抄**：skill 直接把判定原件落库
（schema v3 `agent_verdicts`），返回一个编号，agent 只传编号。


## 本章要点

| # | 一句话 |
|---|---|
| 1 | 第二个 Specialist 的价值不在数据，在**并行被证明过** —— 配了却没验过的参数等于不存在 |
| 2 | 同一个事实只能有一个生产方；两个消费方各算一遍不报错，只会某天悄悄给出两个数 |
| 3 | 但**溯源字段**是例外：它反过来要求人人都有，因为不一致本身就是信息 |
| 4 | 数据源的分工按「谁能自证它描述的是哪一刻」来划，不按谁方便 |
| 5 | `rc=0` + 字段齐全 + 类型正确，仍然可以是垃圾值 —— **量级校验**才拦得住 |
| 6 | 跨源做比值前先确认单位；股与手差 100 倍，而错 100 倍看起来只是「今天爆量」 |
| 7 | 容差不能设成「完全相等」—— 那会造出一个永远报红、于是被忽略的检查 |
| 8 | 一个字段要么有值、要么在 `missing[]` 里；**悄悄消失**是比错值更难发现的第三态 |
| 9 | 验收矩阵要包含「在什么条件下跑」—— Phase 1 全绿却漏了「盘中」这一维 |
| 10 | 守卫报红时先问「规则对不对」，再问「代码对不对」 |
| 11 | 并行的判据是**区间相交**，不是总耗时变短 —— 快慢会被网络波动掩盖 |
| 12 | **不要让 LLM 搬运结构化数据** —— 它不报错，只是漏字段 |
| 13 | agent 开始给自己写「怎么绕过这个错误」的文档时，那是架构在求救 |
| 14 | 查延迟问题挖出完整性问题，是常事 —— **慢往往是某处在做本不该做的事** |
| 15 | 一个会虚报 3 倍的指标比没有指标更糟：它让人去优化不存在的问题 |
