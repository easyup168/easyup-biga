## 目标 / 产出

- Supervisor 那 120 秒的真正去向 —— 它不是在想事情
- 延迟预算 90s → 180s，以及**怎样改预算才不算作弊**
- `tools/verify/isolation.py` —— I-1 终于有可执行判据
- 缺失项台账，以及两次「数着数着就达标了」
- 一个结论：**剩下两条出口条件卡在同一个架构问题上**

## 为什么这么做

### 1. 「差不多做完了」是一种感觉，出口条件是一张表

Phase 2 的八条出口条件写在设计文档里，是开工前定的。到了这一步，
七个 Agent 都建完了，端到端跑得通 —— **很容易觉得就是做完了**。

但逐条对表的时候，2/8。

> 出口条件的价值不在于它们难，而在于它们**是开工前定的**。
> 做完之后再来定标准，定出来的一定是自己刚好达到的那个。

## 坑

### 坑 1 · 🔴 契约推荐的快路从来没生效过

Supervisor 三轮共 120.7s，占总时长 64%。第一反应又是「提示词写得不好」。

按流程展开调用序列：

```
10:45:37  agents_wait   → 五个 id 全部 not_found，8.2s
10:45:43  subagents     → 它自己去查状态，6.2s
10:45:50  sessions_yield→ 退回异步路径，7.4s
```

**22 秒全是协议开销，而且没有任何东西报错。**

去运行时源码里找 `agents_wait` 的判据：

```js
if (!entry?.collect) { errors.push({ runId, error: "not_found" }); continue; }
```

它**只认 swarm collector 子会话**。而契约教 Supervisor 用 `agents_wait`，
**却没教它 spawn 时带 `collect: true`**。

⇒ 那条被标成「优先」的快路，一次都没跑通过。

> 通用原则：**「推荐的做法」如果从未被验证过，它就是一句祝福。**
> 判据是看**它在真实轨迹里返回了什么**，不是看文档里怎么写的。

#### 更深一层：给了两条路，于是它两条都走

契约原文是「**优先**用同步等待 `agents_wait`」+「spawn 之后用
`sessions_yield` **是对的**」。

结果 agent 先试 A，失败，又去查 `subagents` 想弄清 A 为什么没用，最后走 B。
三次工具调用，三个模型往返。

> **写契约时，一个动作只给一条路。**
> 给「优先 A，B 也行」，得到的是 **A 然后 B**。
> 备选要明确标成「兜底」，并写清什么条件下才走它。

#### 一对，不能只用一半

改完之后必须同时写清：`collect: true` 模式**没有完成通知**。
只用 collect 而后 yield，这次对话会**静默地永远停住** —— 既不出卡也不报错。

### 坑 2 · 🔴 改完之后端到端**更慢**了，而我差点只报好消息

| | yield 路径 | collect+wait |
|---|---|---|
| main 轮次 | 3 轮 | **1 轮** |
| main 自身模型时间 | 94.1s | **~73.6s** |
| Stage1→Stage2 空档 | 11–14s | **6s** |
| 端到端 | ~157s | **172.6s** ← 更慢 |

前三行都在改善，最后一行变差 —— 因为这一次 Stage 1 本身慢了
（`news` 63.4→78.3s、`sector` 51.6→61.9s）。

很容易只报前三行。但那样就成了**挑对自己有利的指标**。

诚实的结论只有两条：

1. **结构变对了** —— 一条坏的代码路径被删掉，对冲行为消失了
2. **main 的模型工作量降了约 22%**

**不能声称端到端变快。** 要证明它，需要 Stage 1 稳定下来多测几次 ——
而 Stage 1 的波动源（第三方接口限流）不在我们控制内。

> 这正是「重构要两个独立信号」的场景：
> 结构性证据（调用序列变短）已有，**数值证据还没有**。

### 坑 3 · 改预算的三个必答问题

出口条件 5 要求「延迟预算按实测重推」。四次盘中实测下来，
即使每一项都取最好值：

```
Stage 1 最好 64.2  +  risk 最好 19.9  +  main 最好 73.9  =  158s
```

**90s 在当前架构下做不到。** 所以预算要改成 180s。

但「指标红了就调指标」是本项目明令禁止的。区别在哪？

⇒ **改预算必须同时回答三个问题，缺一条就是作弊：**

| 问题 | 这次的答案 |
|---|---|
| **旧数字错在哪** | `60-105s` 是在一个 agent 都没有时把四个区间相加得到的 —— 愿望，不是预测 |
| **新数字怎么来的** | 四次实测，每项取最好值仍需 158s，180s 留 14% 余量 |
| **什么时候它该红** | 优化后三次都在 158–173s；超 180s 说明某个组成异常了，不是「今天慢一点」 |

还要**指出哪部分不在我们控制内**：Stage 1 的最慢项是第三方接口延迟，
并发度调到 4 会触发渐进限流（第 15 章）。不写这一条，
下一个人会以为 180s 是可以继续压的。

### 坑 4 · 一个 100% 误报的检查，和没写一样

`CLAUDE.md` 的不变式表里，I-1 的验证方式一直写着
「`tools/verify/isolation.py`（**待建**）」。

一条没有可执行判据的不变式，等于一条约定 —— 而约定只能约束记得它的人。

写的时候第一版是这样：

```python
if path.startswith(str(NEIGHBOUR)):    # NEIGHBOUR = ~/.openclaw
    offenders.append(...)
```

自测立刻报出几十条「越界」。全是 BigA 自己的文件 ——

> **`~/.openclaw` 是 `~/.openclaw-biga` 的前缀。**

实测量化：`startswith` 命中 **64** 个 fd，按路径分量比较（`is_relative_to`）
命中 **0** 个。

> 通用原则：**当两个名字有前缀关系时，字符串比较一定会出事。**
> 路径要按分量比，而不是按字符。
>
> 而这个 bug 的形状特别坏：它不是漏报，是**全是误报** ——
> 一个每次都红的检查，几次之后就没人看了，和没写一样。

探针（**全程不碰邻居的任何文件**）：把检测目标指到临时目录、
以写模式打开一个文件 ⇒ 立刻抓到；只读打开 ⇒ 不误报。

### 坑 5 · 🔴 两次「数着数着就达标了」

出口条件 4：**`missing[]` 在真实缺数据时非空 ≥5 次（不是注入故障）**。

设计文档原本写「需要手工日跑 + 一份台账：日期 / 哪个源缺 / 缺失代码 / Card 状态」。
但这四项**全都已经在 `decision_records` 里了** —— 手工再记一遍就是第二套口径，
而且它会先漂。⇒ 台账从库里生成。

#### 第一次：判据用了中文散文

演练注入的缺失要排除掉（否则等于用自己制造的故障证明自己能发现故障）。
判据写的是文案「演练：人为中断」。

测试立刻抓到 `market_calc` / `emotion_calc` 用的是**另一句**
「数据源被人为中断（--break-source X）」。

两套文案 ⇒ 那两个 skill 的**注入故障会被算成真实缺失**，出口条件凭空达标。

⇒ 改用 **CLI 开关的字面量** `--break-source` 做判据。

> **散文会被顺手改写，开关名不会。**
> 判据要落在最不容易被无意改动的那个东西上。

⚠️ 顺带发现最不一致的是 `news_scan` —— **我上一章刚写的那个**。
新加的东西最容易偏离既有约定，因为写的时候没在看别人怎么写。

#### 第二次：不是所有真实缺失都是同等强度的证据

| 类别 | 例子 | 证明了什么 |
|---|---|---|
| **源级**（强） | `emotion.pool.unavailable` | 系统能发现**数据**缺了 |
| 编排级（弱） | `supervisor.agent_offline` | 只证明「我们知道自己少了个 Agent」 |
| `legacy`（弱） | 裸字符串，没有代码 | 统计不出来 |

混着数：29 张卡里 **27 张**「有真实缺失」。
只看源级：**11 张**。

分开之后还有第三层：那 11 张**全在同一天**。而同一天的多次运行缺的往往是
同一个东西 —— 它证明的是「这个源今天不好使」，不是「系统能发现各种缺失」。

⇒ **这条出口条件不能勾。** 工具会在只有一天数据时自己报警。

> 通用原则：一个指标「达标」之后还要再问一句 ——
> **它证明的是不是我当初想证明的那件事。**

### 坑 6 · 🔴 剩下两条卡在同一个根上，而它不是 bug

出口条件 3（真实否决）和 4（跨天缺失）都推不动，原因是同一个：

盘中跑一次，六个 Agent 报出**两个交易日** ——
`emotion` / `news` 用实时源说「此刻」，日线类说「上一个已完成交易日」。

`risk` 拒绝把它们当同一天审，于是**每次都是「无法判定」**。

- 永远「无法判定」⇒ 攒不到真实「否决」
- 每次缺的都是同样那几条 ⇒ 台账攒不出多样性

**这是对的行为。** 把「此刻的情绪」和「上周五的技术面」并排当成同一天的证据，
本来就是在编造一个不存在的时点。

> 通用原则：**当两条验收条件同时卡住，先怀疑它们有共同的根。**
> 分别去凑，会凑出两个绕过同一个问题的补丁。

解法有两条，都不在 Phase 2 范围内：

| 解法 | 代价 |
|---|---|
| 盘中用分时合成一根未完成的 K | MA/MACD 会跳动，要重新定义 ⇒ **口径一改，此前所有实测数字不可比** |
| 明确 Card 只在**盘后**出 | 放弃盘中辅助，但所有数字仍可比 |

⇒ 先做后者。盘中决策是短线系统的核心价值，但那属于 Phase 3 的数据层加厚 ——
现在硬做，会把一个**数据层问题伪装成指标问题**。

## 验证

```bash
cd ~/.openclaw-biga/workspace

B=$(python3 tools/verify/isolation.py --print-mtime)
python3 tools/verify/isolation.py --before "$B"
#   期望：四项全绿

# 缺失项台账（出口条件 4）
python3 tools/verify/missing_ledger.py
#   期望：源级真实缺失 ≥5 张卡；覆盖天数 <2 时它会自己报警

# 延迟与成本（预算已重推为 180s）
python3 tools/verify/latency_report.py --parallel-check
```
