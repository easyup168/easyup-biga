- 一张能核对的功能清单 —— 而不是「差不多做完了」的感觉

## 一、建成了什么

### 数字

| | |
|---|---|
| Agent | **7 / 8** —— Supervisor + Stage 1 五个 + Stage 2 一个 |
| Skill | 7 个（6 个算子 + 决策卡合成） |
| 测试 | **445 条**，全部离线 |
| 数据层 | SQLite WAL，schema **v4**，5 张表，只追加由触发器强制 |
| 已落库决策卡 | 31 张，全部可回放 |
| 核查工具 | 7 个（延迟 / 调用序列 / 隔离 / 缺失台账 / 公开审查 / …） |

### 拓扑

```
                    ┌─ market     大盘：指数、成交额、量能、宽度
                    ├─ sector     板块强度与资金方向
   Supervisor ──┬──→├─ technical  上证指数技术面（均线/MACD/RSI）
     (main)     │   ├─ emotion    情绪周期位置
                │   └─ news       消息面（第一个必须「读懂」的）
                │        ↓  五个**实测并行**（区间相交 27.9s）
                │   ┌─────────────┐
                └──→│ risk        │ 制衡层：只读冻结证据，唯一有否决权
                    └─────────────┘
                         ↓
                    Decision Card（证据可追溯、可回放）
```

**第 8 个 `discipline` 故意不建** —— 它的输入是人的交易行为史，
而本系统不下单不接账户 ⇒ 现在没有输入源，硬建只能编。

### 一张卡里有什么

八段：抬头 / 每个 Agent 一行 / 状态 / 核心矛盾 / **缺失项** /
**提请注意** / 证据 / 合成说明。

两个设计选择值得单独说：

**1. 每个 Agent 有两个判断，回答的不是同一个问题。**

| 列 | 问的是 |
|---|---|
| `verdict` | **数据全不全**（`PASS` / `WARNING` / `UNKNOWN`） |
| `stance` | **它的判断是什么**（各 Agent 有固定词表） |

一个字段装不下两件事。只看 `PASS` 会把它误读成「看好」。

**2. 缺失项永远显示，哪怕 0 条。**

「没有缺失项」本身是一条信息。这是整个项目最优先防范的失败模式的反面 ——
**算不出来必须说算不出来**。

每条缺失带机器可读代码（`market.turnover.date_mismatch`），
所以「哪个源最常缺」是能统计出来的。

## 二、怎么跑、怎么用

```bash
cd ~/.openclaw-biga/workspace

bin/biga-card              # 出一张新卡（实测 2–3 分钟、约 $1.2）
bin/biga-card --list       # 最近出过哪些
bin/biga-card --show <号>   # 看某一张
bin/biga-card --check <号>  # 用冻结证据重跑，断言结论逐字段相同
```

### 为什么需要这个包装

在它之前，出一张卡要手敲一段很长的提示词，而且**漏一句就出问题**：

| 漏了什么 | 后果 |
|---|---|
| `--session-key` | 用默认会话，一轮 `end_turn` 就返回，卡不出来 |
| 「带上决策编号」 | Specialist 用临时号，落库直接报错 |
| 「等全部结算」 | 两次运行交叠（第 15 章那个事故） |

这些都是「靠人记得」的约定 —— 而本项目反复证明那类约定会失效。

> 通用原则：**当一段操作的正确性依赖「记得加某几句」，就把它固化成一条命令。**
> 教程写得再清楚，也只约束读过教程的人。

### 🔴 四个「确认它没骗你」的检查

这是本节真正的重点。**四个互相独立，任何一个都能单独拆穿。**

| 检查 | 命令 | 它证明什么 |
|---|---|---|
| 回放一致 | `bin/biga-card --check <号>` | 卡上的数字确实是从冻结证据算出来的 |
| 真调了 Specialist | `tools/verify/agent_trace.py` | 数据来自**运行时自己的表**，被验证方控制不到 |
| 真并行了 | `latency_report.py --parallel-check` | 判据是**时间区间相交**，不是「跑得快」 |
| 没影响同机其他服务 | `tools/verify/isolation.py` | 逐个进程、逐个 fd 查 |

> 通用原则：**验收要用被验证方控制不到的证据。**
> 「Agent 自报它调用了谁」和「运行时记录了谁被调用」是两回事。

### 单独跑一个 Specialist

```bash
python3 skills/news-scan/scripts/news_scan.py --no-store --render
```

不加 `--no-store` 会**报错**，而且是有意的：一条无法归属的判定原件
比没有更糟 —— 它看起来是正经证据，却说不清属于哪次决策。

演练数据源故障：

```bash
python3 skills/news-scan/scripts/news_scan.py --no-store --break-source feed --render
#   期望：UNKNOWN + news.feed.source_broken
```

**验的是「它会不会假装没事」。**

## 三、收尾时踩的坑

### 坑 1 · 🔴 契约推荐的快路从来没生效过

Supervisor 三轮共 120.7s，占总时长 64%。第一反应又是「提示词写得不好」。
按流程展开调用序列：

```
10:45:37  agents_wait   → 五个 id 全部 not_found，8.2s
10:45:43  subagents     → 它自己去查状态，6.2s
10:45:50  sessions_yield→ 退回异步路径，7.4s
```

**22 秒全是协议开销，没有任何东西报错。**

去运行时源码里找判据：`if (!entry?.collect)` —— `agents_wait` 只认
**swarm collector** 子会话。而契约教它用 `agents_wait`，
**却没教它 spawn 时带 `collect: true`**。

那条被标成「优先」的快路，一次都没跑通过。

> 通用原则：**「推荐的做法」如果从未被验证过，它就是一句祝福。**
> 判据是看它在真实轨迹里返回了什么，不是看文档里怎么写的。

#### 更深一层：给了两条路，于是它两条都走

契约原文是「**优先**用 `agents_wait`」+「`sessions_yield` **是对的**」。

> **写契约时，一个动作只给一条路。**
> 给「优先 A，B 也行」，得到的是 **A 然后 B**。

### 坑 2 · 🔴 改完之后端到端更慢了，而我差点只报好消息

| | 改前 | 改后 |
|---|---|---|
| main 轮次 | 3 轮 | **1 轮** |
| main 模型时间 | 94.1s | **~73.6s** |
| Stage1→Stage2 空档 | 11–14s | **6s** |
| 端到端 | ~157s | **172.6s** ← 更慢 |

前三行都在改善，最后一行变差 —— 这一次 Stage 1 本身慢了
（`news` 63.4→78.3s）。很容易只报前三行，但那是**挑对自己有利的指标**。

诚实的结论只有两条：结构变对了、main 的工作量降了约 22%。
**不能声称端到端变快**，那需要 Stage 1 稳定下来多测几次 ——
而它的波动源（第三方接口限流）不在我们控制内。

### 坑 3 · 改预算的三个必答问题

四次盘中实测，即使每项都取最好值仍需 158s ⇒ **90s 在当前架构下做不到**。

但「指标红了就调指标」是明令禁止的。区别在哪？

| 必答 | 这次的答案 |
|---|---|
| **旧数字错在哪** | `60-105s` 是在一个 agent 都没有时把四个区间相加得到的 —— 愿望，不是预测 |
| **新数字怎么来的** | 四次实测取最好值 158s，180s 留 14% 余量 |
| **什么时候它该红** | 优化后三次都在 158–173s；超 180s 说明某个组成异常了 |

还要**指出哪部分不在我们控制内**，否则下一个人以为 180s 还能继续压。

### 坑 4 · 一个 100% 误报的检查，和没写一样

`I-1`（不得写同机其他服务的目录）的验证方式一直写着「（待建）」。
一条没有可执行判据的不变式，等于一条约定。

写的时候第一版用 `startswith` 判越界 —— 自测立刻报出几十条，全是自己的文件。
因为两个目录名有**前缀关系**。

实测量化：`startswith` 命中 **64** 个 fd，按路径分量比较命中 **0** 个。

> 通用原则：**两个名字有前缀关系时，字符串比较一定会出事。**
>
> 而这个 bug 的形状特别坏：它不是漏报，是**全是误报** ——
> 一个每次都红的检查，几次之后就没人看了。

### 坑 5 · 🔴 两次「数着数着就达标了」

**一、判据用了中文散文。** 演练注入的缺失要排除掉，判据写的是文案
「演练：人为中断」。测试立刻抓到另外两个 skill 用的是**另一句** ——
它们的注入故障会被算成真实缺失，出口条件凭空达标。

⇒ 改用 **CLI 开关的字面量** `--break-source`。

> **散文会被顺手改写，开关名不会。**

⚠️ 顺带发现最不一致的是上一章刚写的那个 skill。
**新加的东西最容易偏离既有约定**，因为写的时候没在看别人怎么写。

**二、不是所有真实缺失都是同等强度的证据。**
「某个 Agent 还没建」证明的是「我们知道自己少了个 Agent」，
不是「我们能发现数据缺了」。混着数 27/29 张卡，只看源级只剩 11 张。

> 通用原则：一个指标「达标」之后还要再问一句 ——
> **它证明的是不是我当初想证明的那件事。**

### 坑 6 · 🔴 一个今天的数，挂着上周五的时间戳

作者看卡时问「怎么用的是 18 日的行情数据」。查下去发现**两件事，只有一件是对的**。

**对的**：日线派生量确实是上一交易日 —— 当天的日线要收盘后才发布。

**错的**：

```
[market] 上涨家数 = 4385   as_of 09-18 15:00
```

4385 是**当天此刻**的数。根因两层：`as_of` 只从日线算**一次**就被所有证据共用；
而这个端点**连日期字段都没有**。代码其实发了 warning，
但 `card.render()` **从不渲染 warnings** —— 于是卡面看起来板上钉钉。

⚠️ 不对称之处：**带日期的源会被核对**（不一致就报 `date_mismatch`），
**唯独没有日期的那个源反而被默认对齐** —— 而它恰恰最可能对不上。

> 通用原则：**一个值的时间戳是它的一部分，不是环境的属性。**
> 「这批数据都是同一时刻的」是个假设，而它对无日期的源从来不成立。

### 坑 7 · 教程本身成了泄露面

人工 review 指出：**「如何接通模型」属于个人/组织的特殊情况**，
不该写进公开仓库。

⚠️ 八项审查一项都没抓到 —— 它既不是密钥，也不是路径，也不是可识别的模块名。

> 🔴 这类内容的危险在于**它读起来像「踩坑记录」** ——
> 而教程恰恰是最鼓励写踩坑的地方。

⇒ 加审查第 9 项。加上之后先红 28 处，分布在 5 个文件。

#### 连带：清理历史时，审查脚本会被自己的清理改坏

`filter-repo --replace-text` 替换**所有** blob，包括审查脚本当前那一份。
九项正则全变成 `(***|***|…)` —— **脚本静默失效，跑起来一切正常**。

修法不是把词填回去，是让脚本自身不再字面包含它们：`[a]bcd` 与 `abcd`
正则等价。就是 `ps aux | grep [b]ash` 那个老把戏。

### 坑 8 · 改完同一秒内跑测试，执行的是旧字节码

修坑 6 时卡了四五轮：代码明明在那儿，就是不生效。

```
card.py   13:53:41.579
card.pyc  13:53:41.503     ← 相差 76 毫秒
```

Python 的 bytecode 缓存用 mtime 判新旧，**粒度是 1 秒**。

> 通用原则：**「改一下、立刻跑」正是探针验证守卫的节奏** ——
> 也正是最容易撞上这个缓存的节奏。探针脚本里清一次 `__pycache__`。

## 四、还做不到什么

诚实地列出来，比含糊带过有用。

| | 状态 |
|---|---|
| 自动下单 | **永不**（本阶段）。不接账户 |
| 定时自动出卡 | 未建 —— 第一条 cron 在 Phase 3 |
| 个股层面的判断 | 未做。当前只到指数与板块层面 |
| 回测 / 区分力检验 | Phase 4 |
| **盘中给出有把握的结论** | 🔴 **做不到，而且原因是结构性的** |

### 🔴 为什么盘中总是 `WAIT`

盘中跑一次，六个 Agent 会报出**两个交易日**：

| agent | `trade_date` | 为什么 |
|---|---|---|
| `emotion` / `news` | 今天 | 实时源 ⇒ 说的是**此刻** |
| `market` / `technical` / `sector` | 上一交易日 | 日线 ⇒ **今天的还没收** |

`risk` 拒绝把它们当成同一天的事实一起审，于是每次都是「无法判定」。

**这是对的行为** —— 把「此刻的情绪」和「上一交易日的技术面」并排当成
同一天的证据，本来就是在编造一个不存在的时点。

⇒ **想看有把握的卡，收盘之后跑。**

> 通用原则：**一个诚实的 `WAIT` 可能是在报告架构问题，而不是市场问题。**
> 区别在于它每次都出现，还是只在某些条件下出现。

### 这也挡住了最后两条出口条件

`risk` 永远「无法判定」⇒ 攒不到真实「否决」；
每次缺的都是同样那几条 ⇒ 台账攒不出多样性。

> 通用原则：**当两条验收条件同时卡住，先怀疑它们有共同的根。**
> 分别去凑，会凑出两个绕过同一个问题的补丁。

## 五、Phase 3 展望

路线图里 Phase 3 是「**数据层加厚 + `discipline` + 独立 IM 应用 + 第一条 cron**」。
经过 Phase 2 的实测，这几件事有了更具体的形状。

### 1. 时间基准统一 —— 从待决项升级为首要项

这是 Phase 2 唯一没能解决、而且**正在挡路**的问题。两条路：

| 解法 | 代价 |
|---|---|
| 盘中用分时合成一根未完成的 K | MA/MACD 会跳动，要重新定义 ⇒ **口径一改，此前所有实测数字不可比** |
| 明确只在盘后出卡 | 放弃盘中辅助，但所有数字仍可比 |

**建议先做后者**，把前者留给数据层加厚。
盘中决策是短线系统的核心价值，但现在硬做，
会把一个**数据层问题伪装成指标问题**。

### 2. 采集缓存 —— 现在有了具体的理由

Phase 2 记过一次「属于 Phase 3，现在做是提前优化」。实测给了它两个新理由：

- 同一个端点被多个 skill 各采一次（日线被三个 agent 分别取 25/120/2 根）
- 第三方接口会**渐进限流**（并发度 4 时 `7.2s → 25.2s → 60.1s` 单调上升）

⇒ 缓存不只是省时间，是**减少对别人接口的压迫**。

### 3. 第一条 cron —— 出口条件已经写死

> **每条 cron 都必须有被证明的消费方。** 判据是调度命令的字面量。

而且 Phase 2 留下了一个现成的消费方：缺失项台账需要**跨天累积**，
手工日跑攒不快。这正是第一条 cron 该干的事。

⚠️ 加 cron 之前先确认 `maxConcurrent` —— Stage 1 的 5 个已经贴着上限，
再加 agent 会**静默排队**（表现是并行检查报「区间不相交」）。

### 4. `discipline` —— 先定输入源，再谈建它

推迟它的理由没有变：没有输入源。Phase 3 要做的第一步不是写它的 skill，
而是**定它吃什么**（候选：人每日手填当日计划与持仓）。

> 通用原则：**先有输入源，再有 Agent。** 顺序反了就只能编。

### 5. 独立凭据 —— 有明确触发条件的债

Phase 3 之前必须换掉共享凭据。它的代价已经写明：
失效时两套系统同时停，而**排查方向天生是错的**。

### 明确**不要**提前做的

- 自动下单（硬前提是 Phase 4 通过）
- 回测框架（Phase 4）
- 个股层面的选股
- PostgreSQL / Redis（切换条件写死在架构文档 §5.1，现在远未触及）

> 通用原则：**路线图的价值一半在于它说了什么，一半在于它拦住了什么。**
