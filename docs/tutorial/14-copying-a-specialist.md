# 第 14 章 · 复制一个 Specialist：这一步的价值在于「没有新机制」

> 📄 **过程** · 写完即冻结（只追加「⏩ 后续变动」指针）

> 对应 Phase 2 的 2.3：加 `sector` 与 `technical`，Stage 1 扩到 4 个。

## 目标 / 产出

- 两个新 Specialist，**核心架构 0 行改动**
- 三个新的数据源陷阱，其中一个是本项目至今最隐蔽的
- 一次「测试抓到写测试的人」的记录

---

## 为什么这么做

### 1. 这一步专门用来证明抽象站得住

前两步都带新机制（2.1 并行、2.2 冻结证据 + 否决权）。2.3 **刻意不带** ——
它就是复制。而复制这件事本身是判据：

> 如果新增一个 Specialist 需要改契约、改 Supervisor、改 Card，
> 那 Phase 1 建的就不是 Multi-Agent 框架，而是一个 Emotion 专用系统。

实际结果：

| 组件 | 改动 |
|---|---|
| `_contract` | **0 行**（只往 `STANCE_VOCAB` 加了两行词表） |
| Supervisor | roster 表加两行 + spawn 清单加两行 |
| `DecisionCard` / `_store` / `replay` | **0 行** |
| 新增 | 两个 skill、两份 `AGENTS.md`、两组测试 |

这就是「新增 Agent = 新增 skill + 新增 agent + 新增测试」该有的样子。

### 2. `technical` 做指数，不做个股

上游文档给 technical 的职责是「个股技术结构」。但 Phase 2 **不选股** ——
没有个股输入。硬做就会变成第二个 `discipline`：**没有输入源却硬建，只能编。**

⇒ 它分析上证指数。有真实输入（日线序列），产出可核对。

⚠️ 只做上证一个指数也是有意的：两市指数高度相关，做两份只会让 Agent
在两个几乎相同的信号之间纠结，而不会多出信息。

### 3. 「范围外」不进 `missing`

sector 的「板块持续性」需要历史序列，Phase 2 不做历史回补。

| 做法 | 后果 |
|---|---|
| 塞一条 `missing`「持续性算不出来」 | 它**每次都在**，很快变成没人看的常驻噪音 |
| ✅ 写进契约：agent 不许谈持续性 | 缺失项只留给真正的数据缺失 |

> **`missing[]` 是给「本该有却这次没有」的。**
> 前者每次不同，后者每次相同 —— 混在一起，前者就被后者淹没了。

## 坑

### 坑 1 · `pz=600` 被静默忽略

请求 600 行，返回 100 行，而 `total` 照报 496。

```
SourceError: boards/industry: 接口声称 total=496 但只返回 100 行 ——
             分页截断（pz=600），涨跌分布会算错
```

这是**守卫先抓到的**，不是人看出来的 —— 写采集层时顺手加的
「核对 `total` 与实际行数」那一行。与第 11 章 kline 的 `lmt` 被忽略是同一类：
**接口不报错，只是少给你。**

少几十个板块会怎样？「上涨板块占比」直接算错，而那个数看起来完全正常。

### 坑 2 · 🔴 同一时刻，不同端点对「新一天还没开始」的表现是**相反**的

这是本项目至今最隐蔽的一个。

周一 08:48（开盘前）实测：

| 源 | 返回 | 如果当成事实 |
|---|---|---|
| 东财板块榜 | 496 行 `pct` **全 0**，领涨股全 `None` | 「所有板块都平盘」 |
| 东财股池 | `tc=0`，`qdate=今天` | 「今日涨停 0 家」⇒ 冰点 |
| 东财涨跌家数 | `0/0/0` | 「全市场无人交易」 |
| 新浪日线 | **20260918 / 3911.87** | 正确（上一交易日） |
| 腾讯行情 | **3911.87 @20260918161402** | 正确 |

**三个实时源清零，两个历史源保留旧值。**

所以不能靠「有没有数据」判断这一天开没开始 —— 每个源都要自己判断。

#### 更危险的是排序

板块榜按涨跌幅降序返回。**全 0 时「第一名」是任意的一行** ——
那天它给的是「板材 0.0%」。Agent 照着说「今日领涨板块：板材」，
完全是编造，而且读起来毫无破绽。

⇒ `BoardResult.nonzero_count`：非零板块数为 0 就是「这一天还没开始」，
进 `missing`，**不产出榜单**。

### 坑 3 · 同一主机，两个端点的容器类型不同

`ulist` 的 `data.diff` 是**数组**，`clist` 的是**字典**（键 `"0"`,`"1"`,…）。

两处都写成数组解析，第二处会静默拿到空列表 —— 于是「今天没有板块上涨」。

### 坑 4 · 测试抓到的是**写测试的人**

```python
def test_单调上涨时macd柱为正(self, wired):
    assert build().result["macd_hist"] > 0
E   assert 0.0 > 0
```

第一反应是代码错了。查下来**代码是对的**：

```
线性上涨: DIF=7.0  DEA=7.0  HIST=0.0
加速上涨: DIF=28.14 DEA=27.02 HIST=2.24
```

完全线性的序列里，DIF 与 DEA 收敛到**同一个常数**，柱必然趋近 0。

> **MACD 柱衡量的是加速度，不是方向。**

改测试：用加速上涨测柱、用 DIF 测方向。并把这条写进 technical 的契约 ——
否则 Agent 会犯一模一样的错：看到柱为 0 就说「没涨」。

### 坑 5 · 🔴 端到端反过来照出前面两个 Agent 的同类坑

五 Agent 跑完（周一 09:05），Card 是诚实的：`WAIT` + 16 条缺失。
但逐字段核对上游 verdict 时发现 —— **sector 挡住的坑，emotion 和 market 没挡**：

| agent | 报了什么 | 实际 |
|---|---|---|
| emotion | `limit_up_count=0`、`max_streak=0`，`trade_date=20260921` | 盘前尚未形成 |
| market | `advance_count=0/0/0`，而 `trade_date=**20260918**` | 🔴 今天的空快照，贴了周五的日期 |

market 那条尤其严重。它不是「算不出来」——

> 它是一个**有日期的错值**：Card 上写着「9-18 上涨家数 0」，
> 而那天真实是 **4277**。日后做归因的人没有任何办法发现这是假的。

⇒ 抽成共享判据 `_sources.session_in_progress(trade_date, retrieved_at)`，
三个实时源各自据此判断。

> **通用原则：在一个 Agent 上修好的坑，去检查所有同类的 Agent。**
> 它们的数据源往往共享同一个行为，而你只在一个地方想到了它。

### 坑 6 · 加了守卫，就产生了一个恒假分支

market 里原本有：

```python
total = b.advance + b.decline + b.flat
if total: ...
else: c.missing.append("分母为零")
```

加了 `not_yet_formed` 守卫（合计为 0 就把 breadth 置空）之后，
那条 `else` **永远走不到了**。

恒假分支就是 L-7。留着不会报错，只会让下一个人以为还有一条路可走。
删掉，并加一条测试钉死它不会回来。

> **每加一个前置守卫，回头看看它让哪段代码变成了死路。**

### 坑 7 · 🔴 守卫比的是**字段名**，于是同义重复整套流程都没被发现

本章走完全套流程、测试全绿、端到端出卡之后，
同步设计文档时顺手查了一遍「同一个事实有没有两个生产方」：

```
market.sh_close   = 3911.87
technical.close   = 3911.87      ← 同一个事实，不同的名字
```

裁定 15 说「同一个事实只能有一个生产方」，而守卫
`tests/test_field_single_producer.py` 比的是**字段名** ——
`sh_close` 和 `close` 在它眼里是两个字段，完全看不见。

这正是复制一个 Specialist 时最容易埋的东西：
`technical` 是照着 `market` 抄的，两者都要上证收盘价，
各自起了个在**自己上下文里**最自然的名字。单看任何一个文件都挑不出毛病。

**修法不是删掉其中一个。** 想清楚这一点花的时间比写代码长：
两个 agent 从同一个源**独立**取值，不一致本身就是信息 ——
它说明两者看到的不是同一份数据，那时它们的结论没有共同基准。
删掉一个，就把这个信号也删了。

⇒ 把隐患变成探测器：

```python
# _contract/verdict.py
CROSS_CHECK_PAIRS = (
    ("market", "sh_close", "technical", "close", "上证收盘价"),
)
```

`risk` 逐对比较，不等就进 `missing`。而守卫**反过来**要求：
声明在表里的字段，必须出现在 risk 的核对清单里。

> 规则因此精确成一句：**重复是允许的，前提是有人核对。**
> 只写前半句，`CROSS_CHECK_PAIRS` 就变成一张「豁免名单」——
> 那是把守卫关掉，不是让它更准。

验证守卫真的会红（而不是自我感觉良好）：

```bash
$ sed -i 's/cross_check_conflict/xx_disabled/' skills/risk-check/scripts/risk_check.py
$ python3 -m pytest tests/test_field_single_producer.py -q
FAILED ...::test_声明的重复必须有人核对
```

### 坑 8 · 追加式存储会把手滑也一起永久保存

验证上面那条时，我写了个手工探针往库里塞两条 verdict。
跑了三次（前两次被契约挡下来：缺证据、stance 不在词表里 —— 契约在干活），
第三次成功。然后才想起来：**`BIGA_DB_PATH` 忘了设。**

`_store` 是追加式的，触发器禁止 `UPDATE` 和 `DELETE`。
那 6 行假 verdict（`task_id BIGA-20260921-900`）**永久留在真库里**。

追加式的好处一直被强调 ——「当时看到的」可重建。
这次看到了它的代价：**手滑也一样不可撤销**。

环境变量早就有，问题在于「记得设它」的唯一执行者是人的记性，
而记性正是这套设计要惩罚的东西。所以不是写进文档就完了：

```bash
tools/verify/probe.sh python3 - <<'PY'   # 库在 mktemp 里，退出即删
```

> 通用原则：当一个约定的**唯一执行者是人的记性**，
> 就把它做成默认路径，而不是写进文档再指望有人读到。

```
emotion    UNKNOWN  无法判定      technical  PASS     空头
```

🔴 **technical 是唯一 PASS 的** —— 它用的是已收盘的历史日线，

自证时间的源，在时间出问题时最稳。
