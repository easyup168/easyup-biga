# 第 48 章 · 独立复核撞见的漏网之鱼：合并进主分支的未清理冲突标记

> 📄 **过程** · 写完即冻结
> **覆盖**：审 `e-two` 分支（外部评审 E 节二：E-17/E-19/E-20）时发现的一个
> 独立缺陷——5 个文件里的 6 处冲突标记从未被真正清理，就被提交、并已经
> 存在于待合并的分支上｜**不覆盖**：E-17/E-19/E-20 本身的实现（那是另一个
> session 的工作，本章只记录复核过程中额外撞见的这一个）

## 目标 / 产出

| 产出 | 内容 |
|---|---|
| 清理 | `CLAUDE.md`、`README.md`（3 处）、`CHANGELOG.md`、`docs/guide/review-prompt.md` 里的 6 处遗留冲突标记 |
| `tests/test_docs_convention.py::test_没有未清理的冲突标记` | 新守卫：扫全部 `docs/*.md`，行首精确匹配 git 冲突标记的三种真实形状 |
| 测试 | 1532 → 1595（新增 19 条，等于当前被跟踪 `.md` 文件数） |

## 为什么这么做

### 1. 独立复核不是只读被检查方给的清单

复核 `e-two`（`176b819`，E-17/E-19/E-20）时，读它 rebase 到 `main` 之后的
`CLAUDE.md` 内容，第一眼就看见：

（下面故意各加一个前导空格，避免这份文档自己被本章新增的守卫抓到——
真实提交里那三行没有这个空格，顶格出现）：

```
 <<<<<<< HEAD
| 测试 | 1532 条 |
 =======
| 测试 | 1532 条 |
 >>>>>>> 2726832 (feat(contract,snapshot): 外部评审 E 节（二）……)
```

`git show 176b819:CLAUDE.md` 确认这**不是**工作区里的脏状态——标记是**已提交
的内容**。往下扫全仓，同样的三行标记出现在 5 个文件、6 处：`CLAUDE.md` 一处，
`README.md` 三处，`CHANGELOG.md` 一处（这一处两边内容真的不同，是两条不同
的 CHANGELOG 条目），`docs/guide/review-prompt.md` 一处。

其中 5 处的形状完全一样：**冲突两边内容恰好相同**（都是「1532 条」，因为
`sync_test_count.sh` 在两条分支上各自跑出了同一个数）。git 仍然会把这种
「文本相同、来源不同」判成冲突，需要人工确认；显然当时确认时**保留了两边
内容却删错了标记行**——这是手工解决冲突最常见的操作失误之一：编辑器里
看到三行标记夹着重复内容，删掉标记行本身，却不小心多删或少删。

### 2. 🔴 这类损坏没有任何自动防线——而这正是最值得记录的部分

`e-two` 自己报的「1532 条测试全绿、`audit_public.sh` 十一项全绿」是真的——
独立复核在他们的 worktree 上重跑过，确认无误。**但那两道闸门都没拦住这个
问题**：

- `pytest -q` 不解析 Markdown。冲突标记那几行不是 Python 语法，不影响任何
  测试的收集或执行。
- `audit_public.sh` 的十一项全部是"找特定形状的敏感内容"（密钥、路径、同机
  已有实例的可识别细节……）。冲突标记不属于其中任何一类，天然不在扫描范围内。
- `test_docs_convention.py` 现有的检查都是**子串/正则匹配特定内容**（类别头、
  测试条数、文件名格式），冲突标记行不巧不落在任何一条判据里。

三道闸门都真实跑过、真实报绿——**损坏的提交混进去了两轮**（先是 `e-two`
自己的第一次报告，然后是它 rebase 到 main 之后）才被人工用眼睛看出来。

> 通用原则：**「跑过测试」和「这条测试会检查这类问题」是两件事。**
> 一套守卫再多，覆盖不到的形状照样会被判成通过——这正是本项目反复强调
> 「守卫要拿真探针验证会红」的理由，这次撞见的是**判据覆盖范围**本身的空白，
> 不是某条判据写错了。

### 3. 判据要精确到 git 真实吐出来的形状，不能只看"像不像"

第一版判据是"行首是不是 7 个连续的同一字符"（`<`/`=`/`>`）。直接在真仓库
跑一遍就假阳性：`docs/design/architecture.md` 里的 RST 风格表格分隔线
（`============  ====================================  ============================`）
同样以 7 个以上的 `=` 开头，被误判成冲突标记。

git 真实吐出来的三行标记有精确形状：`<<<<<<<`/`>>>>>>>` 后面**永远**跟一个
空格加分支/commit 标签，从不裸出现；`=======` 相反，**整行只有这 7 个字符**，
不跟任何东西。把判据从"看开头像不像"改成精确匹配这个形状
（`^(<{7}( |$)|={7}$|>{7}( |$))`），表格分隔线不再命中。

## 执行

```bash
# 发现：确认标记是已提交内容，不是工作区脏状态
git show 176b819:CLAUDE.md | grep -n "^<<<<<<<\|^=======$\|^>>>>>>>"
# → 443:<<<<<<< HEAD / 445:======= / 447:>>>>>>> 2726832 (...)

# 全仓扫描已提交内容里还有几处
git grep -n "^<<<<<<<\|^=======$\|^>>>>>>>" 176b819 -- .
# → CLAUDE.md ×1、README.md ×3、CHANGELOG.md ×1、docs/guide/review-prompt.md ×1

# 清理后
python3 -m pytest -q          # 1595 passed
tools/verify/audit_public.sh --worktree   # 十一项全绿
```

## 坑

第一版判据（"行首是不是 7 个同字符"）在真仓库上假阳性——见上文第 3 节。
教训：**新守卫写完先在真仓库上跑一遍，不要只用手造的小样例验证**，
手造样例天然不会包含真实文档里那些"看起来像、实际是别的东西"的内容。

## 验证

```bash
python3 -m pytest tests/test_docs_convention.py -k "没有未清理的冲突标记" -q
# → 全绿（19 个已跟踪 .md 文件各一条）

# sabotage：往任意一份 docs/*.md 追加一段真实冲突标记，对应那条必须变红
printf '\n<<<<<<< HEAD\nfoo\n=======\nbar\n>>>>>>> feature\n' >> docs/README.md
python3 -m pytest "tests/test_docs_convention.py::test_没有未清理的冲突标记[README.md]" -q
# → FAILED，还原后重跑变绿
```

## 本章要点

| # | 要点 |
|---|---|
| 1 | 复核别人的分支时不要只信自复述的"测试全绿"——那是真的，但"全绿"覆盖不到的形状可能仍然是坏的 |
| 2 | rebase/merge 冲突两边内容恰好相同时最容易手工删错——标记行和内容行长得不一样，但人眼扫得快时会混过去 |
| 3 | 冲突标记对 Markdown 毫无阻力：不是语法、不是敏感内容、不落在既有正则里，三道闸门全部合法地视而不见 |
| 4 | 新守卫要用真仓库验证，不要只用手造样例——本仓库自己的 RST 表格分隔线就撞了第一版判据 |
| 5 | 发现一个新的"没有防线的形状"，直接补一条判据，比事后写一份检查清单更可靠 |
