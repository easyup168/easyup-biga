> 上一章堵的是「写入前不重新校验」这一个洞。这一章把洞往前挪了一层：
> **如果类型本身允许构造出非法状态，写边界重校验能防住的就只是"落库"这一个
> 出口，而不是"这个对象在内存里被谁看到"的每一个出口。** 冻结对象、
> 收紧字段身份、堵住一个 API 悄悄接受两种参数的口子——都是同一件事的变体：
> 让某些错误从「运行时可能发生」变成「类型层面构造不出来」。

## 目标 / 产出

做完这一章会得到：

- `MissingItem` 的身份（`==`/`hash`）从「文本」改成「机器可读代码」，
  同文本异代码的两条缺失项不再被回放路径悄悄合并成一条
- `AgentVerdict` / `DecisionCard` 变成真正不可变的对象——不仅赋值被拒绝，
  `.append()` 这类原地修改也从语法上不再可能
- `DecisionCard` 能区分「重复 agent」（结构性错误，硬拒绝）与
  「agent 缺席」（Phase 1/2 的常态）——但缺席不是无条件放行：`missing[]`
  条数必须不少于缺席 agent 数才放行，不比较任何文本内容，且在卡面上
  如实报出缺席名单（这条判据经过提交前两轮评审 F-6/F-8 才定型，见后文）
- 每张 Card 记录它用的判定原件指向 `agent_verdicts` 哪一行、当时长什么样，
  回放能核对「现在还认不认」
- `confidence` 改名 `data_completeness`——字段名第一次诚实地描述它在算什么
- 修订链不能跨 agent、不能跨决策、不能分叉；一个悄悄接受两个 id 又忽略
  其中一个的 API 被拆成两个不会混淆的 API
- A-I 建的毒行巡检第一次有了真实调用方，不再是一条不会跑的守卫

## 为什么这么做

### 一、`MissingItem` 的身份问题：改「基于什么判等」比听起来更容易踩到自己脚

设计文档 §2 追加 2 记的实测：`replay.py` 反推 `extra_missing` 时用
`m not in from_verdicts`。`MissingItem` 原来是纯 `str` 子类，没有覆写
`__eq__`/`__hash__`，于是两条**文本相同、代码不同**的缺失项——
`market.turnover.unavailable` 与 `supervisor.agent_no_response`，都在说
「数据源不可用」——会被判成同一条。合成阶段的 `card_ops.synthesize()`
用的是自己手写的 `f"{code}\x00{text}"` 复合键，不受影响；但 `replay.py`
直接用了 Python 的集合语义，两条会塌成一条，回放出的 Card **少一条缺失项**。
这是本项目最怕的形状：结论看起来完全合理（Card 依然渲染正常），只是
悄悄丢了一条本该在的信息。

第一反应是「把 `__eq__`/`__hash__` 改成比较 `.code`」，写完才发现事情
没那么简单：仓库里有至少 5 处测试直接拿 `.missing`（一列 `MissingItem`）
跟一份**纯字符串列表**比较（`assert v.missing == ["最高板"]`）。如果
`MissingItem.__eq__` 遇到非 `MissingItem` 的对象就回退到 `NotImplemented`，
Python 会按正常协议尝试反过来调 `str.__eq__`——而 `MissingItem` 本身
就是 `str` 的实例，`str.__eq__` 会直接比较字符内容，于是「回退」这条路
会不知不觉把旧的、基于文本的身份语义原样复活一份，藏在一个容易被忽略的
兜底分支里。

更麻烦的是 hash 一致性：如果 `__eq__` 在遇到纯字符串时肯放行（返回
`True`/`False` 都基于内容），而 `__hash__` 只看 `.code`，就会出现
"两个对象 `==` 为真，`hash()` 却不同"——这违反 Python 的数据模型契约，
后果是把它们放进同一个 `set`/`dict` 时可能各占一个桶，`in` 判断因此
出现两种互相矛盾的结果，取决于走的是哪条比较路径。这类 bug 极难复现，
因为它只在**混用**两种身份语义的地方才会现身。

⇒ 最终定的规则很硬：`__eq__` 对非 `MissingItem` 的输入**一律返回
`False`**，不给 `NotImplemented` 开口子。`__hash__` 只基于 `.code`。
这意味着 `MissingItem("x") == "x"`（跟裸字符串比较）不再成立——
代价是要去把那 5 处测试改成显式取 `.detail` 再比较。改的时候顺手确认了
一件事：`sorted(missing)` / `"某某" in m`（子串测试）/ `f"{m}"`
这三类现有代码里大量存在的写法完全不受影响，因为它们分别走 `str`
继承来的 `__lt__`、`__contains__`、`__str__`，从来不经过 `__eq__`/`__hash__`。
这也是当初把 `MissingItem` 做成 `str` 子类而不是普通 dataclass 的
理由仍然成立——只是「显示」与「身份」现在真正分开了，而不是共用同一个
文本信号。

### 二、A2 的「两步」不是修辞——少一步就是没堵上

`frozen=True` 单独看像是完整的修复，但上一章的 P1/P2 探针（`v.missing.append(...)`）
早就证明了它防不住什么：`frozen` 拦的是 `v.missing = [...]` 这种**重新绑定**，
不拦「对同一个可变对象原地修改」。`missing`/`evidence`/`warnings` 这几个
字段本身是 `list`，`frozen=True` 之后它们仍然是可以 `.append()` 的
list——只是那个 list 现在挂在一个不能重新赋值的属性名下而已。

⇒ 两步都要做：`frozen=True` 挡重新赋值，字段类型换成 `tuple`（没有
`.append()`）挡原地修改。`result` 字段是 `dict`，同样的道理，换成
`types.MappingProxyType`——它是一个只读视图，`result["x"] = 1` 直接
`TypeError`。

这里有一个容易漏掉的细节：`MappingProxyType(self.result)` **不复制**，
它只是包一层只读视图。如果调用方手上还留着原始那个 `dict` 的引用，
在构造 `AgentVerdict` **之后**又去改那个原始 dict，`self.result` 会跟着
变——因为它们本来就是同一块内存。这是同一类洞换了个入口：换成
`MappingProxyType(dict(self.result))`，先复制一份纯净的 dict 再包起来，
两者互不影响。

另一个交叉影响：`__post_init__` 里原来有好几处自我赋值——收敛
`missing`、补 `generated_at`、写 `identity_warning`/`restate_warning`。
`frozen=True` 之后 `self.x = y` 会直接报错，包括在 `__post_init__`
内部。修法是用 `object.__setattr__(self, "x", y)`——这正是 Python 自己
给 `@dataclass(frozen=True)` 生成的 `__init__` 内部用来完成首次赋值的
同一个后门，在构造阶段用它不违反「冻结」想表达的语义（对象构造完成后
不可变），只是把「构造完成」的判定权交还给写代码的人。

还有一处容易漏的收尾：`AgentVerdict.to_dict()` 里原来直接
`"result": self.result`。`self.result` 现在是 `MappingProxyType`，
而 `json.dumps` 只认 `dict` 的**子类**——`MappingProxyType` 实现了
Mapping 协议但不是 `dict` 的子类，直接塞进去会在真正落库（调用 `json.dumps`
的那一刻）才炸 `TypeError`，而不是在构造对象的时候。改成显式
`dict(self.result)` 就好，但这个坑值得记下来：**把一个字段的可变性
收紧之后，要重新检查所有序列化路径是不是隐含假设了「这就是一个普通
`dict`」**——类型收紧的影响面往往比字段本身更宽。

### 三、A5：为什么「拒绝重复」和「拒绝缺席」不能用同一套严格度

设计文档 §2 的评审断言复核里写着：「Card 现在允许同一个 agent 出现两次，
也允许只有 1 个 agent」，两条并列放在一起，读起来像是同一类问题。
动手之前先查了一下两者各自的历史：

**重复没有任何合法场景。** 一次决策里，同一个 agent 只会被 spawn 一次、
给出一条判定；如果 `verdicts` 里出现两条 `agent="market"`，无论是 bug
还是攻击，都没有一种读法能说清楚「该信哪一条」。这条可以直接硬拒绝，
且赋值成本很低——检查了现有测试，没有任何用例故意构造过重复 agent。

**缺席不是。** Phase 1 的 walking skeleton 就是单 agent 系统，那时候
「只有 1 个 agent」是**设计如此**，不是 bug；`ORCHESTRATION.md` 里现在
仍然写着完整的处理约定——某个 Specialist 掉线时，Supervisor 用
`--extra-missing supervisor.agent_offline "..."` 记录这件事，卡照常出，
只是缺失项里多一条。如果把「roster 不全」做成契约层的硬拒绝，会直接把
这条**已经在文档里、已经在正常使用**的失败处理路径炸掉。

动手之前先估了一下代价：`test_contract_behavior.py` 里几乎所有测试
用的都是「1 个 verdict、`missing=[]`」这种最小 fixture——因为它们测的
是别的东西（headline 校验、否决权、序列化往返……），根本不关心 roster
完不完整。如果把「roster 不全就必须有 missing」做成契约层的无条件规则，
这些测试全部要跟着改，而它们本来就不是在测 roster——这类大范围的
无关改动，往往是「判据加错了层」的信号，而不是「这个不变量真的该加」
的信号。

⇒ 拆成两条判据，各自的严格度对应各自的实际风险：

| 判据 | 严格度 | 理由 |
|---|---|---|
| 重复 agent | `__post_init__` 硬拒绝（新卡）/ 警告（旧卡） | 结构性错误，从不合法 |
| agent 缺席 | 只读属性 `absent_agents` 报告事实 | Phase 1/2 的常态，已有正确的处理路径 |

"已建成的 roster" 拿什么当权威源也想了一圈：`STAGE1_AGENTS`/`STAGE2_AGENTS`
包含 `discipline`（裁定 13 故意不建），直接拿它当"已建成"的清单会带进
一个从不出现的 agent；而 `tests/_consistency.py::built_agents()` 扫的是
`agents/` 目录，是纯测试侧的工具，不该被生产代码 import。最后发现
`STANCE_VOCAB` 的 key 集合已经被一条现成的测试
（`TestStanceVocabMatchesContracts`）钉死等于 `built_agents()`——直接
复用它，不用再开第三份「谁是已建成的 agent」的清单。这正是
`dev-workflow` 第五问要防的形状：一份清单在别处已经有权威答案，
不该自己再手抄一份。

### 四、A6：核对逻辑必须验证过「不会踩中上一批已经踩过的坑」

`VerdictRef` 本身的设计不难——`(agent, verdict_id, content_sha256,
contract_version)`，Card 多记一份「这条判定我是从哪一行读出来的」。
真正需要小心的是**核对逻辑**，因为设计文档 §2 追加 4 已经把这里的
一个坑明确钉死了：批 A-I 把 `verdict_json` 换成了 `_canonical_dumps`
（带 `separators`），同一份 `AgentVerdict` 序列化出来的字节从 206 变成
185——也就是说这个序列化格式**从建库以来就已经变过一次**。如果
`verify_verdict_refs()` 的实现是「把 `AgentVerdict.from_dict()` 读回的
对象重新序列化，再跟 Card 上记的哈希比对」，A-I 之前落库的 239 条原件
会**集体核对不上**，而且失效是静默的——两串 sha256 都长得完全正常，
只是对不上，没有任何报错指出「这是因为序列化格式变了，不是数据本身有问题」。

正确做法反而更简单：`agent_verdicts.content_sha256` 这一列本来就是
写入时对**当时那段 blob 文本**直接算的哈希，核对时原样取回来跟 Card
上记的值比对，不重新计算、不重新序列化。`tests/test_write_boundary.py::
TestVerdictContentShaIsHashOfStoredText`（A-I 已经写好）已经把「正确
答案是什么」钉死为一条独立测试，A6 直接复用它的判据，没有另写一套。

顺带发现一个命名上的小陷阱：仓库里早就有一个「`verdict_ref=NN`」的
stderr 约定——skill 落库后打印这一行，agent 拿这个整数 id 传给下一步。
这是个裸 `int`，跟 A6 新增的 `VerdictRef`（一个带 4 个字段的值对象）
说的是同一类东西（都指向 `agent_verdicts` 某一行），但不是同一个符号。
两者在同一个仓库里长期共存，容易在读代码时搞混，专门在 `verdict_ref.py`
模块开头写清楚了区别——这不是能靠改名彻底避免的事（`verdict_ref=NN`
这个约定已经写进好几份 `AGENTS.md`，这一批不能碰它），只能靠写清楚
文档降低混淆概率。

### 五、A7：一个看似只是改名的字段，实际驱动了什么

`confidence` 这个名字暗示了一件从没发生过的事——六个 skill 里它全部是
`len(result) / _EXPECTED_FIELDS`，纯粹的字段覆盖率，跟"模型有多大把握"
毫无关系。改名本身机械（6 个 skill 的构造调用 + 十几处测试），唯一
需要设计的是向后兼容：`from_dict` 双键兼容，`data_completeness` 优先，
读不到就退回 `confidence`——这样历史卡不需要任何迁移脚本就能继续读，
新代码写的字段名开始变得诚实。

顺手做了一件配套的事：既然 A6 引入了 `contract_version`（描述"契约
形状的版本"），这次改名恰好是第一个真正改变了序列化输出**含义**的
契约层变更——`CONTRACT_VERSION` 就定在这一批，取值 `"contract/1"`，
参照的是仓库里已有的 `SYNTHESIS_VERSION` 那套先例（组装逻辑变了就
+1，这里是契约形状变了就 +1）。

### 六、A8 撞上了一个没预料到的连锁反应：schema 版本号被提前占用

`save_verdict(amends=...)` 加两条校验很直接：修订必须指向一条真实存在
的原件、且 `task_id`/`agent` 都要跟原件一致。真正让人多想了一步的是
「线性修订」——一条原件最多被修订一次，不许分叉。第一反应是在应用层
「先查这个 id 有没有被修订过，没有才写」，但这正是 `reserve_decision_id()`
已经用血的教训写在自己文档里的反例：先查后写中间有窗口，两次并发的
`save_verdict` 调用都可能查到「还没被修订」，然后都写成功，仲裁失败。
唯一可靠的办法是数据库自己的唯一约束。

于是要建一条新索引——而新增任何 DDL 都意味着 `SCHEMA_VERSION` 要往前
挪一位。查了一下当前最新版本，是 A-I 之前就有的 v5。给它分配 v6 的
时候才想起来：设计文档里"批 B"那一段写的是"schema v6：decision_runs /
run_events / evidence_sets"——批 B 还没开工，但它已经在文档里"预订"了
v6 这个编号。`schema.py` 自己的规则是"迁移列表只许在末尾追加，不许
改动已发布的条目"——已经落进这一批的索引不能让位，只能把设计文档和
分发提示词里"批 B 是 v6"这句话改成"v7"。这是一次纯粹的**编号级联**，
不是重新设计批 B，但如果不在这一批就改掉那两处文字，批 B 开工的人会
带着"我要建 v6"的预期去动手，撞见 `SCHEMA_VERSION` 已经是 6 才会
发现问题——那时候要么现场改设计文档（分心），要么已经写了一半代码
才发现编号对不上。提前改掉，成本几乎为零。

`load_card` 拆成 `load_online_card`/`load_card_by_record_id` 两个 API
是同一批里最"无聊"但最费体力的一处——不是设计难，是要把全仓 9 个
调用点一个个过一遍，确认每一处原来传的是 `decision_id` 还是
`record_id`，然后换成对应的新函数名。之所以值得做：原来的
`load_card(decision_id, *, record_id=None)` 一旦两个参数都传，
`record_id` 说了算、`decision_id` 被静默忽略——这正是"看起来在校验，
其实那个校验从没发生"的形状，而这类 API 设计上的模糊性不会在类型检查
或者 lint 里报出来，只能在读代码或者踩坑时发现。拆成两个不同名字的
函数之后，调用者被迫在写代码的那一刻就想清楚"我到底想按哪个 id 查"，
这种模糊性从**签名层面**就消失了，不需要指望每个调用者都记得那条
隐藏规则。

### 七、F-4：接一个真实调用方，同时不能把两种"红"混为一谈

A-I 建的 `readback_check.py`（毒行巡检）只有测试和文档，从来没有任何
自动路径会跑它——这正是 `architecture.md` §9 反复强调的"零消费方"
模式：写了检查，但没人真的在问它。接进 `bin/biga-card`，紧挨着已经
接好的 `spawn_check`（同样只读、同样是"唯一每次出卡都会跑到的地方"），
逻辑上很顺。

真正要想清楚的是退出码。`spawn_check` 当年就在这里栽过一次——调用在，
`$?` 没被接住，脚本用 `set -uo pipefail`（没有 `-e`），于是无论
`spawn_check` 返回什么，`bin/biga-card` 都无条件继续到 `exit 0`。
这次要避免同一个坑：`READBACK_RC=$?` 老老实实接住。

但接住退出码之后，下一个问题是：**它该跟哪个信号共用，还是该有自己
的信号？** 毒行巡检发现的行，一定是**比这次运行更早**落库的——A3 的
写边界重校验已经保证新写入的行不可能再变成毒行。也就是说 readback_check
报红这件事，跟"这次出的卡本身有没有问题"是两个不同维度的信息：
这次的卡可能完全正常（`spawn_check` 已经证明 Specialist 真的被调用
过），而库里某个更早的角落有一条历史遗留的坏行。如果让这两种情况
共用同一个退出码（比如都用 `spawn_check` 已经在用的 `4`），使用者
会把"库里有历史包袱"误读成"这次的证据链断了"，排查方向直接错。

⇒ 用一个独立的退出码 `6`，摘要文案也明确写"与这次出卡无关"。这是
`architecture.md` §9 L-13 的另一个变体——不是"守卫查的地方不对"，
而是"两种不同性质的红，如果共用同一个退出码，读者会没法区分它们"。

### 八、提交前自评审挑出两条：F-5（这一批自己开的口子）

这一批八项做完、CHANGELOG 与探针记录都写好之后，没有直接自称"通过"，
而是把 diff、探针红灯输出、"自己觉得最可能被攻击的地方"这三样交给一次
独立的评审——`docs/guide/orchestration-kickoff-prompt.md` 定的流程本来
就要求这一步，不是事后补的仪式。评审第一条就打回来：`MissingItem.code`
"冻结"之后仍然能被 `m.code = "换一个值"` 改掉，不报任何错。

回头查才看清问题出在哪：A2 那次"把所有契约对象都冻结"，动手方式是
`@dataclass(frozen=True)` 加在 `AgentVerdict`/`DecisionCard` 类定义上——
但 `MissingItem` 从来不是用 `@dataclass` 写的，它是 `str` 的子类，靠
手写的 `__new__` 构造（这是为了让它同时能当字符串用，`f"{m}"`/`in`/
`sorted()` 全部免费继承）。A2 的整改是"找到所有 `@dataclass` 的地方
加 `frozen=True`"，这个动作在语法上根本不会碰到 `MissingItem`——它不
在"所有 dataclass"这个集合里，却在直觉上完全应该被这一批"冻结所有
契约对象"的意图覆盖到。`TestVerdictFrozen` 当时测的是**容器**层面
（`missing` 是不是 tuple、`.append()` 是不是被挡住），从没测过"容器里
那个元素自己"能不能被改字段——同一个批次里两类不同的"不可变"，
只覆盖了一类，而这一类恰好是 A1 刚刚用来立身份保证的那个字段。

修法很直接：给 `MissingItem` 补 `__setattr__`/`__delattr__`，统一抛
`dataclasses.FrozenInstanceError`——不新造异常类型，让所有契约对象
冻结失败的报错长一个样子。构造阶段（`__new__` 内部）用的是
`object.__setattr__`，不经过这道覆写，不受影响。

> 这条坑的教训是：**"把所有 X 都做成 Y"这种整改，判据必须是"属于
> 这个意图的东西"，而不是"能被同一个语法关键字捕捉到的东西"**——
> 当一个对象因为别的理由（这里是"要当字符串用"）没有采用团队默认的
> 构造方式时，它会从语法层面的批量扫描里隐身，但不会从产品意图里隐身。

### 九、提交前自评审挑出两条：F-6（设计表格说的和代码做的不一致）

第二条更麻烦，因为它不是"代码有 bug"，是"设计意图本身没讲清楚"。
上面第三节写的是这一批**最初**的判断：缺席不硬拒，只用 `absent_agents`
报告事实。评审翻出设计文档里那张判据表格，指出表格字面写的是"缺席
也应报红"，跟实现选的"缺席永不硬拒"对不上——**这不是一个能靠继续读
代码解决的分歧**，是当初设计这条表格的人和当初写这段实现的人，脑子
里想的其实是两件不完全一样的事，只是都叫"处理缺席"。评审报告里原话
类似"我同意这不是能靠读代码单方面裁定对错的东西，需要往上交"——
评审没有替设计做决定，而是准确指出了这一点该往上交给谁定，这本身就是
评审该做的事。

评审同时挑出第二个、独立的问题：`absent_agents` 这个属性算出来了，
但**没有任何代码读它**——不在 `render()` 里，不在任何校验分支里，
是个纯粹的"零消费方"（`architecture.md` §9 L-1）。这条不需要往上交，
是能直接判定对错的：算出来的事实如果没有任何读取路径，跟没算等价，
先补上"缺席"这一行接进卡面渲染，这部分不等评审结论，直接修。

往上交之后拿到的裁决是折中方案：roster 不全、且 `missing[]` 完全为空
⇒ 拒绝；roster 不全但 `missing[]` 非空（哪怕只有一条，且不要求这条
missing 精确对应哪个缺席的 agent）⇒ 放行。「不要求精确对应」是刻意
加的限定——`missing` 项的代码前缀是**发起方**的命名空间（`market.*`/
`supervisor.*`……），不是缺席 agent 的名字，想靠字符串匹配去猜"这条
missing 说的是不是那个缺席的 agent"，是 `architecture.md` L-13 早就
点名过的「按字符串形状分类」陷阱——判据只问"有没有解释"，不问
"解释得准不准"，后者交给人看卡面上如实列出的缺席名单自己判断。
新判据被要求复用 `_check_roster` 已有的 `from_store` 三段式（新卡
严格拒绝、历史卡/回放只警告），不允许为这一条新开一套宽严规则——
"一张卡里已经有的判据模式，新判据要先证明用不了，才有资格另起一套"。

真正花时间的是修完设计之后的收尾：`test_contract_behavior.py` 等
五个测试文件里，凡是构造 `DecisionCard` 时图省事只给一个 agent、
又完全不关心 roster 完不完整的最小 fixture（这类写法在批 A-II 刚提交
评审时已经有几十处），全部要么补成"满 roster"、要么显式给一条占位
`missing`，二选一——这是纯粹的机械劳动，第三节里估过的"代价与收益
不成比例"的顾虑，在这一步变成了要不要付这笔代价的真实账单，只是账单
落在了自评审之后，而不是最初设计的时候。

> 这条坑的教训是：**设计表格与代码实现，即使出自同一个人同一次
> 提交，也可能在"这句话到底是什么意思"上悄悄分叉**——评审存在的
> 意义之一，就是在这种分叉被合并进主线、变成既成事实之前把它截住；
> 而截住之后该不该改、怎么改，有的能直接读代码判定（零消费方），
> 有的必须交回设计层面裁决（严格度本身的分歧），把两者混为一谈，
> 要么会把该升级的问题自己拍板了，要么会把能立刻修的小问题也拖着
> 等审批。

### 十、F-6 交出去定完之后，又被追问了一句"这个口子多大"：F-8

F-6 定下"有解释就放行"之后，把结果再交出去问了第二意见——这次的
问题不是"该不该拒"（那件事上一节已经定了），而是"这条判据本身够不够
严"。对方直接给出了一个能复现的攻击场景：5 个 agent 静默缺席，
随便挂一条跟它们毫无关系的 `missing`（比如某个数据源自己超时的报告），
一样能通过，因为判据从头到尾只问"missing 是不是非空"。**一条解释能
给任意多个缺席背书**，这是 F-6 版本没意识到的口子。

第一反应是"那是不是又要回到'精确对应哪个 agent'那条被否掉的路"——
但对方指出还有第三条路，既不比较文本、又不是"随便一条就够"：**计数**。
缺席几个、就至少要有几条 missing——不要求内容对应，只要求数量对得上。
这条信号此前一直没被用上，是因为脑子里把"避免按字符串形状分类"
和"不能用任何形式的数量约束"当成了同一件事，其实两者无关：计数
判据完全不看 missing 里写了什么，天然免疫 L-13 那类陷阱。

改完判据本身只是一行——但重新跑测试发现，F-6 那一轮"给一条占位
missing"的收尾方式，这次全数不够用了：`test_contract_behavior.py`
另外还有 6 处用"1 个 agent + 1 条 missing"构造 Card 去测别的东西
（铁律 2、否决权、`.append()` 被拦……），F-6 那一轮因为只要求"非空"，
1 条占位 missing 就混过去了；F-8 一收紧，这些用例全部要么把占位
missing 凑够 5 条（内容注水，可读性变差），要么换一种更干净的思路——
干脆给满 roster，让 `_check_roster()` 直接跳过判断，把"注意力"完全
让给这条测试真正想验的那条检查。后者显然更好：新增了一个
`_roster_with_verdict(v)` 助手（满 roster，但指定 agent 的判定换成
调用方给的那一条），比"数够 5 条占位文本"更接近"这条测试根本不关心
roster"的本意。

修的过程中还顺手撤销了一处误伤：`test_缺失项必须上浮到Card` 一开始
也被当成"需要满 roster"处理了，改完才发现它测的是**更早**一步的检查
（`__post_init__` 里"缺失项必须上浮"那道校验排在 `_check_roster()`
之前），根本轮不到 roster 判据介入，之前的改动是多余的，撤销回最初
的单 agent 写法。

> 这条坑的教训是：**"够不够严"和"该不该管"是两个独立的问题，可以
> 分两轮问**——F-6 先定了"该不该管"（缺席要不要拒），F-8 才问"管得够
> 不够"（拒的判据本身松不松）。同一轮里把两个问题一起抛出去，容易
> 因为第一个问题的讨论压过第二个，把"这个方案本身有没有隐藏的口子"
> 这件事顺带放过去。另外：**修复引入的收尾模式（这里是"给一条占位
> missing"）本身也可能在下一轮判据收紧后失效**——不能假设一次评审
> 定的收尾方式能一直沿用，每次收紧判据之后都要重新过一遍受影响的
> 测试，而不是想当然地"多加几条占位"了事；顺手检查每一处改动是不是
> 真的用得上，改错的地方要撤销，不要让"顺手改的"和"真正需要改的"
> 混在同一次改动里分不清楚。

## 坑

### 坑 1：`__eq__` 返回 `NotImplemented` 会触发一条不容易想到的回退路径

第一版 `MissingItem.__eq__` 对非 `MissingItem` 的输入写的是
`return NotImplemented`，理由是"这是 Python 处理不可比较类型的标准
做法"。写完之后跑现有测试，`.missing == ["纯文本"]` 这类断言全部
仍然通过——一开始以为是好事，检查了一下才发现是坏事：`MissingItem`
本身是 `str` 子类，`NotImplemented` 会让 Python 反过来尝试
`plain_str.__eq__(missing_item_instance)`，而这条路径走的是 `str`
的默认实现，直接比较字符内容——等于新写的"基于 code 判等"完全没有
生效，只是换了个隐蔽的路径把旧行为原样保留了下来。改成对非
`MissingItem` 输入无条件返回 `False`，那 5 处测试才第一次真的转红，
逼着把它们改成显式取 `.detail`。

> 这条坑的教训是：**改一个类型的相等性语义时，"现有测试还是绿的"
> 不能当成"改对了"的证据**——尤其是涉及继承关系的时候，回退路径
> 可能悄悄绕过新逻辑，而不是触发它。

### 坑 2：`test_同一条原件不许被修订两次` 探针失败时报出的是一个不熟悉的异常

验证 schema v6 的唯一索引时，临时删掉 `CREATE UNIQUE INDEX` 那一行，
预期是"第二次修订成功、断言失败"，实际看到的是一次干净的
`Failed: DID NOT RAISE`——符合预期。但验证 A8 的应用层代码校验时
（临时删掉 `save_verdict` 里 agent/task_id 一致性检查），
`test_amends指向不存在的原件被拒` 转成了裸的
`sqlite3.IntegrityError: FOREIGN KEY constraint failed`，而不是原来
预期的、缺失校验导致的"没报错"。这其实是件好事：说明这条代码级校验
不是纯装饰——它在**外键约束报错之前**先一步给出人能看懂的提示，
删掉它之后底层约束仍然兜底，只是错误信息变得难看。两种"红"都确认了
各自要保护的东西确实在起作用，只是形状不完全是最初设想的那样。

### 坑 3：F-4 探针顺带挖出一个跟这次改动完全无关的旧毛病

验证 `bin/biga-card` 的退出码 6 时，沙盒跑出来的 stderr 里混着一段
`StoreNotInitialised` traceback——`_sql()` 那个辅助函数在
`data/biga.db` 还不存在时，用 `readonly=True` 去查
`SELECT MAX(decision_id)`，触发了 `connect()` 早就设计好的
"库不存在就报错"分支。这条异常没被接住，直接打到 stderr，但因为
`$(...)` 只捕获 stdout，`BEFORE` 变量最终拿到一个空字符串——语义上
**恰好是对的**（"还没有任何决策"），所以脚本继续正常运行，不影响
任何功能。这是一个跟本批任何一项都无关的旧毛病（`bin/biga-card`
本来就有，只是沙盒测试第一次把它跑了出来），记进了 `TODO.md`，
没有顺手改——CLAUDE.md 说得很清楚，想到了就记下来，不要在验证
一件事的过程中顺手动另一件事的代码，那样出问题时分不清是哪个改动
导致的。

### 坑 4：F-6 改完设计判据之后，测试炸出来的范围比估计的大一圈

改完 `_check_roster()` 的判据之后跑全量测试，第一次看到的失败数是
两位数，分布在 5 个测试文件里——比第三节动手前估的"几十处"还是
超了一些，因为除了 `test_contract_behavior.py` 自己那些，`test_
decision_card.py`/`test_verdict_provenance.py`/`test_verdict_refs.py`/
`test_write_boundary.py` 里也各自有几处独立写的最小 fixture，彼此
互相不知道对方的存在。逐个修的时候踩到一个需要小心的细节：`test_
write_boundary.py::test_BUY卡事后被塞入缺失项会被拒` 原来的最小
fixture 只给 1 个 agent——直接补一条占位 `missing` 在这里行不通，
因为它测的card 是 `status="BUY"`，铁律 2 本来就要求 BUY 卡的
`missing` 必须是空的；补 `missing` 会先撞上铁律 2，压根走不到这条
测试真正想测的"事后被塞入缺失项"那一步。唯一自洽的修法是把这个
fixture 改成真的给满 6 个 agent 各出一条判定，让 `absent_agents`
本身为空，这样"roster 不全"这个前提从根上不成立，不需要靠 `missing`
去豁免。

> 教训：改一条判据后，"给这个测试补一条占位 missing"不是万能修法——
> 得先看这个测试本身还依赖哪些别的约束（这里是铁律 2），两个约束
> 可能互相冲突，冲突时能同时满足两边的往往是"把 fixture 补完整"，
> 不是"找一条绕过去的近路"。

## 本章要点

| # | 要点 |
|---|---|
| 1 | 改一个类型的相等性语义时，「现有测试还是绿的」不能当证据——继承关系可能让回退路径悄悄绕过新逻辑，必须去查回退路径本身走了哪条分支 |
| 2 | `frozen=True` 只挡重新赋值，挡不住原地修改可变字段——`list`/`dict` 必须同时换成 `tuple`/`MappingProxyType`，两步缺一步就等于没堵上 |
| 3 | `MappingProxyType(x)` 是视图不是拷贝——不先 `dict(x)` 复制一份，调用方对原始对象的后续修改会透传进来，是同一个洞换了个入口 |
| 4 | 收紧一个字段的可变性之后，要重新检查所有序列化路径——`json.dumps` 不认 `MappingProxyType`，这类问题会在落库那一刻才暴露，而不是在构造对象的时候 |
| 5 | 两条看起来很像的「结构不完整」问题，宽严可以完全不同——重复没有合法场景该硬拒绝，缺席则要看有没有显式解释，不能用同一把尺子（这条严格度本身后来被评审 F-6 改过一次，见要点 13） |
| 6 | 核对逻辑设计时，先去读「上一批留下的约束」——序列化格式是否被冻结，直接决定核对该比对存量值还是重新计算，选错会让历史数据静默核对失败 |
| 7 | 「已建成的清单」优先复用一份已经被测试钉死跟权威源一致的现有常量，不要因为它不是为这个用途设计的就另开一份新的 |
| 8 | 新增任何 DDL 都要检查 schema 版本号有没有被设计文档「预订」过——迁移列表只许追加不许改动已发布条目，占用冲突要靠改文档编号解决，不能倒过来改代码 |
| 9 | 一个 API 同时接受两个 id 参数、其中一个被静默忽略，是一种从签名层面就无法被 lint 或类型检查发现的模糊性——拆成两个不同名字的函数，让调用者在写代码时就被迫想清楚 |
| 10 | 两种性质不同的「红」（这次运行的问题 vs 历史遗留的问题）不能共用同一个退出码，否则读者会把后者误读成前者，查错方向 |
| 11 | 探针暴露的问题不一定是探针本身要验证的那个不变量——有时候会顺带挖出一个完全无关的旧毛病，记下来但不要在验证的过程中顺手改掉它 |
| 12 | 「把所有 X 都做成 Y」这类整改，判据要按「属于这个意图」来找，不能只按「能被同一个语法关键字扫到」来找——不用团队默认构造方式（这里是继承 `str` 而非 `@dataclass`）的对象会从批量扫描里隐身，但不会从产品意图里隐身 |
| 13 | 设计表格与代码实现即使出自同一次提交，也可能在具体严格度上悄悄分叉——分叉发现后，「零消费方」这类能直接读代码判定对错的问题可以直接修，但「该多严格」这类分歧要老实交回设计层面裁决，不能替设计做主 |
| 14 | 提交前的自评审是这一批设计流程的一部分，不是可选的收尾动作——本章三条最大的修正（F-5/F-6/F-8）都来自这一步，且都发生在代码第一次进入版本历史之前 |
| 15 | 「不比较文本」和「不能用数量约束」是两件不相关的事——避免按字符串形状分类（L-13）挡的是"猜文本对应关系"，不挡"数一数条数"，计数判据能在不重新引入文本匹配的前提下把判据收紧 |
| 16 | "该不该管"和"管得够不够"可以是评审的两个独立回合——同一版设计可能第一轮只被问到前者；判据收紧后，上一轮引入的收尾模式（这里是"给一条占位 missing"）要重新过一遍受影响的测试，不能假设它还够用 |
| 17 | 顺手改的地方如果发现其实不需要改（这里是 `_check_roster()` 之前就会拦下的检查），要撤销回原样，不要因为"已经改都改了"就留着——分不清哪些改动是必要的，会让下一次排查变困难 |
