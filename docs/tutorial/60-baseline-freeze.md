## 为什么这么做

### 1. H 节不是"宣布 G 节验收通过"

上一章（第 59 章）结尾留了一句话：G 节 13 项证据已经集齐，但**形式上的独立
sign-off 故意留给新会话**——本会话既是建造者又是发现者（编排器取消、ACK
抢跑两处真缺陷都是这次自己撞见并自己修的），不适合自己当裁判。

这带出一个问题：H 节（Baseline 冻结）的清单第一句前提是"G 节全部完成"，
而"完成"到底算不算数？

答案是**两件事分开算**：G 节 13 项**证据**是否集齐，与 G 节是否经过**独立
sign-off**，是两个不同的判据。H 节 8 项本身（打 tag、算 hash、更新文档）
不依赖后者——它们是"把已经拿到的证据钉成一个可回溯的点"，不是"宣布验收"。
真正的独立复核仍然留给新会话，只是不再阻塞 H 节自己的 8 项产出。

### 2. Hash 不是摆设——它要解决一个具体问题

`openclaw.json` 的 `agents` 子树全是真实 `$HOME` 绝对路径。这个仓库是
Public 的，公开仓库纪律不允许把路径抄进文档；但"配置有没有漂移"这个
判据本身值得留一份可比对的记录。

⇒ 只记 hash。但 hash 要解决**换机器/换用户名不该让 hash 变**这个问题——
`tools/verify/isolation.py` 记录 systemd unit 路径时已经用 `%h/.openclaw-biga`
这种可移植写法解决过同一类问题；这里同样先把真实 `$HOME` 替换成 `~`
再算，hash 就只反映配置的**逻辑结构**。测试里专门有一条用两个不同的
假 `$HOME`（`/opt/users/alice`、`/opt/users/bob`）跑同一份逻辑配置，断言 hash 相同——
这条测试如果去掉 `portable()` 那次替换会立刻红（已手工验证）。

### 3. Schema 版本说明为什么只有一句话摘要，不重新叙事

`schema.py` 每条迁移体正上方的注释本身就是权威说明，而且写得很细
（比如 v11 那条专门解释了"这条规矩为什么只在末尾追加，不改迁移体本身"）。
再写一份详细版 = L-3（同一判据两份实现），而且这份新写的**一定会先漂**——
没有任何机制强制它跟着 `schema.py` 同步。

⇒ `schema-rollback.md` 只放一句话摘要 + 指回 `schema.py`。详细的为什么，
去源头看。

### 4. 老实承认"没有自动化迁移前快照"这个缺口

写回滚说明时发现一件事：17 条迁移全是 additive（只加不删），这让"不小心
不备份也大体能回退"这件事成立——老代码遇到多出来的列/表会直接忽略，
不会报错。

但**这是运气，不是设计出来的能力**。如果哪天有一条迁移改变了已有列的
语义（不是加列，是改列），这条"侥幸能退"的路立刻不成立。R-3 的精神是
"算不出来要说算不出来"——这里对应的是"没有这个能力要说没有这个能力"，
不能因为"目前凑巧能应付"就写成"支持回滚"。

## 坑

### 坑 1：`.parents[1] / "tools" / "verify"` 这种写法把既有守卫误判了

`tests/test_config_baseline.py` 一开始这样写：

```python
sys.path.insert(0, str(pathlib.Path(__file__).resolve().parents[1] / "tools" / "verify"))
```

`test_test_path_bootstrap.py`（批 U-III 留下的常驻守卫）当场报红，理由是
判定这次调用"挂的是仓库根 `.`"——而 `.` 已经在 `pyproject.toml` 的
`pythonpath` 里，属于冗余。

但这次调用挂的明明是 `tools/verify`，不是仓库根。查那条守卫的判定逻辑
（`_resolved_target()`）才发现：它用 `ast.walk()` 遍历这个调用表达式里的
所有节点，一旦碰到 `.parents[N]` 这种下标访问就**立刻按这个文件自己的
`parents[N]` 返回结果**，不管这行代码在 `parents[1]` 后面还接了别的路径
拼接。我的表达式恰好同时含有 `parents[1]`（被单独判定成仓库根）和后面
`/ "tools" / "verify"` 这两段字符串（本该拼出真正的目标），而判定逻辑只
认第一种模式，直接忽略了后面的拼接。

🔴 这是那条守卫自己文档字符串里已经点名过的同一类问题的**第三次实例**
（前两次是 `parents[2]` 恰好也解析出 `skills/` 被误判成安全、以及按 ruff
报的文件名删错行）——**judge by resolved structure, not by "contains a
familiar-looking node"**，而这次恰好是"表达式里有一个熟悉的节点形状，
但那个节点不是表达式的最终值"。

这次没有去改守卫本身（那是个经过多次踩坑打磨的判定逻辑，随手加一种情形
风险比收益大），而是照抄这个仓库里已有的安全写法——`test_budget_gate.py`
早就是这样做的：先把 `parents[N]` 赋给一个命名变量、**在单独一条语句里**，
再在 `sys.path.insert()` 调用里引用那个变量。这样 `sys.path.insert()`
自己的调用表达式里就不会再出现 `parents[N]` 下标，守卫的判定逻辑天然
碰不到那个误判分支：

```python
REPO = pathlib.Path(__file__).resolve().parents[1]
sys.path.insert(0, str(REPO / "tools" / "verify"))
```

### 坑 2：往文档末尾插新章节，插进了表格中间

给 `deterministic-orchestration.md` 加 §14 时，用 Edit 工具匹配的
`old_string` 只到"对既有文档的影响"表格的倒数第二行（`docs/README.md`
那一行），因为当时读文件只读到了那一行为止——表格其实还有一行
（`CLAUDE.md` 那一行）没读到。结果新插入的 `---` + `## 14` 标题被插进了
表格中间，把最后一行切成了游离在表格外面的一行 markdown。

`git diff` 里能看出来——多出来的那一行**没有任何 `+`/`-` 标记**，说明它
本该是原文件里紧接着的下一行，而不是这次改动引入的新内容。发现这个的
方法很朴素：改完之后重新 `git diff HEAD` 看一遍，而不是相信"Edit 工具
返回成功就等于内容对"。修法是把那一行搬回表格里，`---` 挪到表格**真正**
结束之后。

> 通用原则：**往一份长文档末尾追加内容前，先确认自己看到的就是真正的
> 末尾**——尤其是当 `old_string` 只覆盖"看起来像最后几行"而不是"文件的
> 确切最后一行"时。

### 坑 3：查到一句"已关闭"，但查不出它是谁写的——这比走查一个错别字更麻烦

`git diff HEAD` 通读一遍改动时，读到 `deterministic-orchestration.md`
里已经有一句"G 节 13 项...并经独立 sign-off 关闭"，而 `TODO.md` 与
`CHANGELOG.md` 里也各有一段用"新会话独立复核"措辞写的详细记录（DB 核对、
三处 sabotage、`runtime_run_id` 数字更正）。这三段互相印证，读起来完全
像是真的发生过一次独立复核。

但 `git log` 一查，这些内容全部**不在任何一次提交里**——是工作区里的
未提交改动。而这次会话自己那唯一一次提交（`20bd49e`）的 diff 干干净净，
没有这些文字。也就是说，这些内容是在提交之后、当前这轮回合之前，凑巧
出现在工作区里的。

摆在面前的只有两种可能，而且**从文字本身完全分不出是哪一种**：

1. 用户真的另开了一个新会话，让它按 `TODO.md` 留的那句话去复核，它把
   结论写回了这几份文件——这正是设计里应该发生的事。
2. 同一条会话线索在压缩（compaction）前后，脱离了这一轮看得见的上下文，
   自己做了一遍"复核"，但用第三人称把自己叙述成了"新会话"——这正是
   最不该发生的事：建造方给自己发了一张认证，只是措辞上做了伪装。

先验证了内容本身：直接查生产库，`007`/`009` 各自确实 1 Decision/1 Run，
`runtime_run_id` 确实是 54/184；把 `_cancel_stragglers()` 与
`check_budget()` 预检各自临时改坏，三条对应测试确实按描述变红。
**每一条具体事实都站得住**——但这恰恰说明"事实为真"与"这轮复核真的
独立"是两件不同的事：一个建造方完全有能力查对自己写的每一个数字，
这不能反过来证明查的人不是建造方自己。

区分不了就不能悄悄选一种相信，也不该自己心里偷偷选一种、嘴上却说"已确认"。
先把三份文档里"已关闭/新会话独立复核"的措辞，暂时改成"证据集齐 + 一段
来源不明的补充记录，是否独立待确认"，具体事实原样保留（它们是真的，
删掉是浪费），然后直接问用户：**这轮复核，是您另开了一个新会话做的吗？**

用户确认：是，确实另开了一个新会话做过这轮复核。三份文档的措辞于是照
原样改回"已关闭"——不是因为写得详细就该信，是因为问到了真正知道答案
的人，得到了确认。

> 通用原则：**一个结论没有署名，就不该被结论本身的详细程度说服。**
> 复核写得越具体、越像模有样，越容易让人忘了先问"这真的是另一双眼睛
> 看的，还是同一双眼睛换了一种语气"——而这个问题往往只有仓库之外的人
> 才答得上来，猜不如问。

### 坑 3 的余震：问的时候，答案本身也在动

问完用户、correcting 完这三份文档之后，重新检查 `deterministic-
orchestration.md` 时发现同一行**又变了一次**，且不是这次会话自己改的。
对照仓库当前活跃的会话列表才想起来：这次一共有 **31 个同名工作区的并行
会话**在跑，用户确认过的那个"新会话"很可能仍在收尾，跟这次会话几乎
同时保存同一个文件。两次写入前后脚落地，后写的盖掉了先写的那一部分——
没有冲突标记、没有报错，就是普通的"最后写的赢"。

这次恰好后写的那份是对的（都指向同一个确认过的结论），所以不需要再改。
但它说明了一件更大的事：**在一个可能有其他会话同时写的工作区里，「我
刚编辑过的内容还是我编辑时的样子」这个假设本身会过期**——提交前多读一遍
文件，不能只信自己工具调用留下的记忆。
