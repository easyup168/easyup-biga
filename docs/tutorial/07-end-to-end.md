# 第 07 章 · 端到端：证明 Supervisor 真的调了 Specialist

> 📄 **过程** · 写完即冻结（只追加「⏩ 后续变动」指针）
> **覆盖**：这一段是怎么建起来的 ｜ **不覆盖**：当前设计（见 [`../design/`](../design/architecture.md)）


> **本章目标**：`biga agent --agent main -m "今天市场情绪怎么样？"` 跑通，
> 并**证明** emotion 确实被调用了 —— 不是 Supervisor 自己编的。
>
> 这一章几乎全是排查。真正写代码的部分只有几行契约修改，
> 其余时间都花在「为什么它不工作」上 —— 而那部分才是值钱的。

## 1. 先定义「证明」

验收标准第 1 条的原话是：

> Supervisor **确实 spawn 了** `emotion`（`agent_runs` 有该行，**不是自己编的**）

「不是自己编的」这五个字是整条标准的重点。

在多 Agent 系统里，Supervisor 回答说「我调用了 Emotion Agent，它返回情绪分 48」——
**这句话本身不能作为证据**。LLM 完全可以把整段调用过程编出来，而且编得非常像：
有 Agent 名字、有返回值、有时间。

所以需要一份**调用方之外的记录**。

### 一个假绿的例子

最初的验收脚本是这么写的：

```python
rows = list_agent_runs(decision_id=decision_id)
if "emotion" in {r["agent"] for r in rows}:
    c.ok("agent_runs 有 emotion")
```

它当时是**绿的**。但那行 `agent_runs` 是我手工跑 `synthesize.py` 插进去的 ——
**人跑一遍脚本和 Supervisor 真的 spawn，在这张表里长得一模一样。**

于是把它加硬：必须同时命中 OpenClaw 运行时自己的 `subagent_runs` 表 ——
那张表由 spawn 机制写入，BigA 的业务代码碰不到它。

```python
"""🔴 这一条要证明的是「Supervisor **真的**调了 emotion」，不是「有人跑过 emotion」。

只查 BigA 自己的 `agent_runs` 是不够的 —— 人手工跑一遍合成脚本也会写进那张表。
所以必须同时命中 OpenClaw 运行时自己的 `subagent_runs`。
"""
```

改完之后它立刻变红了 —— **这才是当时的真实状态。**

> **通用原则**：验证「A 做了 B」时，证据必须来自 **A 控制不到的地方**。
> 由被验证方自己写的记录，只能证明它声称做过。

## 2. 三层迷宫：为什么它一直不工作

配好 agent、配好委派白名单之后，第一次运行的结果是：Supervisor 跑起来了，
搜了四次工具都没找到 spawn，最后用了一个通用子 agent 顶替。

排查下来是**三个独立的问题叠在一起**，每一个单独看都像根因。

> 🔴 **本节只写可迁移的结论。**
> 具体怎么配、本机有哪些限制，属于**这台机器与这个账号的特殊情况** ——
> 是个人/组织信息，不该写进一个公开仓库，**即使是以「踩坑记录」的形式**。
> 这类内容的危险恰恰在于它读起来像踩坑记录，所以会被顺手写进教程。
>
> 那部分记在仓库外的本机笔记里。仓库侧由
> `tools/verify/audit_public.sh` 的第 9 项守着。

### 第一层：登录时的一个自动选择，决定了 Agent 跑在哪个运行时上

登录流程里有一步要选认证方式。它**探测到本机的环境就自动替你选了**，
并据此往配置里写了一组 `agentRuntime` 设置。

不同的运行时意味着完全不同的东西：内置 harness 里的 agent 是 OpenClaw 的 agent；
桥接到外部 CLI 之后，它变成一个被 OpenClaw 驱动的**别人的**会话。

**这一步最坑的地方是它没有问你。** 它探测、它决定、它写配置，
输出里只有一行提示。

> **通用原则**：安装器的「智能默认」会写进配置并长期生效。
> 装完之后**把它实际写了什么读一遍** —— 尤其是那些你没被问到的项。

### 第二层：桥接模式下，工具可能整体到不了会话

桥接模式靠把 OpenClaw 自己的工具作为 MCP server 注入给外部 CLI。
理论上没问题。

实际上 gateway 日志里有一行警告，混在几百行输出中间，说这个 MCP server
**被本机的一条策略拦下了**。于是注入的 49 个工具一个都没到达会话，
Supervisor 的 `ToolSearch` 自然返回：

```
No matching deferred tools found
```

它不是「没想到用 spawn」，是**那个工具根本不存在于它的世界里**。

> **通用原则**：`ToolSearch` 找不到工具时，先问「它在不在这个会话的工具表里」，
> 再问「提示词写得好不好」。**两者的表现完全一样，修法完全不同。**

### 我在这里犯了一个错

查到这一步时，我直接 `curl` 那个 MCP server 问它有多少工具，得到 **0**，
于是断言「OpenClaw 没给 CLI 暴露任何工具」。

**这个结论是错的。** MCP 协议要求先 `initialize` 握手再 `tools/list`，
我跳过了握手。补上之后是 **49 个工具，`sessions_spawn` 就在里面**。

> **通用原则**：探测一个协议端点时，**先按协议规定的方式握手**。
> 少一步握手拿到的空结果，看起来和「真的什么都没有」完全一样 ——
> 而你会基于它做出完全错误的归因。

### 第三层：切了运行时，但没有凭据

知道根因后把运行时改回内置 harness，重启 gateway，跑一句最小探测：

```
All models failed (2): ... No API key found for provider "anthropic".
```

因为桥接模式提供的是**插件自带的 synthetic auth** —— 它让桥接能跑，
但**不产生任何 auth profile**：

```
$ biga models auth list --agent main
Profiles: (none)
```

内置 harness 需要真凭据。**两件事缺一不可**，而这正是前几轮反复失败的原因：
换认证方式时运行时还钉在桥接模式，换运行时时又没有凭据。

> **通用原则**：当一个东西需要 A 和 B 同时成立，而你每次只改一个，
> **每次都会失败，且每次的报错都不一样** ——
> 于是看起来像「一个接一个的新问题」，其实是同一个。

## 3. 最有价值的一句话：「另一套是好用的呀」

排查卡住的时候，有人指出了这一点。

这句话的价值在于：**它提供了一个对照组。**

同一台机器、同一个环境、同一个 OpenClaw，一套能用一套不能用 ——
那么差别一定在两者之间某个**可枚举**的地方。于是去读那一套的配置（只读）：

| | 已有实例（能用） | BigA（不能用） |
|---|---|---|
| `agentRuntime` 钉死 | **完全没有** | 被 login 钉成了桥接模式 |
| agentDir 里的 auth profile | **1 条** | **0 条** |

两行差异，两个根因，一一对应。

> **通用原则**：排查时如果存在一个「同环境但能用」的系统，
> 优先去读它的配置，而不是继续在坏的那套里试。
> 对照组能把「无限的可能原因」收敛成「两者之间的有限差异」。

### 一个有代价的妥协，和把它变成显性的做法

最终的凭据方案让 BigA 与已有实例**共享同一份凭据**。这与裁定 1（完全独立）
相抵触，是有意识做出的让步。代价是真实的 ——

> 凭据失效时，**两套系统同时停**。
> 而你的第一反应会是「BigA 这个新系统又出问题了」—— **排查方向天生是错的。**

接受它之后，做了三件事把这条耦合**从隐性变成显性**：

1. **profile 的命名自曝身份** —— 任何人跑 `models auth list` 看到它，
   都会知道这不是本项目自己申请的
2. `CLAUDE.md` 里写一节「已知耦合」，**包含排查顺序**
3. `TODO.md` 挂一条带**可判定触发条件**的替换项

> **通用原则**：接受一个有代价的妥协时，真正重要的不是记下「我们妥协了」，
> 而是记下**它出问题时会长什么样**。
> 三个月后没人记得这个决定，但那时故障会以「排查方向错误」的形式出现。

⚠️ 具体用的是哪种凭据、为什么只能用它，**不写在这个仓库里** ——
见上面那条关于个人/组织信息的说明。

## 4. 成功的样子

切换运行时 + 补上凭据之后：

```bash
$ biga agent --agent main -m "只回复两个字：收到"
收到
```

然后是真正的端到端。关键证据出现在 OpenClaw 自己的表里：

```
subagent_runs: 1 行
  run_id                 = 3a6a5ecb-8989-49fd-842f-057f66e0099f
  controller_session_key = agent:main:main
  child_session_key      = agent:emotion:subagent:deb35b08-…
```

`controller` 是 main，`child` 是 emotion。**这一行 BigA 的业务代码写不出来。**

emotion 子会话 `status=succeeded`，8 次工具调用，耗时 79.9 秒，
`raw_market_snapshot` 新增 8 条 —— 它确实去采了真实数据。

## 5. 我自己造的一个假 bug

第一次成功 spawn 之后，我查了一下状态：

```
main:    status=succeeded, last_tool_name=sessions_yield
emotion: status=running
decision_records: 没有新增
```

于是判断：Supervisor **提前收工了** —— spawn 完就 `sessions_yield` 交还控制权，
自己标记成功，而 Card 从未产出。我还据此在 `AGENTS.md` 里写了一整节
「绝不允许 `sessions_yield` 式的提前收工」。

**这个判断是错的。**

再等了两分钟之后，Card 出现了：

```
record_id=3  BIGA-20260919-002  status=WAIT  generated_at=17:41:02
```

时间线是这样的：

```
17:37:55  发起提问
17:38:19  main spawn emotion → sessions_yield → 本轮 succeeded
17:39:27  emotion 跑完（79.9s）
17:41:02  main 被运行时唤醒 → 合成 Card → 落库
```

`spawn → yield → 被唤醒 → 继续` **就是 OpenClaw 异步委派的正常模式**。
我只是查得太早，把「异步进行中」误判成了「已经放弃」。

于是把那一节整个改写，并把硬约束换了个对象：

```markdown
注意这条约束的对象是**整个对话**，不是**你的某一轮**。
你在 yield 之后那一轮确实结束了，这没问题；但被唤醒之后你必须把事情做完。

⚠️ 一个容易骗过自己的地方：`status=succeeded` 只表示**你这一轮**正常结束，
**不表示任务完成了**。判据只有一个 —— `decision_records` 里有没有新增一行。
```

> **通用原则**：在异步系统里判断「它失败了」之前，先确认**你等够了没有**。
> 把「进行中」误判成「已失败」，会让你去修一个不存在的 bug ——
> 而修法往往是把正确的机制关掉。

顺带一提，这条经验本身也证明了那个判据的价值：
不要看 `status`，看**产物有没有出现**。

## 6. 「今天」在非交易日意味着什么

第一张真正的 Card 是这样的：

```
BIGA DECISION CARD   BIGA-20260919-002   17:41:02
──────────────────────────────────────────────────
emotion      UNKNOWN  —

状态：WAIT

核心矛盾：2026-09-19 是周六，非交易日，无情绪数据可判断

⚠ 缺失项（7）
  · 涨停家数 —— 请求 20260919 但数据源返回的是 20260918 的数据
  · 炸板家数 —— 请求 20260919 但数据源返回的是 20260918 的数据
  · 跌停家数 —— 请求 20260919 但数据源返回的是 20260918 的数据
  · 全部情绪指标 —— 没有任何股池返回可用的交易日
  · 涨跌家数 —— 已取到数据，但缺少可信交易日，无法确定它描述的是哪一天
  · risk agent 尚未上线，本卡未经风险审查
  · discipline agent 尚未上线，本卡未经纪律审查

证据
  （无）
```

**这张卡在诚实性上是满分的。** 它拒绝用 09-18 的数据冒充 09-19，
把每一条缺失都列了出来，还主动声明了两个未上线的 Specialist。
第 05 章那个「数据源静默造假」的防线，在真实链路上生效了。

**但它对人没有用。**

周六问「今天市场情绪怎么样」，有用的回答是
「最近一个交易日（周五）是这样的」，而不是「今天没开盘，所以我什么都不知道」。
后者技术上没错，但它把一个**可以回答的问题**变成了一张全是缺失项的空卡。

根因在契约：`emotion` 的 `AGENTS.md` 写的是
「Supervisor 指定了交易日就加 `--date`（严格模式）」，
而 Supervisor 很自然地把「今天」翻译成了今天的日期。

两处都改了：

```markdown
人问「今天市场情绪怎么样」，**默认不要指定日期**。让 Specialist 走宽松模式，
取数据源给出的最近一个交易日，并在 Card 上注明那是哪天。

⚠️ 但注明日期是**强制**的。可以给周五的数据，不可以让人以为那是今天的。
```

> **通用原则**：「诚实」和「有用」是两个独立的目标，都要满足。
> 一个只优化诚实的系统会退化成「什么都不敢说」——
> 那同样是一种失效，只是它看起来像谨慎。

## 7. 排查方法小结

这一章用到的手段，按「先用哪个」排序：

| 手段 | 什么时候用 |
|---|---|
| **找对照组** | 存在一个同环境但能用的系统时，优先读它的配置 |
| **读产物，不读状态** | `status=succeeded` 骗人，`decision_records` 有没有新行不骗人 |
| **看运行时自己的记录** | `subagent_runs` / `task_runs` 是 agent 伪造不了的 |
| **翻完整启动日志** | 那句 `blocked by ***` 混在几百行里，grep 才看得见 |
| **读会话 transcript** | 能看到 agent 到底调了什么工具、ToolSearch 返回了什么 |
| **直接探端点** | 但要按协议握手，否则空结果会误导你 |
| **对比 config 备份** | `openclaw.json.bak` 让「这次登录改了什么」一目了然 |

## 8. 本章要点

| 要点 | 一句话 |
|---|---|
| 证据要来自被验证方控制不到的地方 | `agent_runs` 人能伪造，`subagent_runs` 不能 |
| 安装器的「智能默认」会悄悄决定运行时 | 输出里只有一行提示，背后是一组配置改写 |
| 一条本机策略能静默拦掉整个工具集 | 表现是「模型找不到工具」，看起来像提示词问题 |
| 探端点要按协议握手 | 少一步握手的空结果，和「真的没有」长得一样 |
| **对照组是最强的排查工具** | 「另一套是好用的」这一句直接把搜索空间收敛了 |
| 妥协要记的是「它坏起来什么样」 | 不是「我们妥协了」，而是故障时的排查顺序 |
| 🔴 环境特定的细节不进公开仓库 | 它读起来像踩坑记录，所以最容易被顺手写进教程 |
| 异步系统里先确认等够了没有 | 把「进行中」当「失败」，会让你去关掉正确的机制 |
| 看产物，别看状态 | `succeeded` 只说明这一轮结束了 |
| 诚实和有用是两个目标 | 只优化诚实会退化成「什么都不敢说」 |
