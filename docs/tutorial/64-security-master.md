## 目标 / 产出

第一张 point-in-time 的事实表：**某个知识截止时刻下，A 股市场上有哪些票**。

```text
schema v27  fact_security_master           每行挂在一个不可变分区上
data/datasets/security_master.py           归一 / 质量裁定 / 落 fact / 发快照
providers/eastmoney_security_master.py     抓取层（⚠️ 本机未探活成功）
bin/biga-security-master                   同步命令，三态退出码
tools/verify/security_master_probe.py      探活工具，手工跑
```

## 为什么这么做

### 外部实现有一处做得特别对

它的报告里有一节叫 **Point-in-time honesty boundary**：

> 这个源给的是**当前在册**名单和上市日期，**没有完整退市历史**。
> 因此只保证「从 BigA 第一次成功同步那天起」的 point-in-time，
> 不宣称覆盖之前。"The live current-universe provider cannot be backdated.
> This prevents today's list from being falsely published as an old
> historical snapshot."

**这正是 R-3 的正解。** 一个能"提供"历史 universe 的 Security Master，
比一个诚实说"我只有从今天起"的更危险 —— 回测会拿着今天的名单去跑三年前，
而**幸存者偏差不会报错**，它只会让结果好看。

原样保留，一个字没改。

### 🔴 但它从没打过那个接口

它的 `TEST_RESULTS.md` 最后一句：

```text
Live Eastmoney network fetching was not executed.
```

整个 provider —— URL、三个 host、过滤串、分页、字段编号 —— **全是没验证的**。

而本仓库开发流程的第一条就是：

> **设计先探活。** 对外部数据源做任何设计之前，先用 curl 打一次真接口。
> 「外部评审建议我们 Offline First, Live Last。对本项目**恰好是反的**：
> 先写 fixture 等于把一个坏掉的 API 形状固化进测试。」

于是这一章真正做的事，是**补做那一步**。

## 坑

### 探活的第一课：先建对照组，再下结论

第一次打，三个 host 全失败（502 / 空）。

差一点就写下"这个端点不通"。但**同一分钟内**打既有的生产端点：

```text
push2delay/ulist.np   → {"rc":0, ... 真数据}
push2ex/getTopicZTPool → {"rc":0, ... 真数据}
quote.eastmoney.com    → 200
```

网络是好的、东财是活的。**只有 clist 在 502。** 那才是一个有意义的信号。

> 通用原则：**一次失败什么都证明不了。** 对照组是把"失败"变成"信号"的唯一办法。

### 第二课：探针本身会制造它要观察的现象

继续打了十来个请求之后，**连对照组也开始 502**。

我把自己限流了。于是：

- 「clist 不通」这个结论**再也没法复验**
- 而且此刻任何进一步的实验都是在被限流的状态下做的，全部无效

⇒ 停止探测，把状态如实记成 **未验证**，写一个手工探活工具留给"不被限流的时候"。

> 🔴 **「不可用」和「我没验成」是两件事**，而它们在屏幕上长得一模一样。
> R-3 说的就是这个。

### 第三课：参考实现里写着我本该先看的东西

停下来之后去翻 `a-stock-data`（一份记录每个端点实测可用参数、主源/备胎顺序与
风控经验的公开速查库）。它的东财统一入口第一句：

> 所有 eastmoney.com 接口都应通过它请求，**避免高频被封 IP**。
> `EM_MIN_INTERVAL = 1.0` 秒 + 0.1~0.5 秒抖动。

而外部实现用的是 `ThreadPoolExecutor(max_workers=2)` 并发翻页、**零间隔**。
全市场约 5400 只 / 每页 100 ⇒ 约 54 页。

我踩的坑和那份实现将来会踩的，是同一个。

还有两处：

- 它的 `EM_CLIST_HOSTS` 是 `push2` → `push2delay`；外部实现反过来
- 它把 `fs` 交给 requests 的 params（`+` 编成 `%2B`），而外部实现
  `urlencode(..., safe="+:")` 让 `+` 裸上线 —— **query 里的裸 `+` 服务端解成空格**，
  `m:1+t:2` 会变成 `m:1 t:2`

⇒ 抓取层按参考实现改写：串行 + 限流 + `%2B` + 主域顺序。

### 我自己判错一次：看常量不看调用点

我一度写下"它少发了 `po/np/fltt/invt/fid` 五个参数"——**那是错的**。
常量块里确实只列了两个，但实际请求发了十个，比参考实现还多一个 `ut`。

我看的是文件顶部的常量，没看 `_fetch_page()` 里真正拼的那个 dict。

> 🔴 **按「代码长什么样」下判断，而不是按「它实际做什么」。**
> 这和守卫落错地方是同一个毛病，只是这次发生在读代码的时候。

### 注册一个"链路建成但源没验"的数据集，算不算 L-1

我的 P11 守卫要求每个注册的 dataset 都答得出谁读它。`cn.security_master`
有读路径（`security_universe_at`），链路也整条建成了，只是**上游取不到数**。

判断：**注册**。理由是它取不到数时的行为是 **fail-closed** ——
Data Run 转 FAILED、不发布快照、CLI 退非零。注册表没有撒谎：
它说"这个数据集归平台管"，而平台确实管着它，只是现在管出来的结果是失败。

⚠️ 但这件事必须**写在注册表里**，不能只留在我脑子里 ⇒
provider 的 title 里直接写着「本机尚未探活成功」，质量策略的
`not_checked` 里也写着。
