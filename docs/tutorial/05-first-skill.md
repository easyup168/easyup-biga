## 1. 先别写代码：现有的轮子在哪

我一开始的做法是：打开数据源文档，一个个端点试过去。

被叫停了：

> 「XX 下面有完整的数据源的获取方法，不要从零开始呀。」

这个提醒值得单独记一笔。同一台机器上跑着一套成熟的同类系统，
它的数据采集经过了长期的真实检验 —— 哪个端点稳、哪个会挂、
哪个库版本咬过人，全都是**用时间换来的信息**。
从零试端点，等于把别人已经付过的学费再付一遍。

于是改成：先读它的采集层，把知识拿过来，再自己实现。

拿到了四样东西：

| 拿到的 | 价值 |
|---|---|
| 可用端点清单 | 省掉大量试错 |
| 情绪指标的完整口径 | 涨停/炸板率/连板梯队/赚钱效应/晋级率 —— 成熟的领域知识 |
| 情绪周期五阶段的量化标准 | 直接成为 Agent 的判断依据 |
| **一条血的教训** | 见下 |

那条教训写在它的数据契约文档里：

> 把爬虫封装库的版本**钉死**。它不承诺 API 稳定，本项目已被咬过两次
> （一个接口被删、一个接口改名），**都曾静默失效数月**。
> 不许升级，不许新增接口而不加失败告警。

这条直接决定了本章后面的两个设计。

> **通用原则**：进入一个新领域之前，先找**已经在这个领域踩过坑的人或系统**。
> 端点清单可以自己试出来，「这个库咬过我两次」只能靠别人告诉你。

⚠️ 一个边界：借鉴知识 ≠ 共用状态。本项目与同机已有实例**零共享可写状态**，
自己重新采数据、写自己的库。拿过来的是**知识**，不是**耦合**。

## 2. 实测：哪些端点真的能用

知识拿到了，但「在它的环境里能用」不等于「在我的环境里能用」。逐个实测：

| 端点 | 结果 |
|---|---|
| `push2ex.eastmoney.com`（三个股池） | ✅ 稳定 |
| `push2his.eastmoney.com`（历史 K 线 / ulist） | ⚠️ curl 通，urllib 被直接断连 |
| `push2delay.eastmoney.com`（ulist） | ✅ 稳定 |
| `push2.eastmoney.com` | ❌ 302 / 超时 |
| `hq.sinajs.cn` | ✅（需 `Referer`） |
| `qt.gtimg.cn` | ✅ |

两个值得记的细节：

**① 同一份数据常有多个镜像主机，可用性各不相同。**
`ulist.np` 这个接口在 `push2delay` 上好好的，在 `push2his` 和 `push2` 上
一律 `RemoteDisconnected`。所以代码里配的是一条**备选链**，不是单个 URL。

**② curl 能通不代表你的 HTTP 客户端能通。**
`push2his` 用 `curl` 拿得到，用 Python 的 `urllib` 就被服务端直接关连接。
所以**探测必须用你真正要用的那个客户端**，不能用 curl 探完就当数了。

## 3. 🔴 本章的核心：一个会静默骗你的接口

这是全章最重要的一节。

涨停池接口接受一个 `date` 参数。直觉上：给它一个日期，它返回那天的数据；
日期不对就报错。实测结果是：

| 请求 `date` | 返回 `rc` | 返回 `qdate` | `tc` | 实际含义 |
|---|---|---|---|---|
| `20260918`（周五，交易日） | `0` | `20260918` | 78 | ✅ 正确 |
| `20260920`（周日，非交易日） | `0` | `20260918` | 78 | ⚠️ 静默返回上一交易日 |
| `20260101`（元旦，非交易日） | `0` | `20260918` | **0** | ⚠️ 最坏 |

**三行都是 `rc=0`，都没有任何错误提示。**

第二行还算好 —— 数字是真的，只是日期错了。

第三行才是真正危险的：你问「2026 年 1 月 1 日涨停多少家」，它答「0 家」。
如果你信了，你的数据库里就会多出一条**完全虚构的市场事实**：
「2026-01-01 涨停 0 家」。而元旦根本没开市。

没有异常、没有警告、没有空值。这条假数据会一直躺在库里，
参与后续所有的统计、回测、归因。

### 这类失败的形状

它属于本项目最优先防范的那一类：**失败时不报错**。

再看一眼这三行的共同点 —— **返回的都是「看起来完全合理的数字」**。
78 是个合理的涨停家数，0 也是个合理的涨停家数。
光看数字，你永远分不出哪个是真的。

### 唯一的解法：让数据自己说它是哪天的

幸运的是，这个接口的响应里带一个 `qdate` 字段 —— **数据自己声明的交易日**。
三次请求的 `qdate` 全都是 `20260918`，诚实地说明了「我给你的就是 9 月 18 日的数据」。

于是定下本项目的一条硬规则：

> **`as_of` 永远取自 `qdate`（数据自己声明的日期），
> 绝不取自「我请求的日期」。**

代码里长这样：

```python
def _as_of_from_qdate(qdate: str) -> datetime:
    """🔴 as_of 取自数据自己声明的 qdate，绝不取自我请求的日期。"""
    d = datetime.strptime(qdate, "%Y%m%d").date()
    return datetime.combine(d, _CLOSE, tzinfo=CN_TZ)
```

> **通用原则**：一个外部接口返回的数据，**它自己对自己的描述**（版本号、
> 时间戳、数据日期）比**你对它的假设**（我请求的是什么）可信得多。
> 两者不一致时，永远相信前者，并且把不一致本身当成一个需要上报的事实。

### 严格模式 vs 宽松模式

日期语义分两种，代码里明确区分：

```python
# 宽松：没指定日期 = "给我最新的" —— 这不是一个契约，qdate 是什么就是什么
python3 emotion_calc.py

# 严格：指定了日期 = 一个契约 —— 对不上就是没拿到，进 missing[]
python3 emotion_calc.py --date 20260918
```

```python
if self.date is not None and not r.date_matches:
    # 显式指定了日期 = 一个契约。对不上就是没拿到要的东西。
    self._note(missing=f"{label} —— 请求 {self.date} 但数据源返回的是 {r.qdate} 的数据")
    return
```

实测严格模式请求周日：

```
status=partial verdict=UNKNOWN result=0项 missing=5条
  · 涨停家数 —— 请求 20260920 但数据源返回的是 20260918 的数据
  · 炸板家数 —— 请求 20260920 但数据源返回的是 20260918 的数据
  · 跌停家数 —— 请求 20260920 但数据源返回的是 20260918 的数据
  · 全部情绪指标 —— 没有任何股池返回可用的交易日
  · 涨跌家数 —— 已取到数据，但缺少可信交易日，无法确定它描述的是哪一天
```

一条数据都没编。

## 4. 为什么最后没用现成的封装库

有一个现成的 Python 库封装了这些接口，用它能少写一百行代码。实测它也确实能用。

最后还是选了直接打 HTTP，两个理由：

**① 它把 `qdate` 丢了。**
库把响应整理成 DataFrame，列是：`序号 / 代码 / 名称 / 涨跌幅 / … / 连板数 / 所属行业`。
**没有日期列。** 而上一节刚说明，`qdate` 是这个接口唯一能让你分辨真假的字段。

用库的话，第 3 节那个「元旦涨停 0 家」的陷阱就**完全无法防御** ——
你拿到一个 0 行的 DataFrame，没有任何线索告诉你这 0 是真的还是假的。

**② 第 1 节那条教训。**
爬虫库不承诺 API 稳定，同类系统被静默咬过两次。
既然本项目只需要三个端点，直接持有 URL 反而让失效点更少、更可见 ——
URL 变了会 404，库函数改名会 `AttributeError`，但库函数**悄悄改变返回结构**
不会有任何症状。

> **通用原则**：封装库用「更好用的接口」换走了「原始响应里的信息」。
> 当被换走的那部分恰好是你的**正确性依据**时，这笔交易就不划算了。

## 5. 采集层：失败一律抛错，绝不兜底

`sources.py` 的唯一职责是「把数据源返回的东西原样拿回来」。它不算涨停率、
不判断强弱、**不填默认值**。

> ⏩ **后续变动**：这个文件在 Phase 2 的 2.1 被抽到了共享包
> `skills/_sources/`（`http.py` + `eastmoney.py`）—— 因为出现了第二个消费方
> `market-calc`，而共用的不只是 URL，更是重试 / 退避 / 备选主机链这套判据。
> 过程见[第 11 章](11-second-specialist.md)。本章其余内容不受影响：
> 职责划分与错误处理口径一个字没改。

```python
class SourceError(RuntimeError):
    """数据源不可用或返回了无法解释的内容。

    🔴 采集层遇到问题一律抛这个，绝不返回一个「兜底值」。
    返回兜底值 = 让上层无法区分「真的是这个数」和「没取到」。
    """
```

还有一道容易忽略的校验：

```python
if total and len(rows) != total:
    raise SourceError(
        f"{pool}: 接口声称 tc={total} 但只返回 {len(rows)} 行 —— "
        f"分页可能截断（page_size={page_size}）"
    )
```

接口自己报了总数，那就拿它跟实际行数对一遍。
**悄悄少几行比完全取不到更难发现** —— 取不到会报错，少几行只是数字偏小一点。

### 重试：可以有，但耗尽必须抛错

实测这些公开端点会偶发 TLS 握手超时。第一版没有重试，四个请求里能成功两个。
加了三次退避重试后全部稳定。

但重试代码有个必须守住的边界：

```python
#: 🔴 重试耗尽后**必须抛错**，由上层记入 missing[] ——
#:    绝不允许「重试几次还不行就返回 0」，
#:    那会把网络抖动变成一条虚假的市场事实。
_RETRIES = 3
_BACKOFF_SEC = (0.8, 2.0)
```

「重试几次还不行就用默认值」是极其常见的写法，也是本章反复在防的那件事的又一个变体。

还有一个细节：**返回了内容但不是 JSON，不重试。**

```python
except json.JSONDecodeError as e:
    # 返回了内容但不是 JSON —— 多半是网关错误页，重试没有意义
    raise SourceError(...) from e
```

重试应该只用于**瞬时故障**。对一个稳定返回错误页的端点重试三次，
只是把一次失败变成三次失败加六秒延迟。

## 6. 计算层：skill 到底不做什么

架构里有一条硬约束：

> **S-2**：skill 不得做判断性归类（「这属于强势板块」）。
> skill 返回事实与分数，判断留给 agent。

具体到情绪：

| 归 Python（本 skill） | 归 Emotion Agent（LLM） |
|---|---|
| 涨停 78 家、炸板 25 家、最高 4 板 | 这算不算「亢奋期」 |
| 炸板率 24.27% | 炸板率 24% 在当前位置是否算健康 |
| 情绪分 55.52（确定性公式） | 这个分数此刻该不该信 |

沿用一套既有的**情绪周期五阶段量化标准**（涨停家数 / 连板高度 / 炸板率 / 跌停家数
对应冰点、修复、亢奋、衰退、恐慌），是一份很好的判断依据 —— 但它属于**判断**，
所以它写进 `agents/emotion/AGENTS.md`，不写进 skill。

理由是**口径分裂**：同一个「强不强」，如果 skill 算一遍、agent 的 prompt 里又算一遍，
两边会慢慢漂开，而且**漂开时不会报错**。

有一条测试专门守这个边界：

```python
def test_不产出周期归类(self, wired):
    """硬约束 S-2：skill 不做判断性归类。"""
    r = build().result
    banned = {"stage", "cycle", "phase", "情绪阶段", "judgment", "advice"}
    assert not (banned & set(r))
    for v in r.values():
        assert not isinstance(v, str) or v in (QDATE,), \
            f"skill 的 result 不该出现自然语言判断: {v!r}"
```

第二条断言（result 里不许出现自然语言字符串）比第一条有用得多 ——
它拦的是**没想到的字段名**，而不只是我列出来的那几个。

### 「算不出来」不是 0

炸板率需要涨停池和炸板池同时在场：

```python
if zt and zb:
    denom = zt.total + zb.total
    if denom:
        add("broken_rate", round(zb.total / denom, 4), "炸板率", ...)
    else:
        c.missing.append("炸板率 —— 涨停与炸板家数均为 0，分母为零")
else:
    c.missing.append("炸板率 —— 需要涨停池与炸板池同时可用")
```

对应的测试断言的是**这个键根本不存在**，而不是它等于 0：

```python
def test_炸板率缺一个池就算不出来(self, wired):
    v = build(break_source={"broken_board"})
    assert "broken_rate" not in v.result
    # 🔴 关键：不是填 0，是根本没有这个键
    assert v.result.get("broken_rate") is None
```

## 7. 并行化：这不是调优，是能不能用

第一版串行采集，四个请求 **26 秒**。端到端预算是 60 秒 ——
光采集就吃掉一小半，剩给两个 Agent 的推理时间不够。

改成并行后 **18.8 秒**（网络本身慢，没到理论值）：

```python
# 四个请求互不依赖，并行拿。串行约 26s，并行约 8s ——
# 端到端预算卡在 60s，这一步不是调优，是能不能用的问题。
jobs = [
    lambda: c.collect_pool("limit_up", "涨停家数"),
    lambda: c.collect_pool("broken_board", "炸板家数"),
    lambda: c.collect_pool("limit_down", "跌停家数"),
    c.collect_breadth,
]
with concurrent.futures.ThreadPoolExecutor(max_workers=len(jobs)) as pool:
    for fut in [pool.submit(j) for j in jobs]:
        fut.result()
```

### 并行引入了一个竞态，而且很隐蔽

原来的 `collect_breadth()` 里有这么一段：

```python
if self.store and (qd := self.qdate):        # ← self.qdate 来自其他三个池
    self._keep_raw(save_raw_snapshot(...))
```

串行时这是对的：涨跌家数最后采，那时三个池都跑完了，`self.qdate` 已经有值。

**并行之后它就错了** —— 涨跌家数可能先于股池完成，此时 `self.qdate` 还是 `None`，
于是这条原始数据被**静默跳过不落盘**。没有报错，只是库里少一条记录。

修法不是加锁，是**把依赖后续结果的逻辑挪到后面去**：

```python
# ⚠️ 这里**不**落 raw、**不**发警告：
# 两者都依赖 qdate，而 qdate 要等全部股池跑完才知道。
# 并行采集下在这里读 self.qdate 是竞态 —— 统一放到全部完成后做。
```

> **通用原则**：把串行代码改成并行时，真正的风险不是「两个线程同时写坏一个变量」——
> 那个有锁能解决。风险是**原来隐含的顺序依赖**：某段代码读了另一段的结果，
> 而这个依赖从来没被写出来过，因为串行时它自动成立。

顺带，共享状态也确实加了锁：

```python
def _note(self, *, missing: str | None = None, warning: str | None = None) -> None:
    with self._lock:
        ...
```

## 8. 三档 verdict 必须都可达

`verdict` 表达的是**数据完整度**，不是市场判断：

| verdict | 条件 |
|---|---|
| `PASS` | 无任何缺失 |
| `WARNING` | 有缺失，但核心三项（涨停家数 / 炸板率 / 最高板）齐备 |
| `UNKNOWN` | 核心三项有缺 |

写完之后要问一个问题：**`WARNING` 这一档真的到得了吗？**

因为核心三项里的「炸板率」需要两个池，看起来随便断哪个源都会掉到 `UNKNOWN`。
如果 `WARNING` 实际不可达，那段代码就是**死分支** ——
它照常参与判断，只是永远不生效，而且永远不会有人发现。

所以写了一条专门的测试：

```python
def test_三档verdict都可达(self, wired):
    """防死分支：任何一档取不到，说明那段逻辑是恒假的。"""
    levels = {
        build().verdict,
        build(break_source={"limit_down"}).verdict,
        build(break_source={"limit_up"}).verdict,
    }
    assert levels == {"PASS", "WARNING", "UNKNOWN"}
```

实测确实可达（断跌停池或断涨跌家数 → `WARNING`）。

> **通用原则**：写了一个有 N 个分支的判定，就要有 N 个测试证明每一支都能到达。
> 到不了的分支不是「暂时用不上」，是**已经坏了但还没人知道**。

## 9. 测试：离线，且桩要守规矩

### 为什么测试不许联网

```python
"""🔴 这些测试**不许联网**。理由不是速度，是可信度：
依赖外网的测试会因为对方抖动而随机变红，几次之后所有人都会开始忽略它的结果 ——
一个被习惯性忽略的测试等于没有测试。"""
```

真实采集的验证靠**手工跑一次**（下面「验证」小节），以及测试里对返回**结构**的断言。

### 一个真实的测试 bug：桩不遵守入参

严格模式那组测试一开始是绿的 —— 但绿得不对。

我的假 `fetch_pool` 忽略了传进来的 `date` 参数，直接返回预设好的
`PoolResult(requested_date="20260918", qdate="20260918")`。
于是 `date_matches` 永远为真，那道「日期对不上就进 missing」的门**从来没被测到过**。

```python
def fake_pool(name, date, **kw):
    v = plan.get(name)
    if isinstance(v, Exception):
        raise v
    # 🔴 桩必须遵守自己的入参。如果这里不把 requested_date 换成真正传进来的
    # date，`date_matches` 就永远为真，严格模式那组测试会因为错误的原因通过。
    return dataclasses.replace(v, requested_date=date)
```

> **通用原则**：桩（stub）必须像被替换的真实对象一样**响应输入**。
> 一个无视入参、永远返回同一个东西的桩，会让一整片测试因为错误的原因变绿 ——
> 这比测试红了还危险。

## 12. 本章要点

| 要点 | 一句话 |
|---|---|
| 先找踩过坑的人 | 端点清单能自己试出来，「这个库咬过我两次」只能靠别人告诉你 |
| 借鉴知识 ≠ 共用状态 | 拿过来的是知识，不是耦合 |
| 用你真正要用的客户端去探测 | curl 通不代表 urllib 通 |
| 同一份数据常有多个镜像主机 | 配备选链，不配单个 URL |
| **接口会返回看起来合理的假数字** | 请求非交易日 → `rc=0` + `tc=0`，一条虚构事实就此入库 |
| **信数据的自述，不信自己的假设** | `as_of` 取自 `qdate`，永远不取自「我请求的日期」 |
| 指定 = 契约，不指定 = 尽力 | 严格模式对不上就进 `missing[]`；宽松模式只记警告 |
| 封装库换走的可能正是正确性依据 | 它把 `qdate` 整理掉了，那个陷阱就再也防不住 |
| 采集层不许兜底 | 返回默认值 = 让上层无法区分「真是这个数」和「没取到」 |
| 重试只用于瞬时故障 | 拿到错误页还重试，只是把一次失败变成三次 |
| 重试耗尽必须抛错 | 否则网络抖动会变成一条虚假的市场事实 |
| 「算不出来」不是 0 | 断言的是**键不存在**，不是值等于 0 |
| 并行是功能要求 | 26s → 19s，决定端到端能不能进 60s |
| 并行的真风险是隐含顺序依赖 | 不是抢写变量 —— 那个有锁能解决 |
| 每个分支都要有测试到达 | 到不了的分支是「已经坏了但没人知道」 |
| 桩必须遵守入参 | 无视入参的桩会让一整片测试因为错误的原因变绿 |
| 测试不许联网 | 会随机变红的测试，几次之后就没人看了 |
