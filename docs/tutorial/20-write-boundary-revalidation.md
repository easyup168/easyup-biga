## 目标 / 产出

## 为什么这么做

### 一、问题不是假想出来的，是复现出来的

设计文档 §2 的评审复核里记着这一条：

```
save_verdict(非法对象)   →  ✅ 成功落库
load_verdict(同一行)     →  ❌ ValueError（from_dict 复校验，铁律 1）
```

复现方式很直白：先合法构造一个 `AgentVerdict`（`missing=[]`、`verdict="PASS"`），
再直接 `v.missing.append(MissingItem("事后塞的", "some.code"))`。Python 的
`list.append` 不会重新触发 dataclass 的 `__post_init__`——这不是 bug，是正常
语义。但契约层唯一的校验点就是 `__post_init__`，于是这一步之后，`v` 就是一个
"missing 非空却 verdict=PASS" 的非法对象，而**没有任何东西知道**。

`save_verdict` 拿到这个对象只做了 `json.dumps(v.to_dict())` 然后 INSERT——
它信任调用方交进来的对象本身，不重新校验。写入**成功**。直到某一天有人
`load_verdict()` 读这一行，`from_dict()` 重建对象触发 `__post_init__`，才第一次
报错。而 `agent_verdicts` 建表时就带了只追加触发器（v3，`_append_only()`）：
这一行删不掉、改不掉。

> 一个**可修复**的错误（重新调用一次 `save_verdict`），
> 因为校验点摆错了位置，变成了一个**不可修复**的错误（一行永久的死数据）。

⚠️ 排查过生产库：239 条 verdict、37 张卡，读不回来的 0 条，含 `NaN`/`Infinity`
的 0 条。**这一章做的是预防性修复，不是救火。**

### 二、为什么不能简单地「在 `save_*` 开头加一句 `assert`」

第一反应可能是：`save_verdict` 开头加一行 `v.__post_init__()` 手动重跑校验
不就行了？两个理由说明这不够：

1. **`__post_init__` 校验的是内存里的属性，不是「序列化之后长什么样」。**
   A4 要求同时挡住 `NaN`/`Infinity`——这是 JSON 序列化层面的问题
   （Python 的 `json.dumps` 默认会把 `float("nan")` 写成裸的 `NaN` token，
   这不是合法 JSON，但 Python 自己能读回来，于是「写进去的东西不是合法 JSON」
   这件事永远不会被单独的 dataclass 校验发现）。
2. **`DecisionCard` 有「新卡严、旧卡宽」的三段式语义**（`from_store` 标志），
   直接重跑 `__post_init__` 而不小心处理这个标志，会把整套语义弄反——
   下一节详细讲这个坑，它是这一批里最容易踩错的一处。

⇒ 统一做法是：`Domain Object → 规范序列化（拒绝 NaN/Infinity）→ 严格重建
（走 `from_dict()`，重新触发 `__post_init__`）→ DB`。不信任对象本身，
只信任「它序列化之后还能不能被同一套契约重新构造出来」。

### 三、`from_store` 那道坑：重建路径必须能选择「按新卡校验」还是「按旧卡校验」

`DecisionCard.from_dict()` 原来是这样的：

```python
@classmethod
def from_dict(cls, d):
    return cls(..., from_store=True)   # 硬编码
```

这是有意为之的：从库里读回来的历史卡（Stage 0 统一占号之前落库的那些）
允许判定编号与卡号不一致，`from_store=True` 让契约层把这类问题降级成
`identity_warning` 显示在卡面上，而不是拒绝构造——不然 31 张历史卡里
20 张永远读不出来。

问题是：如果 `save_card` 的写边界重校验也直接调 `DecisionCard.from_dict(...)`
（不传参数），拿到的重建对象**永远是 `from_store=True`**——包括正在写入的
**新卡**。也就是说，如果一张新卡在构造之后被篡改成「重复的缺失项」这种
只在 `from_store=False` 时才会被拒绝的非法状态，写边界的重建会因为
`from_store=True` 把它降级成一条 warning 而不是拒绝，**新加的这层校验对
这类篡改完全无效**——而这种「守卫确实在查，只是查的时候用错了严格度」
正是 `architecture.md` §9 L-13 的标准形状。

修法不是另写一套重建逻辑（那是第二套口径），是给 `from_dict()` 加一个
**默认值不变**的可选参数：

```python
@classmethod
def from_dict(cls, d, *, from_store: bool = True):
    return cls(..., from_store=from_store)
```

所有现有调用点（`load_card`、四个测试文件里的往返测试）一个字都不用改，
因为默认值还是 `True`。`save_card` 内部显式传 `from_store=card.from_store`：

```python
DecisionCard.from_dict(json.loads(payload), from_store=card.from_store)
```

新卡（`from_store=False`）走严格路径，历史/回放卡（`from_store=True`）
维持原来的宽松路径——「新卡严、旧卡宽」的三段式语义原样保留，而不是被
写边界这一层新代码悄悄削平。

⚠️ **这一步本身还留了一个洞，是评审复核时挑出来的**：上面这行代码信任的
是 `card.from_store`——`DecisionCard` 一个尚未 `frozen` 的普通属性
（`frozen=True` 是下一章批 A-II 的 A2）。也就是说 `card.from_store = True`
这行赋值不会报错，攻击者（或者一段有 bug 的代码）可以在合法构造之后同时
篡改 `.missing` 和 `.from_store`，把刚加的这层重校验也一起绕过去——档位
自己说了算，而对象正是这次要防的篡改对象。

修法是把档位挪到**调用参数**上：`from_store=replay_of is not None`。
`replay_of` 由 `card_ops.persist()` 的调用方决定（在线路径永远不传，
`replay.py --store` 永远传原始 `record_id`），不受 `card` 对象自身状态
影响。批 A-II 把 `DecisionCard` 改成 `frozen` 之后，`card.from_store = True`
会直接抛异常，这条攻击路径会被 A2 顺带堵死——但**在那之前**，档位不该
建在一个可写的对象属性上，这是评审复核指出的、需要在这一批就修的问题，
不是可以留到下一批的「已知问题」。详见「坑」一节。

### 四、严格 JSON 为什么拆成两个函数，而不是改一个

外部评审的 drop-in 建议是统一加 `separators=(",", ":")` + `allow_nan=False`。
但仓库里已经有一个 `payload_sha256()`，`raw_market_snapshot.content_sha256`
与 `Evidence.raw_hash` 的对应关系建立在它**当前**的输出格式上。直接改
`separators` 会静默改变所有历史哈希——两串 sha256 都「看起来正常」，
只是再也对不上当时存的那一个，而这种失效不会报错，只会在某天有人想核对
「这条证据出自哪份原始响应」时悄悄查不到。

⇒ 拆成两个函数：

| 函数 | 用途 | 改了什么 |
|---|---|---|
| `_canonical_dumps()`（新） | `card_json` / `verdict_json` 这类**新增**载荷 | `separators=(",", ":")` + `allow_nan=False` |
| `payload_sha256()`（原有） | raw 层内容哈希 | **只加** `allow_nan=False`，分隔符维持原状 |

而 `allow_nan=False` 这个改动本身是安全的：对不含 `NaN`/`Infinity` 的历史
数据，输出逐字节不变。只有本来就不该写进去的值，才会从「静默写入一个
Python 能读、RFC 8259 不认的裸 `NaN`」变成「写入前直接报错」。

`save_raw_snapshot` 完全不需要新代码：它已有的
`sha = payload_sha256(payload)` 这行本来就在 `connect()` 打开数据库连接**之前**
执行——只要 `payload_sha256` 拒绝 `NaN`，这一行天然就是写边界，NaN 会在任何
DB IO 发生之前就地抛错。

### 五、验证「历史哈希不变」不能靠承诺，要靠一份改动前生成的向量

「这次改动不会影响历史哈希」——这句话本身无法验证自己。唯一可信的做法是：
**在改任何代码之前**，用当时的实现对固定的样例数据生成哈希值，落进 fixture
并立刻 `git add`（让 git diff 能证明这份 fixture 早于后面的代码改动）。之后
`payload_sha256` 无论怎么改，这份 fixture 里的值都不会重新生成——测试只做
比对。如果哪天真的改错了分隔符，这条测试会因为「新哈希 ≠ 旧哈希」而红，
而不是因为「新哈希 ≠ 新哈希」（那样等于什么都没测）。

### 六、审查脚本顺带暴露的一个误报——以及第一次修法本身也是错的

`tests/fixtures/payload-sha256-vectors.json` 一落地，
`tools/verify/audit_public.sh --worktree` 立刻报「Gateway token —— 2 处」。
原因是那条检查的第三个分支是裸的 `\b[0-9a-f]{64}\b`——sha256 恰好也是 64 位
十六进制，检查分不清「这是一个令牌」还是「这是一段内容哈希」。

**第一版修法**把方向改反了：要求「必须有 `token` 标识符 + 赋值才算令牌」，
不满足就不命中。这确实消掉了误报，但评审复核用真实泄露形状一对照就露了
馅——`biga attach --token <hex>`（空格分隔，不含 `:`/`=`）、
`Authorization: Bearer <hex>`（key 是 `Authorization` 不是 `token`）、
散文里裸贴一个值，三种都是这套系统实际会产生的泄露形状，收窄之后**全部
漏检**。

这正是「先想清楚默认值该往哪边倒」的反例。安全检查的默认必须是「命中」，
例外要自己举手——本仓库另外两处已经在用同一条原则（只追加触发器「新表
默认就该受保护」、测试计数守卫「默认必须最新，例外要标冻结」），而第一版
修法反过来把默认状态从「安全」改成了「需要举证才安全」。

**改对的方向**：保留裸十六进制作为默认命中，只**豁免**明确自称哈希的
赋值/键值形式（`sha256:`/`content_sha256=`/`raw_hash:` 紧跟着它自己的
那个十六进制串）。`chk()` 加了一个可选的第三参数（豁免模式），不传时
其余检查行为逐字节不变。判据仍然不按文件名放行——按**语法结构**（是不是
一次自称哈希的赋值）判断，跟它存在哪个文件无关，这也是 `architecture.md`
§9 L-13 反复出现的教训：判据要落在真实区分点上，而不是随便找一个「看起来
能分开好坏」的近似条件。

⚠️ **这句"判据落在语法结构上"，第一次落地时自己也没做到位**——最初的
实现是「这一行出现了 `sha256` 这个词，就豁免整行」，而不是「抠掉自称
哈希的那一小段」。下一段专门讲这个坑，因为它本身也是一次「守卫查的地方
和它声称查的地方不是同一处」。

### 六点五、豁免的粒度必须等于命中的粒度

第一版的豁免实现是 `grep -Ev "$3"`——命中豁免词就整行扔掉。而**命中的
单位是一个十六进制串，不是一整行**。两者粒度不一致，后果是：只要一行里
出现过 `sha256` 这个词，那一行上**所有**的十六进制都会被一起放过，包括
另一个真令牌。

评审复核给出了一个格外扎心的例子：一段**解释这条检查本身**的文档散文，
「令牌也是 64 位十六进制，和 sha256 长得一样：`OPENCLAW_MCP_TOKEN=<真令牌>`」
——这一句话既示范了真实的泄露形状，又提到了 `sha256` 这个词，第一版的
豁免逻辑会把它整行放过。这正好压在本仓库最容易失守的地方：CLAUDE.md
已经记录了五次「描述规则时把真值抄了进去」，其中两次就发生在**写那条
规则的同一次提交里**——残余风险恰好落在经验上最脆弱的位置。

`{"token":"<真令牌>","sha256":"<内容哈希>"}` 是另一个更直接的例子：
`_canonical_dumps` 这一批刚开始产出单行压缩 JSON，这种「令牌和哈希挤在
同一行」的格式不是假设出来的，是这一批自己新增的输出形态。

⇒ 豁免的实现从「按行扔」改成「按子串抠」：

```bash
chk() {
    body=$(printf '%s' "$DIFF")
    [ -n "${3:-}" ] && body=$(printf '%s' "$body" | sed -E "s/$3//g")
    c=$(printf '%s' "$body" | grep -E "^\+.*$2" | grep -vc '^+chk "' || true)
    [ "$c" -gt 0 ] && { echo "⚠️  $1 —— $c 处"; FAIL=1; } || echo "✅ $1"
}
```

`$3` 不再决定「扔不扔整行」，而是先把「自称哈希的键 + 赋值 + 它自己的
十六进制串」这一小段从文本里原地抹掉，再对剩下的文本做正例匹配——同一行
里其他独立的十六进制，不管前面有没有出现过 `sha256` 这个词，该命中的
仍然命中。

探针把两轮的场景合成一份：F-1 的 9 行（6 真实泄露 + 3 纯哈希声明）
加上 F-1b 指出的 4 种复合场景（令牌与哈希同一个键值对里、令牌与哈希分列
同一句解释性散文/同一行 CLI 注释、markdown 表格一行两列各放一个），
命中的行与预期精确对上：13 行里 10 行命中、3 行豁免，一个不多一个不少。

> 豁免逻辑本身也是一条判据，判据也会有「查的地方和声称查的地方不是
> 同一处」这个问题——这一次它藏在「按行还是按子串」这个粒度选择上。

### 七、`content_sha256` 锚的是哪一刻——这个区别现在不重要，下一批会重要

`agent_verdicts.content_sha256` 现在的算法很直白：对刚生成的 `blob`
（也就是马上要存进 `verdict_json` 的那段文本）直接 `hashlib.sha256`。
这意味着它是**「这次写入的文本」的哈希，不是「这个对象」的哈希**——两者
今天恰好等价，只是因为序列化格式自建表以来没变过。

这一批刚把 `_canonical_dumps` 加了 `separators`（`payload_sha256` 特意
没跟着改，就是为了不制造这个问题——但 `verdict_json` 用的是新函数，
所以它自己已经踩过一次格式变化）。评审复核指出：**下一批**（A-II 的
A6，`VerdictRef` 上卡校验）如果核对方式是「重新序列化对象再比对」而不是
「直接比对存量文本的哈希」，这一批之前落库的行会集体核对不上，而且是
静默的——两串 sha256 都「看起来正常」。

这一批还不需要做任何事（今天没有代码会重新核对这个哈希），但**必须把
这个区别写下来**，否则下一批写 A6 的人会理所当然地假设「哈希是对象的
规范形式」，然后被 239 条历史行的静默核对失败反噬。写了一条注释和一条
钉住它的测试，比指望三个月后有人记得这茬更可靠。

## 坑

### 坑 1：`DecisionCard.from_dict()` 默认 `from_store=True`，写边界的重建不能照单全收

见上文「为什么这么做」第三节。第一版实现直接调用
`DecisionCard.from_dict(json.loads(payload))`，测试全绿——因为测试样例里
凑巧没有一条同时满足「新卡」+「篡改的是从宽路径才会检查的那类不变量」。
后来专门为这个场景写了一条探针（P2：BUY 卡事后塞入缺失项，这个维度
`save_card` 原有的身份检查完全不查）才发现问题。

### 坑 2：测试用例的 `card = {...}` 字典字面量被契约唯一实现的 AST 扫描拦下

`tests/test_readback_check.py` 里手工构造一份「毒卡」时，直接写了一个含
`decision_id`/`status`/`headline`/`verdicts`/`missing`/`synthesis`/`model_ref`
七个键的字典字面量——这正是 `test_contract_single_impl.py` 里
「手搓字典版契约」扫描器要抓的形状（铁律 4：契约只有一份实现）。

这次**不是**误报：这段代码看起来确实像是在手搓一个 `DecisionCard`。
唯一的区别是这里必须这么写——如果构造真正的 `DecisionCard` 对象，
`__post_init__` 会在到达「写进库」这一步之前就先一步拒绝它，测试的前提
（一行已经落库的毒卡）就搭建不起来了。加一行 `# contract-exempt:` 注释
说明原因，而不是去改扫描器——扫描器是对的，例外应该由写代码的人举手，
不是让判据自己变松。

### 坑 3：新增测试改变了实测条数，文档徽章要重新同步

`tests/test_docs_convention.py::test_文档里的测试条数与实测一致` 在全量跑时
报了实测数与文档不一致。这条测试的存在就是为了让这种漂移**在本地就报红**，
而不是留到评审时才被发现。跑一次 `tools/verify/sync_test_count.sh` 即可，
不需要手改任何数字。⚠️ 这个数字会随每一批新增测试再变——本章后续每加一条
探针的回归测试，都要记得重跑一次这个脚本，不要在验证小节里写死某个具体值。

### 坑 4：开工会话交出的两处修法，评审会话各挑出一处方向反了的

这一批做完、交给评审会话复核时，两处收窄类的修法都被指出**方向搞反了**：

1. **`from_store` 的档位建在了一个可写属性上**（见「为什么这么做」第三节
   末尾）——这是「加一层新校验」时最容易忽略的坑：新校验本身没写错，但它
   信任的输入（`card.from_store`）来自一个还能被随意篡改的对象，等于没加。
2. **`audit_public.sh` 的令牌判据收窄反了方向**（见第六节）——把「宁可错杀
   不可放过」的默认检查改成了「需要满足特定形状才命中」，用真实泄露形状
   一对照就能看出漏检面变大了。

两处的共同教训：**收窄一条已有检查的匹配范围时，要先问「这条检查的默认
值应该往哪边错」。** 安全类检查默认值该往「多疑」那边错（宁可多报，人工
排除误报），而不是往「精确」那边错（少报但可能漏掉真实泄露）——这与本仓库
「只追加触发器：新表默认就该受保护，例外要自己举手」是同一条原则，只是
第一次应用到「审查脚本自己的判据」上时，这条原则没有被自动想起来。

两处都在同一个工作session内、代码进入评审前发现并改正——过程记在这里，
是因为「明明推理很扎实,还是把方向搞反了」这件事本身值得记住，而不是假装
第一版就是终版。

## 本章要点

| # | 要点 |
|---|---|
| 1 | 校验点摆在**读**而不是**写**，会把一个可修复的错误变成不可修复的错误——尤其是对只追加表 |
| 2 | 挡住「构造合法、事后改字段」类篡改的唯一办法是**写入前重新构造一遍**，而不是指望 `__post_init__` 会被自动重跑 |
| 3 | 给一个从宽/从严两态的重建函数补校验时，**先确认重建走的是哪一态**——用错默认值，新加的校验对最该防的那类篡改反而无效 |
| 4 | 「这次改动不影响历史哈希」不能靠承诺验证——**改动前**生成的固定向量才是唯一可信的证据，而且不能在改完之后重新生成 |
| 5 | 严格 JSON 不等于把所有 `json.dumps` 调用改成同一套参数——**先看这个哈希有没有被用来跨时间比较**，用来比较的那个绝对不能动格式 |
| 6 | 「64 位十六进制」这类形状判据分不清令牌和内容哈希——补的不是豁免名单，是**上下文**（是不是一次赋值） |
| 7 | 测试代码手搓一个契约形状的字典是完全可能且必要的（模拟绕过契约层的毒行）——这时候该加的是 `contract-exempt` 注释，不是弱化扫描器 |
| 8 | 新增测试之后先跑一次全量 `pytest`，文档条数漂移会在本地就报红，不用等评审 |
| 9 | **收窄一条已有检查的匹配范围前，先问默认值该往哪边错**——安全类检查该往「宁可多报」错，反过来往「精确匹配才命中」改，等于把默认状态从「安全」改成「需要举证才安全」 |
| 10 | **给一段写入代码补校验时，校验依据的那个字段本身是否可信，和校验逻辑本身是否正确，是两件独立的事**——档位判断建在对象的可变属性上，比建在调用方传入的参数上更容易被绕过 |
| 11 | 「这个哈希今天等于对象重新序列化的结果」是**巧合**还是**不变量**，取决于序列化格式有没有被冻结——分不清这两者，下一批的人会理所当然地假设一个不成立的等式 |
| 12 | 审阅自己写的安全类判据时，找一份**真实的攻击/泄露形状清单**逐条对照，比读代码本身更容易发现「看起来更精确，其实是漏检」这类反向错误 |
| 13 | **豁免的粒度必须等于命中的粒度**——命中的单位是一个十六进制串，豁免就只能豁免那一个串；按整行豁免会让同一行里另一个真值被一起放过 |
| 14 | 描述「这条规则要防什么」时最容易顺手把真值写出来当例子——本仓库已经吃过五次这个亏，最脆弱的时刻恰恰是**写这条规则本身**的那次改动 |
