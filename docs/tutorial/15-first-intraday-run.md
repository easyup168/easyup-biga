# 第 15 章 · 第一次盘中运行：它找出了四个休市日永远找不到的问题

> **覆盖**：这一段是怎么建起来的 ｜ **不覆盖**：当前设计（见 [`../design/`](../design/architecture.md)）

> 对应 Phase 2 的 2.4 开工前：把前四个 Specialist 放到真实交易时段里跑一次。

## 目标 / 产出

- schema v4 `decision_ids` —— 决策编号的原子分配器
- 板块榜并发翻页：67.9s → ~19s
- 四个只在盘中才暴露的问题，其中一个是**数据正确性**级别的
- 一次「我自己违反了自己写的开发流程」的完整记录

## 为什么这么做

### 1. 前两次实测都在休市日，而我们拿它当了基线

2.3 做完时端到端 71.0s，预算 90s，看起来很健康。
设计文档里我写了一句提醒：

> ⚠️ 这个数字**是休市日测的**……盘中四个 agent 都要打实时接口，
> 延迟分布会不同 —— 出口条件 5 要的是盘中实测。

写下这句的时候，我以为它是一句谨慎的免责声明。

**盘中实测出来是 214.9s —— 超预算 2.4 倍，差了整整 3 倍。**

> 通用原则：**当你为一个数字写下「这个环境不代表真实环境」时，
> 你其实是在说这个数字没有意义。** 那就别把它写进验收表 ——
> 一个带星号的绿灯，过几周就只剩绿灯了。

### 2. 盘中窗口是稀缺资源，所以顺序要反过来

A 股一天只有 4 小时交易时段。这意味着：

- **能在任何时候做的事**（写设计、写测试、读代码）都要往后排
- **只有盘中能做的事**（打实时接口、跑端到端）必须先抢

所以这一章的施工顺序是反常的：先把端到端挂到后台跑，
再回头做 news 的数据源探活。等结果回来时，探活也做完了。

## 坑

### 坑 1 · 🔴 我违反了自己写进流程的第 6 条，于是造出了一个没见过的故障

开发流程第 6 条：**端到端必须开新会话且等结算**。这条是我写的。

第一次盘中 e2e 我直接敲了：

```bash
biga agent --agent main -m "..."
```

少了 `--session-key`。结果：

```
09:37:42→09:38:04  21.4s  main  stop=end_turn  session=main
```

用的是默认会话 `agent:main:main`，一轮 `end_turn` 就返回，`rc=0`，**输出为空**。
而四个 subagent 还在后台跑着。

看到 rc=0 又没出卡，我以为是命令没生效，**两分钟后又起了一次**。

于是两次运行交叠。而下面那个 bug，就是这样被触发的。

> **违反流程的代价常常不是「这次没做好」，而是「制造出一个你从没见过的故障」。**
>
> 这次是运气好 —— 它让我提前找到了一个真 bug。
> 但「靠运气发现」和「靠流程避免」之间，隔着的是下次会不会这么走运。

### 坑 2 · 🔴🔴 两次运行的证据被合成进了同一张卡

两次运行各出了一张卡。单独看，**两张都毫无异常**：五个 agent 齐全、
时间戳都在几十秒内、缺失项正常上浮、状态都是诚实的 `WAIT`。

对比才看得出来：

```
BIGA-20260921-006  09:40:57        BIGA-20260921-007  09:42:08
  technical  PASS  result#3b4dd3a0   technical  PASS  result#3b4dd3a0  ← 同一条
  sector     UNKNOWN                 sector     PASS                   ← 相反
```

两张卡**共用同一条 `technical` 判定原件**（result 哈希完全相同），
而且对 `sector` 给出相反的结论 —— 相隔 71 秒。

#### 根因有两层，只修一层不够

**表层**：五个 specialist 都写着 `new_task_id(1)` —— 序号硬编码。
所以所有判定原件的 `task_id` 全是 `-001`，任何两次运行都无法区分。

这个 bug **在 `synthesize.py` 上修过一次**。`next_decision_id()` 的
docstring 里甚至写着它的形状。而修的人没去查兄弟模块。

上一章（14 章）的要点 9 正是：

> **在一个 Agent 上修好的坑，去检查所有同类的 Agent。**

写下这条的人，在下一章就违反了它。⇒ 所以这次补的不是一句提醒，
而是一条 AST 测试：

```python
def test_没有人再硬编码序号1(self):
    bad = [...]  # 扫所有 skills/*/scripts/*.py
    assert not bad
```

> 通用原则：**「记住要检查兄弟模块」是一条靠记性的规则，所以它会失效。**
> 能机器化就机器化 —— 哪怕规则本身听起来根本不需要测试。

**根本**：编号原来在**合成时**才分配，而那时证据早就采完了。

> **一个决策必须在收集证据之前就有身份，否则证据无处归属。**

这条后来写进了 `architecture.md` §9 作为 **L-11**。

#### 修法：把守卫放在改不掉的地方

| 做法 | 为什么 |
|---|---|
| Stage 0 占号，沿全链下传 | 身份先于证据 |
| 占号靠**主键冲突**仲裁 | 「先查空位再插入」中间的竞态窗口正是本次事故的机制 |
| 临时号 `-000`，**自曝身份** | 原来的默认值 `-001` 看起来像个正经决策号 |
| 守卫放在 `save_verdict` | 五个调用点各写一遍默认值，正是同一个 bug 能活在五个文件里的原因 |
| 合成时拒绝混血 | 最后一道 |

**检查顺序也是设计的一部分。** 混血检查排在 stance 完整性检查之前 ——
证据来自两次运行时，先抱怨「缺 stance」会把人引向错误的修复：
补完 stance，真正的问题还在，而且更难看见了。

> **身份比完整性更根本。**

### 坑 3 · 慢的不是 Agent，是 skill —— 而且要拆到第三层才看得见

盘中 214.9s，`sector` 一个就占 113.6s。第一反应还是「提示词写得不好」。

按流程展开调用序列：

```
09:52:21  exec     sector_calc.py --task-id BIGA-20260921-009
09:52:37  process  {"action": "list"}
09:52:40  process  {"action": "poll", "timeout": 30000}
09:53:17  process  {"action": "log",  "limit": 5000}
09:53:22  process  {"action": "poll", "timeout": 30000}   ← 输出已经拿到了
09:53:51  exec     amend_verdict.py --ref 82 --stance 轮动分散
```

两次 30 秒的 `poll` 占了 60 秒。而 `01:53:17` 那次 `log` 已经拿到输出了 ——
第二次 poll 是纯粹的浪费。

但再往下一层才是真因：skill **自己就跑了 68 秒**，
超过运行时的阈值被自动转成了后台进程，agent 才不得不轮询。

再往下一层：

```
  industry    496 个板块  请求 5 次  网络 16.3s
  concept     504 个板块  请求 6 次  网络 42.5s
```

`fetch_boards` **串行**翻页，11 次请求、**58.8 秒纯网络等待**。

> 三层下来，第一层看到的是「agent 在 poll」，第三层才是「串行 HTTP」。
> **每一层看起来都像根因。** 停在任何一层，都会去优化一个不是瓶颈的东西。

### 坑 4 · 🔴 并发度调大反而更慢，而且单次计时看不出来

把翻页改成并发（4 个 worker），第一次测：**7.18s**。从 67.9s 到 7.18s，
提升 9 倍 —— 差点就这么写进 CHANGELOG 了。

多跑了两次：

| 第几次 | 耗时 |
|---|---|
| 1 | 7.18s |
| 2 | 25.17s |
| 3 | **60.10s** |

**单调上升。** 网络抖动是双向的 —— 只升不降说明是**渐进限流**：
打得越猛，对方限得越狠。

降到并发 2：

| 第几次 | 耗时 |
|---|---|
| 1 | 23.33s |
| 2 | 9.13s |
| 3 | 23.45s |

有起伏，不爬升。均值 ~19s，比串行快 3.6 倍。

> 通用原则：**调并发度必须连跑几次看趋势。**
> 单次计时分不出「这次快」和「还没被限到」。
> 而第一次测到的恰好是最快那次 —— 照它定参数，就是把限流当成了性能。

⚠️ 顺带测准了 14 章那个 `pz` 坑的精确边界：

```
  pz=100   实际返回  100 行  total=504  ✅ 兑现
  pz=200   实际返回  100 行  total=504  🔴 被截断
  pz=500   实际返回  100 行  total=504  🔴 被截断
```

硬顶在 100。页数减不了，只能折叠等待。

### 坑 5 · 我写的「乱序」测试没有在测乱序

并发拼页有个真实风险：用 `as_completed` 的**到达顺序**拼装，
同样的输入会产生不同的 `raw`，回放就对不上。

于是写了一条测试，再用探针验证它会红 —— 把字典构造改成倒序提交。

**测试没红。**

因为顺序保证根本不在字典怎么造，而在下面那一行：

```python
got = dict(zip(rest, pool.map(_one_page, rest)))
for pn in rest:                    # ← 保证在这里
    payload, page, t = got[pn]
```

换成真正的到达顺序才红：

```python
futs = {pool.submit(_one_page, pn): pn for pn in rest}
got = [(futs[f], f.result()) for f in as_completed(futs)]
```

> **探针不红时，先怀疑探针，而不是庆幸守卫很强。**
> 我拆掉的是一个根本不承担这个保证的地方 ——
> 那次「通过」什么也没证明。正确的探针已写进测试 docstring。

### 坑 6 · 🔴 盘中出不了有把握的卡 —— 而这是对的行为

修完上面所有问题，盘中端到端终于跑通了。结果 Card 还是 `WAIT`，
理由是四个 Specialist 报出了**两个交易日**：

| agent | `trade_date` | 为什么 |
|---|---|---|
| `emotion` | `20260921` | 实时涨跌停池 ⇒ 说的是**此刻** |
| `market` / `technical` / `sector` | `20260918` | 日线 ⇒ 今天的还没收，只能报上一个已完成交易日 |

`risk` 拒绝把它们当成同一天的事实一起审。这**完全正确** ——
把「此刻的情绪」和「上周五的技术面」并排当成同一天的证据，
本来就是在编造一个不存在的时点。

但它的含义要说明白：

> 按目前的构造，BigA **盘中出不了有把握的卡**。
> 不是因为哪里坏了，而是因为数值基准本身是分裂的。

两种解法都要改指标口径（盘中用分时合成未完成 K / 只在盘后出卡），
而口径一改，此前所有实测数字都不可比。⇒ 记入 Phase 3 待决，现在不选。

> 通用原则：**一个诚实的 `WAIT` 可能是在报告架构问题，而不是市场问题。**
> 区别在于它每次都出现，还是只在某些条件下出现。
