# 第 10 章 · 延迟与成本：先把账记对，再谈优化

> 📄 **过程** · 写完即冻结（只追加「⏩ 后续变动」指针）
> **覆盖**：这一段是怎么建起来的 ｜ **不覆盖**：当前设计（见 [`../design/`](../design/architecture.md)）


> **本章目标**：让「一次决策要多久、花多少钱」变成**可测量**的事实，
> 然后再决定要不要优化、优化什么。
>
> **本章产出**：一个延迟/成本分解工具、216s → 75s 的真实过程，
> 以及一个被证伪的验收指标。

---

## 1. 起点：一条写在验收标准里的红字

`architecture.md` §11.3 的第 7 条验收标准是：

> 单次端到端 **< 60s**（只有 2 个 agent，8 个时才允许到 105s）

跑完第 07 章的端到端之后，这一条是唯一没过的。Card 上写着「耗时 130s」。

自然的第一反应是「太慢了，去优化」。**先别动。**
在优化任何东西之前，必须先回答一个更基础的问题：

> **那个 130s，是测出来的，还是猜出来的？**

---

## 2. 第一个坑：系统自报的数字不是测量值

Card 上的耗时来自 `synthesize.py --elapsed-ms`，而这个参数是 **Supervisor 自己填的**。
它是一个 LLM 对「我刚才花了多久」的估计。

拿它和真实墙钟对了两次：

| 场次 | Supervisor 自报 | 真实墙钟 | 偏差 |
|---|---|---|---|
| A | 偏小 | —— | **低报 43%** |
| B | 130.0s | 74.8s | **高报 74%** |

它不是「有系统偏差、可以校正」，而是**两个方向都偏，且幅度不可预测**。

> **通用原则**：让被测对象自报成绩，得到的不是测量值，是作文。
> 任何进入验收判据的数字，必须来自**被测对象之外**的独立记录。

这条在 LLM 系统里尤其致命 —— 模型填一个看起来合理的数字，
不会报错、不会崩溃，只会让你对着错的数字做优化。

---

## 3. 去哪里拿真实的墙钟

OpenClaw 的 runtime 会把每一轮 LLM 调用写进 agent 库的 `trajectory_runtime_events`：

```sql
SELECT created_at, event_json FROM trajectory_runtime_events;
```

每个 `event_json` 是一条轨迹事件。需要的是两类，用 `runId` 配对：

- `prompt.submitted` —— 这一轮什么时候开始
- `model.completed` —— 什么时候结束，以及 `usage`（token + 成本）

于是有了 [`skills/_store/runtime.py`](../../skills/_store/runtime.py)：
一个**只读**的 runtime 读取器，把轨迹翻译成 `AgentTurn` 列表。

两个设计决定值得说：

**其一，它是只读的，而且在代码里标了 `# store-exempt:`。**
项目有一条铁律「业务代码不许出现裸 `sqlite3.connect`，一律走 `skills/_store/db.py`」。
这个文件是唯一的例外 —— 它读的是**别人的库**（OpenClaw 自己的状态），
不是 BigA 的数据。豁免必须在代码里显式标注，而不是让扫描规则去猜。

**其二，它有一个 `unavailable` 列表。**

```python
@dataclass
class RuntimeProbe:
    turns: list[AgentTurn] = field(default_factory=list)
    unavailable: list[str] = field(default_factory=list)
```

读不到某个 agent 的库、表结构对不上、事件缺字段 —— 这些都进 `unavailable`，
而不是静默返回一个短一点的列表。调用方必须先看它：

```
⚠️  运行时数据不完整，下面的分解**不可全信**：
    · agent=emotion: 轨迹表不存在
```

这就是第 03 章那条 `UNKNOWN` ≠ `PASS` 在观测工具里的样子。
**一份残缺却长着完整模样的报告，比报错危险得多。**

---

## 4. 怎么界定「一次决策」的窗口

有了全部轮次，还得知道哪几轮属于这一次决策。

Card 落库时记了 `generated_at`。窗口的另一端用 Supervisor 自报的 `elapsed_ms`
往前推 —— **这是那个不可信的数字唯一还有用的地方**：
它只用来划一个足够宽的框，框里的轮次再用真实时间戳算。
框划得偏大不影响结论，因为合计是按框内轮次的真实起止算的。

没有 `elapsed_ms` 时退回固定时长窗口，**并且必须在报告里说清楚**：

```
⚠️  这张 Card 的 elapsed_ms 是 0（Supervisor 没传 --elapsed-ms），
    只能按固定时长往前取窗口。**窗口里可能混进别的运行**，
    下面的合计数偏大，不可作为达标判据。
```

还有一个反直觉的细节，踩过才知道：

```python
# 🔴 按「区间重叠」而不是「结束时刻落在窗口内」：
#    Supervisor 是在自己那一轮的**中途**调 synthesize.py 落卡的，
#    所以那一轮的 ended_at 必然晚于 Card 的 generated_at。
#    用结束时刻过滤会把最关键的合成轮整个漏掉。
turns = [t for t in turns
         if t.ended_at >= start and t.started_at <= end]
```

用「结束时刻在窗口内」过滤，会把**最慢的那一轮**（合成轮）漏掉 ——
报告会显示一个漂亮很多的数字，而且不报错。

---

## 5. 两份独立记录要对账

轨迹是一份记录。OpenClaw 的调度器还有另一份 —— `subagent_runs` / `task_runs`。
两份都读，对不上就说：

```
⚠️  对账不一致 —— 调度器记录了下面这些执行，但 trajectory 里没有对应轮次：
      19:38:59–19:39:35 subagent emotion (ok)
      ⇒ 下面的合计**偏小**，缺了这些执行的耗时与成本。
```

> **通用原则**：观测工具自己也会坏。
> 只有一份数据源时，你无法区分「系统没干这件事」和「我没测到」。

## 6. 开始测：第一个假设错了

工具就位，第一次真实测量：**216.3s，$0.70**，Supervisor 光工具调用就 18 次。

最直觉的优化方向是**思考档位**（thinking）。输出 token 高 = 思考多 = 慢，
把 `agents.defaults.thinkingDefault` 从 `high` 降到 `medium`：

| 档位 | 墙钟 |
|---|---|
| high（基线） | 216.3s |
| medium | 139.8s?? |

——**根本不是 thinking 的功劳。** 同一档位重跑，数字在 120–216s 之间乱跳。
真正的变量藏在那 18 次工具调用里。

于是去看 Supervisor 到底在调什么。看完发现它在**自救**。

---

## 7. 真正的原因：延迟是正确性 bug 的症状

三个 bug，每个都不表现为「报错」，只表现为「慢」。

### Bug 1 · `decision_id` 撞号，Supervisor 每次都在自救

`synthesize.py` 里写死了 `new_task_id(1)`，所以一天里第二次决策必然撞上
`UNIQUE constraint failed: decision_records.decision_id`。

Supervisor 看到报错之后**没有放弃** —— 它去查库、看已用的编号、改参数、重试，
最后成功落卡。整个过程约 18 次工具调用、140 秒。

这是最危险的一类 bug：**系统"能用"，只是每次都要自救一遍。**
如果只看「有没有出卡」，它永远不会被发现。

修法不只是改代码，还要让错误**自己解释自己**：

```python
def next_decision_id(*, day=None, path=None) -> str:
    """扫当天已用编号，返回下一个可用的。"""
    ...
    used = {int(t) for r in rows if (t := r["decision_id"].rsplit("-", 1)[-1]).isdigit()}
    seq = next(i for i in range(1, 1000) if i not in used)
    return new_task_id(seq, day=day)
```

并且把 UNIQUE 冲突翻译成一句指路的话，而不是把原始 SQL 错误抛给 agent：

```
ValueError: decision_id BIGA-20260919-001 当天已存在。
            不要手工递增 —— 用 next_decision_id() 取下一个可用编号。
```

> **通用原则**：给 Agent 看的错误消息，要包含**下一步怎么做**。
> Agent 会认真读报错并自己想办法 —— 报错写得含糊，它就得花十几轮去猜。
> 这不是"AI 不够聪明"，这是错误消息的成本被记在了延迟账上。

**216.3s → 165.8s**，Supervisor 工具调用 18 → 5。

### Bug 2 · 相对路径 + 错误的工作目录 = `find /`

emotion 的 `AGENTS.md` 里写的是仓库根的相对路径：

```bash
python3 skills/emotion-calc/scripts/emotion_calc.py    # ❌
```

但 spawn 出来的 emotion，工作目录是它自己的 `agents/emotion/`。
脚本找不到，于是 emotion 开始**满文件系统找**，跑起了 `find /`。

修法是两条一起：

```bash
cd ~/.openclaw-biga/workspace && python3 skills/emotion-calc/scripts/emotion_calc.py
```

外加一句明确的禁令写进契约：**任何情况下都不要 `find /`。找不到就报缺失。**

> **通用原则**：给 Agent 的命令要么用绝对路径，要么自带 `cd`。
> "从仓库根执行"是给人看的说明，Agent 的 cwd 不一定在那儿。

**165.8s → 121.0s**，emotion 工具调用 10 → 2。

### Bug 3 · 自相矛盾的契约，让 Agent 被拒两次

emotion 的契约里同时写着两句话：

- 「技能返回的 JSON 原样透传，不要改」
- 「发现单日快照的局限要写进 `missing`」

而契约层的铁律是：`missing` 非空 ⇒ 不能是 `PASS`、不能是 `completed`。

于是 emotion 加了 `missing`、保持 `status: completed` ⇒ 被契约拒绝 ⇒ 重试 ⇒ 再拒。

这不是 Agent 的错，是契约写得自相矛盾。修法是把隐含规则**摆到台面上**：

| 你要做的 | 那么必须同时 |
|---|---|
| 往 `missing` 里加一条 | `status` 改 `partial`、`verdict` 改 `WARNING` 或 `UNKNOWN` |

**121.0s → 74.8s**，emotion 工具调用 2 → 1。

### 小结

| 测量 | 改动 | 墙钟 | main 工具调用 | emotion 工具调用 |
|---|---|---|---|---|
| ① | 基线 | 216.3s | 18 | — |
| ② | `decision_id` + 范例 | 165.8s | 5 | 10 |
| ③ | emotion 工作目录 | 121.0s | 4 | 2 |
| ④ | 契约自洽 | **74.8s** | **2** | **1** |

> **通用原则**：Multi-Agent 系统里，**延迟往往是正确性问题的症状**。
> Agent 不像函数那样"错了就崩"，它会重试、会绕路、会自己想办法。
> 这些努力全部记在延迟账上，而日志里一片祥和。
>
> 看到"慢"，先别调参数 —— 先去数工具调用次数，看它在忙什么。

## 8. 回头验证：thinking 到底是不是杠杆

bug 清完、噪声没了，再回来测一次 thinking。这次信号是干净的：

| 档位 | 等卡墙钟 | 输出 token 合计 | 卡的质量 |
|---|---|---|---|
| medium | **74.8s** | 6,731 | 13 证据 / 3 缺失 / WAIT |
| low | **79.3s** | 6,468 | 13 证据 / 3 缺失 / WAIT |

降档**没有变快**（79.3 > 74.8，差异在噪声内），输出 token 只少了 4%。

原因不难理解：到这一步，输出 token 已经由**实际产出**主导 ——
读技能返回的 JSON、写 13 条证据、写核心矛盾 —— 而不是由思考预算主导。
拧一个已经不是瓶颈的旋钮，不会有事发生。

> **通用原则**：先证明某个旋钮是瓶颈，再去拧它。
> 顺序反了，你会把噪声当成效果。

## 9. 成本的两个坑

### 坑一 · 缓存读和缓存写不能合成一列

`thinking=low` 那次测出来 **$0.4816**，medium 是 **$0.2179** —— 看上去贵了一倍多。

差点就得出「low 档更贵」这个荒谬结论。拆开看：

| 档位 | 输出 tok | 缓存**读** | 缓存**写** | 成本 |
|---|---|---|---|---|
| medium | 2,920 | 135,690 | 9,970 | $0.0950 |
| low | 2,746 | 46,511 | **50,298** | $0.1717 |

写缓存按 **1.25×** 基础费率计费，读缓存按 **0.1×** —— 差 12 倍。
测 low 之前重启过 gateway，提示词缓存是**冷的**，于是大量 token 走了"写"。

这跟 thinking 毫无关系。是我自己的报告把两列合成了「缓存tok」，把这事盖住了。

修法：拆成两列，并且自动识别冷启动：

```
⚠️  缓存写占比偏高 —— 这次多半是**冷启动**（刚重启 gateway / 改过配置 /
    换过提示词）。此时的**成本不可与热缓存的运行横向比较**；
    耗时受影响小，仍可比。
```

> **通用原则**：把计费方式不同的量合并成一列展示，等于制造了一个
> 会骗人的指标。**聚合之前先问：这些数字的单价一样吗？**

### 坑二 · 卡落库了，账还没完

翻轨迹时发现，Card 生成之后还有轮次：

```
19:39:36  main       30.0s  out=2920  $0.0950   ← 卡在这一轮落库
19:40:36  main        7.7s  out=9     $0.0451
19:42:44  main       11.1s  out=501   $0.0575
```

后两轮的 `runId` 长这样：

```
announce:requester-settle:...:yield-1:retry-1
announce:requester-settle:...:yield-1:retry-2
```

子 agent 全部 settle 之后，runtime 会**再唤醒一次** Supervisor，投递失败还会重试。
这些轮次**不该计入等卡时间**（卡早落库了），但**真金白银花掉了** ——
$0.1026，占一次决策总成本的 **32%**。

所以报告分两个口径：

```
      等卡墙钟   74.8s      预算 90s      ✅ 达标
      等卡成本 $0.2179

卡后尾巴 2 轮 · 18.8s · $0.1026（占决策总成本 32%）
     决策总成本 $0.3205
```

> **通用原则**：「用户等了多久」和「这件事花了多少钱」是**两个问题**。
> 异步系统里它们的边界不重合，用一个数字回答两个问题必然有一个是错的。

## 10. 最后：那个 60s 本身是错的

改完三个 bug、确认 thinking 不是杠杆之后，稳定落在 **74.8s**，
而验收标准写的是 **< 60s**。

按常规做法，这时候该继续削。但先做了一件事：**去查 60 这个数是哪来的。**

它来自 `architecture.md` §10.1 的分阶段预估表：

| Stage | 内容 | 预估 |
|---|---|---|
| 0 | Supervisor 拆任务 | 5-10s |
| 1 | 五个分析 Agent（×5 并行） | 20-40s |
| 2 | risk / discipline（×2 并行） | 15-25s |
| 3 | Supervisor 合成 + 渲染 | 20-30s |
| | **合计** | **60-105s** |

`5+20+15+20 = 60`，`10+40+25+30 = 105`。

**「60-105s」是下界之和与上界之和 —— 它是一个估计范围，不是一个预算。**
把 60 拿去当及格线，等于要求四个阶段**同时命中各自的最好情况**。

把实测按同样的阶段拆开，结论很清楚：

| Stage | 设计预估 | Phase 1 实测 | |
|---|---|---|---|
| 0 发出 spawn | 5-10s | **8.0s** | ✅ 区间内 |
| 1 emotion | 20-40s | **36.0s** | ✅ 区间内 |
| — 交接空档 | 未估 | 1.0s | |
| 3 合成 + 渲染 | 20-30s | **30.0s** | ✅ 压着上沿 |
| **合计** | | **75.0s** | ❌ vs 60s |

**每一个阶段都在自己的预估区间内，合计仍然 75s。**
没有任何一个阶段超支 —— 超的是那个加法。

还有第二处推理错误。原验收写「只有 2 个 agent，所以该 < 60s」，但：

- Stage 1 的下界 20s 描述的是「5 个并行 specialist 里**最快**那个」。
  Phase 1 只有一个 emotion，它就是 36s，**你没得挑**。
- Stage 0 + Stage 3 是**与 agent 数量无关的固定开销**，实测 38s，占 51%。

**减少 agent 数量并不会把总时间拉向下界。**
（反过来这也是好消息：加到 8 个 agent 时，这 38s 固定开销不变，
新增的 specialist 并行跑 —— 系统是能扩的。）

于是改判据，并写清楚为什么：

> 单次端到端 **< 90s**（热缓存，2 个 agent）—— 判据是 `latency_report.py` 的
> **等卡墙钟**，不是 Card 上 Supervisor 自报的 `elapsed_ms`。
> 90s = Stage 0/1/3 预估上界之和（10+40+30 = 80s）+ 10s 盘中网络余量。

八 Agent 的 105s **没有跟着改** —— 它出自同一套有问题的算术，
而且 Stage 3 在只有一个 specialist 时就已经压着 30s 上沿了。
那个数要等 Phase 2 有真实数据再推。**没有数据就不改，也不拿它当承诺。**

> **通用原则**：指标定不下来的时候，人会倾向于"先定一个，以后再说"。
> 问题是那个数字会活下来，变成硬指标，然后有人为了满足它去削系统。
>
> **发现指标错了，改指标是对的**，前提是：
> 说清楚原来的数怎么来的、错在哪、新的数怎么推出来的 ——
> 而不是悄悄把 60 改成 90。

## 11. 验证

```bash
cd ~/.openclaw-biga/workspace

# 最近一次决策的延迟与成本分解
python3 tools/verify/latency_report.py

# 指定某一次
python3 tools/verify/latency_report.py --decision-id BIGA-20260919-010

# 全量验收（第 8 项就是延迟）
python3 tools/verify/phase1_acceptance.py \
        --decision-id BIGA-20260919-010 \
        --baseline /tmp/neighbor_baseline.json --live
```

预期：

```
✅ 8. 单次端到端 < 90s（真实墙钟）
      74.8s（3 轮，$0.2179）；Supervisor 自报 130.0s
──────────────────────────────────────────────────────────────
PASS 9  ·  FAIL 0  ·  PENDING 0
```

注意最后那句 `Supervisor 自报 130.0s` —— **它被保留在输出里**。
自报值和实测值的差距本身是有价值的信息，不该因为"我们现在用实测了"就把它藏掉。

## 本章要点

1. **让被测对象自报成绩，得到的是作文不是测量值。** 判据必须来自外部记录。
2. **Multi-Agent 系统里，延迟常常是正确性 bug 的症状。** Agent 会自救，
   自救的代价全部记在延迟账上，日志里却一片祥和。看到慢，先数工具调用次数。
3. **先证明旋钮是瓶颈，再去拧。** thinking 在这里完全不是杠杆。
4. **聚合之前先问单价是否相同。** 缓存读/写差 12 倍，合成一列就成了骗人的指标。
5. **"用户等了多久"和"花了多少钱"是两个问题。** 异步系统里边界不重合。
6. **发现指标错了，改指标是对的** —— 前提是把推导过程写下来。
