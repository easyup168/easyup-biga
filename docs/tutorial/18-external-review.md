## 一、为什么要请外人

到第 17 章为止，项目已经有 400 多条测试、九项公开审查、四项隔离自检，
文档里还专门有一节「失败模式清单」。**自检的结论是：一切良好。**

然后外部评审报了 23 条，其中 7 条高危。

> 🔴 **这不是「测试写得不够多」。**
> 每一条被报出来的问题，都落在某条**已经存在的守卫**的视野之外，
> 而那条守卫自己是绿的。

最典型的一条：项目最看重的不变式 I-1（不得写已有实例的文件）有一个
可执行判据、写进了 `CLAUDE.md` 的「改动环境后跑一次」。
评审现场重放了它的判据，然后指出：

```
排除真实网关后，仍被判定为 BigA 进程的数量: 10
若排除真实网关，I-1 仍会判定为 ✅ 通过： True
```

那 10 个是编辑器、终端、以及评审会话自己 —— 纯粹因为 cwd 在仓库里。
**真网关早已崩溃时，这项检查照样报「检查了 N 个进程，✅ 通过」。**

它验证的其实是「我这个终端没有泄漏 fd」，这几乎永远为真。

> 通用原则：**一个几乎永远为真的检查，和没有这个检查，信息量相同。**

## 二、评审提示词怎么写

完整版在 [`../guide/review-prompt.md`](../guide/review-prompt.md)，这里说三个设计决定。

### 2.1 最重要的一句是警告，不是任务

```
🔴 这个仓库的文档非常详尽、而且高度自省 —— 它会主动列出自己踩过的坑。
   这很容易产生一种错觉：「他们连这个都想到了，那应该没问题」。
   但「把问题写进文档」和「把问题解决掉」是两回事。
   ⇒ 不要以文档为准。以你自己跑出来的结果为准。
```

**没有这段，评审会变成文档朗读。** 一个自省的项目对评审者是有麻痹作用的：
它把话都说尽了，看起来只剩下认同。

### 2.2 明确告诉它「不要从教程开始读」

```
不要从教程开始读（docs/tutorial/，17 章）—— 它是过程记录，
读完你会获得建造者的视角，而那正是评审要避开的。
```

教程写得越好，这条越重要。**共情是评审的敌人。**

### 2.3 给出「已知问题」清单，明确说不要重复报

八条已知问题直接列出来。理由不是省时间，是**逼它去找别的**：
不给这张表，报告里会有一半是我们早就写在文档里的东西，
而那会让人误以为评审很彻底。

### 2.4 要求的输出格式里有一条别人不会要的

```
为什么现有守卫没抓到 —— 这条最重要
```

「有 bug」是结论，**「为什么我们的防线没发现它」才是可以改进的东西**。
23 条发现里价值最高的部分全部来自这一栏。

## 三、23 条发现归成七类

逐条修法在 `CHANGELOG.md`，这里只讲**形状**。

| 类 | 条数 | 形状 |
|---|---|---|
| 自检工具自己会自欺 | 3 | 检查在「什么都没扫到」时报绿 |
| 看起来正常的错值 | 2 | 有值、格式完整、量级荒谬或排名任意 |
| `as_of` 归属 | 3 | 一个今天的数挂着上一个交易日的时间戳 |
| **清单不会自己长大** | 4 | 手写名单不随组件数量增长而同步 |
| 守卫的边界 | 4 | 名字暗示的范围比实际验的大 |
| spawn 证明 | 1 | 自己写的表证明不了自己 |
| 文档与体验 | 5 | 点名了不存在的文件、数字漂移 |

### 3.1 出现最多的那个：手工维护的名单

评审自己归纳的一段，值得原样抄下来：

> **手工维护的名单**（测试的 parametrize 列表、运行时配置的 allow 数组、
> 架构文档里的组件清单、同一不变式的重复实现）**不会随组件数量增长而
> 自动同步**。而且这个形状里至少有两处是「一个坑已经真实炸过、
> 专门补了守卫，另一处结构相同的地方至今没人管」。
>
> 这比任何一条单独的发现都更值得记住：清单类约定第一次踩坑后，
> 团队本能地去补**那一个**，而不去问「还有哪些地方是同样的结构」。

实例：

- 一条配置漏了某个 agent 导致端到端少 spawn 一个 —— 为此写了守卫。
  **姊妹配置**是同一个形状的第二处名册，全仓没有任何测试碰过它，实测确实也漏了同一个。
- 契约文本检查的清单是**手写的三条**，而契约有六份，自第四份建立起从未更新。
- 词表校验「命中才查，命不中就放行」—— 下一个 agent 忘记登记时静默失效。

修法统一成一句：**默认纳入，例外自己举手。**

| 原来 | 改成 |
|---|---|
| 手写「要查哪几个」 | 扫目录 / 扫 `sqlite_master` / parametrize 到常量表自己 |
| 漏掉的悄悄不查 | 例外必须写进 `EXEMPT` 或行内标记 |

### 3.2 判据要落在**要害**上，不只是覆盖面

同一条发现（契约缺了一句话）有两个改法，只做第一个不够：

```
① 清单从手写三条 → 扫目录          ← 覆盖面
② 判据从「提到了 verdict_ref」→ 字面量 `verdict_ref=NN`   ← 要害
```

**只做 ①，那份契约仍然会通过** —— 因为 "verdict_ref" 这个词在它里面
本来就出现 3 次，全在示例段落里。纯子串匹配检查的是「提到了这个词」，
而不是「讲清楚了第一次去哪拿」。

> 🔴 覆盖面上去了不等于判据对了。**先问「它到底在比什么」。**

## 四、🔴 修复过程本身翻了五次车

这一节是本章的核心。**五次都是同一个形状，五次都由探针抓到。**

| # | 我写的守卫 | 它实际查的 | 探针怎么戳穿 |
|---|---|---|---|
| 1 | 量级围栏 | 围栏函数本身 | 删掉产品线里那行调用，**一条都没红** |
| 2 | raw 层时刻归属 | 手工探针验过是对的 | 改回旧写法，**一条都没红** |
| 3 | spawn 证明 | 表名在文件里出现过 | docstring 里也有那名字，改查询照样绿 |
| 4 | 幽灵文件检查 | 反引号里的路径 | 而要找的幽灵写在目录树里，是**裸文件名** |
| 5 | spawn 证明（第二次） | agent 名出现在最近记录里 | **伪造一个决策号也能通过** —— 见下节 |

> 🔴 **守卫查的地方，和它声称守的地方，不是同一处。**
> 五次里有三次是「测了函数，没测产品线真的走了这个函数」。

### 4.1 第 1 次：测了函数，没测调用

围栏函数被测得很细：干净窗口不报、坏 tick 报、真实腰斩不误报、
中位数不被单根极值带偏 —— 六条测试。

然后把 `technical_calc.py` 里**调用它那一行**删掉：

```
python3 -m pytest tests/test_technical_calc.py tests/test_sanity_fence.py
  0 条红
```

补了一条走完整 `build_verdict()` 的回归测试才真的会红。

> **测函数，和测「产品线上真的走了这个函数」，是两件事。**
> 前者让你放心，后者才是守卫。

### 4.2 第 4 次：检查上线时什么都没查出来

「设计文档不许点名不存在的文件」这条，第一版只匹配反引号里的完整路径。
而评审报的那两个幽灵文件，写在 ASCII 目录树里：

```
│   └── verify/ placebo.py  reachability.py  isolation.py
```

**裸文件名，一个反引号都没有。** 上线时它一个都没查出来，
而我差点就当成「通过了」。补了按 basename 比对 `git ls-files` 的第二条路之后，
当场扫出 **6 个**（评审只报了 2 个），其中四个是
「由 `tests/xxx.py` 钉住」这种陈述句 —— 而那些测试文件都不存在。

> 🔴 **评审找到的是样本，不是全集。** 人去找的时候，也只找得到想到过的那几个。
> ⇒ 拿到评审结论后，**先给那一类上一条机器判据，再看它扫出多少。**

## 五、被外部复查推翻的那次修复

第一轮 23 条修完之后，请同一个评审做了**复查**。它推翻了其中一条。

### 5.1 问题

「Specialist 真的被 spawn 了吗」这条，第一版做得看起来很扎实：
覆盖全部 6 个 specialist、判据取自契约的 stage 名单（会自己长大）、
接进了出卡流程（每次出卡都跑）。

复查指出：**它不按决策号绑定。** 它只问「这个 agent 名字有没有出现在
最近 50 条运行时记录里」。

复现只要三行：

```
伪造决策号 BIGA-20260921-901，用合法 API 写 6 行执行账本
→ spawn 核验：6 个 agent 两份独立记录都齐   ✅ 通过
```

伪造的号**蹭上了别的决策的真实记录**。而出卡命令正常使用本来就会反复运行 ⇒
这个条件在真实机器上**几乎总是成立**，不是刁钻场景。

最讽刺的是：决策号本来就**明文写在运行时记录里**，一个 `WHERE` 就能绑，
我没绑。

### 5.2 为什么我自己的测试发现不了

这才是要记的部分。第一版的测试是这么写的：

```python
monkeypatch.setattr(pa, "_runtime_spawn_records",
                    lambda: [{"child_session_key": a, ...} for a in AGENTS])
```

它 fake 的是**取记录那个函数本身** —— 而「按决策号过滤」正是那个函数的职责。
于是测试把要验的那段逻辑**整个绕过去了**，还看起来测得很全（7 条）。

改法：造一份**真的 sqlite**，字段形状照抄真库，让被测代码走完整查询路径。
然后退回旧实现 —— 4 条当场红。

> 🔴 **假的东西造得太靠上，测的就是自己写的假货，不是产品代码。**
> 判断「fake 该放在哪一层」的方法：**被 fake 掉的那部分，就是你没在测的部分。**

### 5.3 顺带撞出第二个 bug

写伪造探针时，中间有一步账本还没写入，输出是：

```
▸ spawn 核验：0 个 agent 两份独立记录都齐 []
退出码=0
```

**「无事可查却报绿」，出现在一个专门为了防造假而写的工具里。**

修的时候顺手把三态分清楚了，而这个区分本身值得单列：

| 情形 | 判定 | 为什么必须分开 |
|---|---|---|
| 读不到运行时库 | 判不了（rc=2） | 环境问题，不是造假 |
| 库能读、本决策零记录、而账本有行 | **伪造**（rc=1） | ← 关键 |
| 两边都空 | 判不了（rc=2） | 什么都没发生 |

> 🔴 **「判不了」会被忽略，「伪造」不会。** 把后者报成前者，等于没报。

## 六、诚实地结账：不要用「全部修完」

第一轮修完，台账写的是「**23 / 23 全部处理完**」。

复查给了另一个口径：

| 档 | 数量 | 含义 |
|---|---|---|
| ✅ 模式级修复 | 15 | 根因消除，同形状的下一例也会被挡住 |
| 🔶 **实例级修复** | 7 | **报出的那个场景堵上了，模式还在** |
| ⬜ 诚实标注修不干净 | 1 | 代码注释里自己写明防不住 |

中间那一档是这次最该学的东西。举两个例子：

- 量级围栏：**压缩了错误的量级，没有消除错误** —— 5 倍以内的坏值照样过
- 第二处名册对账：**清单式检查只加固了这一个字段**，第三处名册出现时同样没人管

> 🔴 复查的原话：**修复清单类问题最容易的坑就是「治好这一例，模式还在」——
> 而这次修复过程本身又踩了一遍。**

把这一档单独列出来，就是不让它被「23/23」这种数字盖住。
**一个混在一起的百分比，会让最需要继续做的事看起来已经做完了。**

### 6.1 还有一件事：被表扬的那条

评审单独表扬了一条**没有解决**的问题：教程里「不许写同机已有实例细节」
的检查是一份 8 词黑名单，同义改写即可通过。

代码注释里写着：

```python
# ⚠️ 这条没有彻底的解法 —— 目标是开放式自然语言，
#    不像开关名那样有稳定锚点可以切换过去。
#    - 能挡住：顺手写出常见措辞（绝大多数真实情况）
#    - 挡不住：刻意的同义改写
```

复查证实这个自我评估是诚实的。

> **说清楚守卫挡不住什么，和让它挡住更多，是同等的工程贡献。**
> 一个被高估的守卫比没有守卫更危险 —— 它让人不再去想这件事。

顺带做了件能做的：措辞挡不住，但**路径和端口是确定的字符串**。
补了一条可判定的兜底，当场扫出 4 份教程里的真实泄漏。
