## 一、为什么这六条值得单独一章

第 18 章的 23 条大多是「某个数算错了」「某个字段没守」。
这一轮的六条是另一个层级：

| # | 发现 | 它的形状 |
|---|---|---|
| 1 | `spawn_check` 不是闸门 —— 退出码被丢掉 | 检查跑了，**结果没人用** |
| 2 | 没有 `.git` 时十几条守卫集体 error | 守卫在**与自己无关的原因**上崩掉 |
| 3 | 声称离线的单测真的在连新浪 | 规则只写在 docstring 里，**没有执行者** |
| 4 | 巡检工具的「判不了」和「不通过」同码 | 三态在渲染层对了，**在调用层塌回两态** |
| 5 | 已被推翻的口径还在三处代码里 | 改口径是全仓动作，**人只改自己正看着的文件** |
| 6 | risk 的 fail-closed 是「半硬」的 | 标签说不知道，**载荷说得头头是道** |

六条归成一句话：

> 🔴 **守卫查的地方，和它声称守的地方，不是同一处。**

这句话在本仓库已经出现十次。它终于有了编号 —— **L-13**。

### 为什么这一类最难自己发现

因为它**不产生任何异常信号**。

守卫存在、名字取得很准、测试全绿、CI 也绿。你去读它，它确实在 assert 某个东西。
唯一的问题是那个东西**不是坏掉时会变化的那个东西**。

拿第 1 条当例子。当时的守卫是这么写的：

```python
def test_出卡流程真的会调它(self):
    text = (REPO / "bin" / "biga-card").read_text(encoding="utf-8")
    run = text.split("# ── 出新卡")[1]
    assert "tools/verify/spawn_check.py" in run
```

看起来完全合理：「确认出卡流程真的会调它」。而 `bin/biga-card` 里是：

```bash
$PY tools/verify/spawn_check.py "$NOW"      # 裸调用
echo "▸ 延迟与成本：…"
exit 0                                       # ← 无条件
```

脚本用的是 `set -uo pipefail`（**没有 `-e`**），于是：

```
spawn_check exit 1（有伪造）  →  biga-card 仍 exit 0
spawn_check exit 2（判不了）  →  biga-card 仍 exit 0
```

真实语义是「跑了一次检查并打印结果」。而守卫查的是**字符串在不在** ——
字符串一直都在，所以它永远绿。

> 一条**不会红**的守卫，比没有守卫更糟：
> 它占着「这件事已经有人管」的位置。

## 二、为什么这么做：判据该落在哪里

修法不是「把守卫写仔细一点」。仔细也会漏 —— 十次里有七次都是当时觉得已经很仔细了。
真正的变量是**判据的种类**。

| 想守的东西 | ❌ 会漏的判据 | ✅ 有效判据 |
|---|---|---|
| 这个检查被用上了 | 源码里有没有这个字符串 | 它的**退出码**改变了流程（行为测试） |
| 这条围栏生效了 | 函数单测 | 从**真实调用点**走进去 |
| 这个口径只有一份 | 文件名里有没有关键词 | AST 扫描（第二份实现常常改了名） |
| 这些测试不许联网 | 在 docstring 里写一句 | **进程内拦 socket**，违规就红 |
| fail-closed 生效了 | 断言 `verdict == "UNKNOWN"` | 断言**载荷里一个派生字段都没有** |

三个例子展开讲。

### 2.1 「不许联网」原来只是一句话

两个测试文件的开头各写着：

```python
🔴 这些测试**不许联网**。理由不是速度，是可信度：
```

而在这一章之前，**没有任何东西执行这句话**。

评审就是这么抓到的：`test_sanity_fence.py` 里那条「资金侧失效时不给排名而是报缺失」
只桩掉了 `fetch_boards`，而 `build_verdict` 并发跑三个 job ——
`collect_date` 那一路照样真的去连新浪。

> 这是同一形状的**最纯形态**：声称的那一处根本没有守卫。

判据搬进进程里（`tests/conftest.py`，autouse fixture，拦 socket 三个入口）。
围栏一跑就命中评审报的那一条，**而且只命中它** —— 零误报。
那是围栏本身最好的验证：它复现了一个已知实例，没有顺带抓出一堆无辜的。

> 通用原则：**规则写在注释里，等于没写。**
> 一条规则要么有执行者，要么就承认它只是建议。

⚠️ 围栏有明确的边界，必须写出来：它跨不过 `fork`。
`subprocess` 起的子进程不受保护 —— 那类测试要自己把会联网的东西换成桩。
不写这条，下次就会有人以为「有 conftest 就安全了」。

### 2.2 三态在每一层都要是三态

红线 R-3 是 `UNKNOWN ≠ PASS`。工具们在**打印**上早就照做了（「🔶 判不了」到处都是）。
评审指出 `latency_report.py` 读不到运行时数据时退 `1` —— 和「Stage 1 真的串行了」同码。

顺着这条线扫一遍，同形状**一共四处**。最说明问题的是这一处：

```python
elif tally["PENDING"]:
    # 🔴 PENDING 不算 PASS。这条是本项目的第一条红线。
    print("\n⏳ 尚未判定完毕 —— PENDING 不等于通过。")
...
return 0 if tally == {"PASS": len(checks), "FAIL": 0, "PENDING": 0} else 1
```

**注释是三态的，代码是两态的。** 紧挨着。

修法不是逐个改数字，而是给这套口径一个**唯一定义**（`tools/verify/_verdict.py`），
再用 AST 钉住：`main()` 里不许出现裸整数退出码。

为什么要 AST 而不是「有没有 import」：
只查 import 挡不住「import 了、但某个分支还是 `return 1`」——
那正是这一章要防的东西本身。

> 通用原则：**最常见的读法是「跑完没报错就是过了」，读的正是退出码。**
> 三态只做到渲染层，等于没做。

顺带定了一条更实用的东西 —— 两个非零码的区别是**排查方向**，不是严重程度：

```
1  去看代码 / 配置（确实观察到了违规）
2  去看数据、环境、时机（没查成）
```

最常见的 `2` 是「报告跑早了，Supervisor 那一轮还没写进 trajectory」，等十几秒就好。
把它读成「坏了」会让你一开始就走错方向。

### 2.3 「半硬」的 fail-closed

第 18 章加过一道 Stage 边界的身份守卫：risk 发现上游判定来自别的决策时，
报缺失并把结论压成 `UNKNOWN`。

评审指出它是**半硬**的。检测到之后它**照样把全套指标算完**，最后才改标签：

```
verdict:    UNKNOWN
result:     coverage_ratio=1.0, trade_date_consistent=True,
            max_staleness_sec=…, tripped_thresholds=[volume_spike]
confidence: 0.9          ← 由 len(result) 算出来的
warnings:   [异常放量…]   ← 从别的决策的证据里算出来的
```

每个数字都是把两次决策的证据**混在一起**算出来的，而它们和正常判定**逐字段同形**。

> `verdict` 说「不知道」，`result` 说得头头是道。
> 只要有一个消费方读后者不读前者，fail-closed 就漏了。

而消费方不止一个：回放脚本、缺失项台账、将来的模型分层。

改成硬的 —— 检测到就立刻返回，`result` 里只留「归属本身」。
归属是关于**这次混淆**的事实，不是关于市场的事实，所以它可以留，而且必须留：
否则读卡的人只知道「不知道」（报错要指路）。

## 三、坑

### 3.1 契约层顶回来了一次，而它是对的

硬 fail-closed 的第一版把两个归属字段塞进 `result`、`evidence=[]`：

```
ValueError: [risk] result 字段无证据支撑: ['foreign_task_ids',
  'upstream_attribution'] —— 已有证据覆盖 []。无据之言不入 Card（铁律 3）
```

第一反应是「加个豁免」或者干脆 `result={}`。两个都不对：

- 豁免会在铁律上开一个口子，而铁律的价值全在没有例外
- `result={}` 会把排查需要的信息一起扔掉

正解是**老实给证据**：归属确实是 risk 在 `retrieved` 这一刻亲眼看到的，
它有正当的 `as_of`。

> 通用原则：**契约报错时先假设契约是对的。**
> 它拦下来的多数不是「不让我写代码」，而是「你正在写的东西缺了一个必要的部分」。

### 3.2 探针第一次红，红的是探针自己

「旧口径不许再出现在活文档里」这条守卫第一次跑就报了一处违规：

```
· tests/test_store.py:319
```

去看那一处，它明明白白写着「第 7 章在端到端实测时**推翻了它**」。
是守卫的**词表**少了「推翻」这个词。

照着守卫直接去改代码，就会把一段正确的文字改坏。

> ⚠️ **探针第一次红的时候，先怀疑探针，再怀疑代码。**

### 3.3 第一个探针没红 —— 因为窗口开得太宽

那条守卫的第一版判据是「这一句附近 ±6 行有没有人澄清过」。
探针（把 `SKILL.md` 的旧句子放回去）**照样绿** —— 下方的修正块还落在窗口里。

而那恰好就是 `db.py` 的病：旧断言与修正**同时存在**，一个 docstring 里两句话互相打脸。

> 判据必须是「这一句**自己**带着历史框」，不是「附近有人澄清过」。

收紧到 ±2 之后两个探针都红了。
**如果没跑探针，这条守卫会以「已修复」的身份留在仓库里。**

### 3.4 `'markers' not in s` 被子串匹配骗了

给 pytest 注册 `network` 标记时，判断「有没有注册过」写的是：

```python
if 'markers' not in s:   # ❌
```

而 `addopts` 里有 `--strict-markers` —— **它包含 `markers` 这个子串**。
条件恒假，注册从来没写进去。表现是一条 `PytestUnknownMarkWarning`，
而 `-q` 下它很容易被当成噪音划过去。

### 3.5 嵌套 f-string 把外层字符串提前闭合

用 `python3 - <<'PY'` 做字符串替换时，替换文本用了 `'''…'''`，
而文本内部又有 `seed.write_text(f'''…''')` —— 外层字符串在那里就结束了：

```
File "<stdin>", line 44
    import sys; sys.path.insert(0, {str(work / "skills")!r})
                                                        ^
SyntaxError: invalid syntax
```

改成先把内容写进一个文件、再拼接。
**「用脚本改脚本」省下的时间，经常在引号上还回去。**

## 四、执行

```bash
# ① 出卡闸门：行为测试，不是字符串检查
python3 -m pytest tests/test_spawn_proof.py -q

# ② 禁网围栏（围栏自己的守卫）
python3 -m pytest tests/test_no_network.py -q

# ③ 没有 .git 也要能跑 —— 真的剥掉 .git 跑一遍别的守卫
python3 -m pytest tests/test_scan_fallback.py -q

# ④ 退出码三态
python3 -m pytest tests/test_verify_exit_codes.py -q

# ⑤ 旧口径不许复活 + risk 硬 fail-closed
python3 -m pytest tests/test_risk_check.py -q
```

每一条都配了探针。以第 ① 条为例：

```bash
# 把闸门拆掉（退回裸调用 + 无条件 exit 0）
python3 -m pytest tests/test_spawn_proof.py -q
#   FAILED …::test_核验失败时出卡命令必须失败[1-有伪造]
#   FAILED …::test_核验失败时出卡命令必须失败[2-判不了]
# 恢复
#   21 passed
```

⚠️ **验证 fail-closed 的测试，本身不能有 fail-open 的代价。**
第一版的闸门测试直接跑了真实出卡路径 —— 守卫一坏，测试就会**真的花钱**。
改成两个桩：`BIGA` 换成一个往临时库里落一张真卡的脚本，
`spawn_check.py` 换成一个按参数退码的桩。全程不联网、不花钱。

## 本章要点

| # | 要点 |
|---|---|
| 1 | **守卫查的地方，和它声称守的地方，不是同一处** —— 本仓库出现十次的失败模式，编号 L-13 |
| 2 | 一条**不会红**的守卫比没有守卫更糟：它占着「这件事已经有人管」的位置 |
| 3 | 判据的**种类**比判据写得细不细更重要。字符串存在性、文件名、函数单测都是会漏的种类 |
| 4 | **规则写在注释里等于没写。** 「这些测试不许联网」写了很久，没有任何执行者 |
| 5 | 围栏的**边界**要写出来。进程内的猴补丁跨不过 `fork`，不写就会有人以为已经安全 |
| 6 | 三态在**每一层**都要是三态 —— 最常见的读法是「跑完没报错就是过了」，读的正是退出码 |
| 7 | 两个非零退出码的区别是**排查方向**（`1` 去看代码，`2` 去看数据与时机），不是严重程度 |
| 8 | fail-closed 不能只改标签。**载荷里留着看似正常的派生数字**，任何不读标签的消费方都会照常用它们 |
| 9 | fail-closed 也不等于一片空白 —— 要留下「谁串进来了」这类**关于故障本身**的事实 |
| 10 | 契约报错时**先假设契约是对的**。铁律 3 那次拦得准，正解是补证据而不是开豁免 |
| 11 | **探针第一次红，先怀疑探针。** 照着一个有 bug 的守卫改代码会把正确的东西改坏 |
| 12 | 探针**没**红也是结论：那条守卫的窗口开得太宽，差点以「已修复」的身份留在仓库里 |
| 13 | 改一条口径是**全仓动作**。人只会改自己当时正看着的那个文件 ⇒ 判据要落成测试 |
| 14 | 验证 fail-closed 的测试，自己不能有 fail-open 的代价（第一版会真的花掉 $1.37） |
