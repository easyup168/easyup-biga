## 为什么这么做

### 1. 契约只查了「有没有证据」，没查「证据支不支持」

铁律 3 一直是「`result` 的每个键都要有同名 Evidence」。评审 §16 指出它漏了后半句：

```python
result["market.x"] = 100
Evidence(field="market.x", value=1)     # 同名证据在，值差一百倍
```

这份事实能被构造、落库、上卡，而**每一道既有检查都通过**。

> 🔴 **「有证据」和「证据支持这个结论」是两件事。**
> 只查前者的检查读起来像在验证，实际只验证了「字段名对上了」。

判据取 canonical JSON 而不是 `==`，理由是**要和回放比对同口径**：回放比的是序列化
之后的字节，两处口径不一致就会出现「契约说相等、回放说不等」。代价是 `1` 与 `1.0`
算不同 —— 实测生产库 411 个字段全部满足，0 个例外，所以这个严格度是免费的。

### 2. 🔴 我把「相等」和「合法」搞混了一次

第一版用 `allow_nan=False` 序列化。NaN 序列化失败 → 退回 `==` → 而 `nan != nan`
⇒ 一份 result 与 evidence **本来就是同一个 NaN** 的事实被判成「对不上」，
实测当场打红 `TestP4StrictJSON` 六条 —— 那几条测的是**写边界的严格 JSON**，
被我这道检查抢在前面报了个不相干的错。

> 通用原则：**一个检查只回答一个问题。**
> 「这两个值一不一样」和「这个值合不合法」是两件事，合法性有它自己的那道检查
> （写边界 `allow_nan=False`）。混进来的结果不是更严格，是**把别人的错误报成自己的**。

改成 `allow_nan=True` 之后，NaN 两边都序列化成 `NaN`、相等，合法性照旧由写边界拒。

### 3. 更正：我上一轮报的「缺席被合并」是错的

我在三轮复核里说过「五个 agent 缺席可能在卡上只显示成一条」，依据是
`MissingItem.__eq__` 只看 `.code`，以及 `card.py` / `replay.py` 里的两处 `set()`。

**端到端复现证明这个结论不成立**：

```
编排器造出来的 extra_missing：5 条
裸 set() 之后：1 条            ← 我当时引用的就是这个数
🔴 真正落到卡上的 missing：5 条   ← 一条不少
```

`card_ops.synthesize()` 按「**代码 + 文本**」复合键去重，文本不同就都留着。

> 🔴 **我把一个局部属性（`MissingItem` 的判等口径）当成了端到端的数据丢失。**
> 那条属性是真的，推论不是 —— 中间隔着一层复合键去重，而我没走完全链路就下了结论。
> 教训不是「别相信局部观察」，是**局部观察只能支撑局部结论**；要说「卡上会少一条」，
> 就得真的造一张卡出来数。

### 4. 真正的洞在旁边：条数够了，但对不上号

```
absent  = [market, news, sector, technical, emotion]   5 个缺席
missing = 5 × risk.upstream.coverage_incomplete        5 条毫不相干
⇒ 旧判据（比条数）放行
```

`_check_roster` 当时**只能**比条数 —— 因为按文本去猜「这条 missing 说的是不是那个
缺席的 agent」是 L-13（按字符串形状分类），那条纪律不能破。代码自己的 docstring 也
承认了这个口子。

⇒ 解法不是去破 L-13，是**把需要判断的东西挪进结构**：agent 名字进代码
（`supervisor.<agent>.agent_no_response`），对应关系变成解析而不是猜测。

> 通用原则：**「只能靠猜文本」往往意味着信息放错了位置。**
> 与其改进猜的算法，不如让生产方把那个信息写进结构化字段 ——
> 前者永远是启发式，后者是判据。

### 5. 收紧判据的真实成本：25 处凑数占位

十一个测试文件里约 25 处写着 `missing=[f"占位{i}——本文件不测 roster" …]`。
那是在旧的计数判据下凑条数用的，而它**正是新判据要拦的东西** —— 也就是说，
这些夹具一直在演示那个洞。统一换成 `tests/_roster.py::absent_registrations()`
之后，卡上登记的就是真的缺席的那几个，对测试本身无损、对读者更诚实。

## 坑

1. **sabotage 报了一次假阴性。** S1 用 `for _ in ():` 去禁用循环，结果 `-k` 选中的
   六条一条没红 —— 破坏点写得不对。改成 `if False:` 直接掐掉抛错那一步才确认它会红
   （3 条）。⚠️ 这是第 44 章「sabotage 要能看出跑了几条」的同一个形状第二次出现：
   **只看「红了几条」分不清「守卫失效」和「破坏没打上」。**

2. **`import` 被插进 `from x import (` 的括号里。** 批量给测试文件加 `_roster` 导入时，
   正则匹配到的是括号内第一行。第三次犯（批 N/O 各一次）—— 插入点要找**最后一个
   右括号之后**，不是「最后一个 import 关键字之后」。

3. **`_ev()` 的默认值是 int，result 写的是 float。** 三个 `facts_split` 文件里
   `result={f"{agent}_x": 1}` 配 `_ev(..., value=1.0)`，在等值检查下当场对不上。
   这类夹具不一致以前不会有人发现 —— 因为没有任何东西在比它们。

## 本章要点

| 要点 | 一句话 |
|---|---|
| 「有证据」≠「证据支持这个值」 | 只查前者的检查读起来像在验证，实际只验证了字段名对上了 |
| 一个检查只回答一个问题 | 把「合不合法」混进「一不一样」，结果是把别人的错误报成自己的（NaN 那次） |
| 判等口径要与回放同源 | 否则会出现「契约说相等、回放说不等」这种最难查的矛盾 |
| 🔴 局部观察只能支撑局部结论 | `MissingItem` 判等只看 code 是真的，「卡上会少一条」是错的——中间隔着复合键去重 |
| 「只能靠猜文本」= 信息放错了位置 | 与其改进猜的算法，不如让生产方把它写进结构化字段 |
| 凑数的夹具就是洞的演示 | 25 处「占位 missing」一直在示范那个被放行的场景 |
| sabotage 要分清两种 0 | 「守卫失效」和「破坏没打上」都表现为 0 条红 |
