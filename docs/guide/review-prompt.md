## 这是什么

EasyUp for BigA 2.0：基于 OpenClaw 的 Multi-Agent A 股短线**决策辅助**系统。
不自动执行交易，产出一张证据可追溯、可回放的 Decision Card，最终决策由人做。

当前状态：Phase 2 进行中，出口条件 6/8。7 个 Agent（Supervisor + Stage 1 五个
+ Stage 2 一个），659 条测试，SQLite schema v5。

## 🔴 先读这个警告，它是本次评审最重要的一条

**这个仓库的文档非常详尽、而且高度自省** —— 它会主动列出自己踩过的坑、
承认哪些数字不可比、标注哪些结论证据不足。

这很容易产生一种错觉：**「他们连这个都想到了，那应该没问题」。**

但「把问题写进文档」和「把问题解决掉」是两回事。而且本项目自己就反复
栽在同一个形状上：**守卫写了却从没见它红过**、**检查通过是因为它什么都没查**。

⇒ **不要以文档为准。以你自己跑出来的结果为准。**
每当你准备写下「文档里说……」，先问一句：我验证过吗？

## 请重点攻击这五个面

### 1. 🔴 守卫是不是真的会红

本项目有大量「守卫」（测试 / 契约校验 / 审查脚本 / 不变式检查）。
**对你抽查的每一条，问同一个问题：把它守的东西破坏掉，它会不会红？**

方法：临时改坏，跑测试，**必须 FAILED**，然后还原。

已知本项目自己抓到过两次「测试没在测它声称的东西」：

- 一条并发顺序的测试，探针改的是一个**根本不承担那个保证**的地方
- 一条判据用中文散文做匹配，而另外两个模块用的是**另一句话**

⇒ 找第三次。特别关注：**AST 扫描类**的测试（它们只看字面量，
f-string 拼出来的东西看不见）、**字符串匹配类**的判据。

### 2. 🔴 有没有「通过是因为什么都没查」的检查

这个形状在本项目出现过至少三次：

- 强推时 pre-push 扫的是 `旧..新` 区间，而旧 commit 已不可达 ⇒ 空区间 ⇒ 报绿
- `agents_wait` 对所有 id 返回 `not_found`，瞬时返回，看起来像「等过了」
- 一个越界检查因为路径前缀关系 100% 误报，于是被当成噪音

⇒ 对每个检查问：**它在什么条件下会「无事可查」？那时它报什么？**

### 3. 🔴 静默 fail-open

项目的第一红线是 `UNKNOWN ≠ PASS`：算不出来必须说算不出来。

请找：**有值、但值是错的**的路径。比 missing 更危险，因为它不会被看见。

已知的形状（用来举一反三，不是让你复述）：

- 一个今天的数，挂着上一个交易日的时间戳
- 盘前接口返回全 0，被当成「今天涨停 0 家」
- 排序榜全 0 时「第一名」是任意的一行，而读起来毫无破绽

⇒ 特别查：**无日期字段的数据源**、**分母为零的比值**、
**排序后取 top-N**、**跨源做除法**。

### 4. 契约与数据层的洞

- `skills/_contract/` 声称是 Evidence / AgentVerdict / DecisionCard 的唯一实现。
  **有没有第二套？** 有没有绕过它构造的路径？
- `skills/_store/db.py` 声称是唯一 DB 入口。**有没有裸 `sqlite3.connect`？**
- 只追加由触发器强制。**触发器真的拦得住吗？** 试着 UPDATE 一行。
- 回放（`bin/biga-card --check <号>`）声称「逐字段相同」。
  **它比的是什么？会不会比了个平凡相等？**

### 5. Agent 契约与实际行为的差距

`AGENTS.md`（Supervisor）与 `agents/*/AGENTS.md`（各 Specialist）是提示词契约。

- 契约里写的工具名、参数、命令，**在运行时真的存在吗**？
  （本项目栽过一次：契约推荐的「快路」从来没生效过）
- 契约有没有给同一个动作**两条路**？（那样 agent 会两条都走）
- 契约声称「不许做 X」，**有没有机器在管**？还是只是一句话？

## 可用的核查手段

```bash
bin/biga-card --list                                  # 已有的卡
bin/biga-card --show <号>                              # 看一张
bin/biga-card --check <号>                             # 回放一致性
python3 tools/verify/agent_trace.py                   # 各 agent 的调用序列
python3 tools/verify/latency_report.py --parallel-check
python3 tools/verify/isolation.py --print-mtime       # 隔离自检
python3 tools/verify/missing_ledger.py                # 缺失项台账
tools/verify/audit_public.sh --worktree               # 公开内容审查（九项）
tools/verify/probe.sh <命令>                           # 在一次性库上跑，不污染真库
```

🔴 **要动数据库就用 `tools/verify/probe.sh`** —— `_store` 是追加式的，
写错的行**删不掉**（本项目自己污染过 6 行）。

🔴 **所有 OpenClaw 命令走 `~/.openclaw-biga/bin/biga`**，不要直接敲 `openclaw` ——
那会读写同机另一套实例的状态目录。

## 输出要求

按**严重度**排序，每条写清四件事：

```
[严重度] 一句话结论
  证据    ——  你**跑了什么命令、看到了什么**（不是「文档里说」）
  失败场景 ——  什么输入 / 什么条件下会出错，错成什么样
  为什么现有守卫没抓到  ——  这条最重要
```

严重度口径：

| | |
|---|---|
| 🔴 高 | 会产生**错误但看起来正常**的结论（静默 fail-open） |
| 🟡 中 | 守卫失效、或验收证据不成立 |
| 🟢 低 | 可维护性、一致性 |

最后请单独回答三个问题：

1. **如果只能修一个，修哪个？为什么？**
2. **哪一条「已被证明」的结论，你认为证据其实不成立？**
3. **有没有哪个地方，你试着攻击但没攻破？** —— 这条同样有价值，
   它告诉我们哪些防护是真的。

⚠️ **如果你什么都没找到，请直说**，不要为了凑数报告风格问题。
但在说「没找到」之前，确认你**真的跑过东西**，而不只是读过文档。

## 给评审结果的后续处理

拿到结论后，按本仓库的规矩：

1. **先复现**再动手 —— 报告可能是错的（本项目的 agent 也误报过）
2. 修完**用探针验证守卫会红**，否则等于没修
3. 同一个 commit 里更新 `CHANGELOG.md`，写**为什么**
4. 如果是「已知但没做」的，补进设计文档的已知问题，不要当成新发现
